  is experimental. Use the correct clean-start model; do not add compatibility
  paths, fallback behavior or weakened contracts to preserve old experimental
  rows (Master1). Within the requested task, agents may directly read/write,
  repair data and delete experimental duplicates in these Sigma databases
  without repeated permission requests. Verify the actual target and bounded
  scope, preserve tenant/permission/financial correctness and record operations
  and results. This data grant does not cover production, out-of-project access, full data reset,
  or database drop. The migration rule below separately covers scoped schema changes.
- An unqualified review/audit is source-read-only. It may update the prescribed
  review artifacts, but not application source, configuration or instructions.
  A plan-only request stops at the plan. A named phase executes only that phase.
- A request to implement/fix/refactor or the direct review-and-refactor command
  authorizes the confirmed in-scope implementation. Freeze consumed contracts,
  continue to reconciliation and the in-app screen guide, and do not stop at a
  plan when authorized decisions are resolved. Pause only the portion dependent
  on an exact missing material business/API/financial/permission decision.
- An authorized implementation that needs a schema change includes creating and
  applying its scoped EF migration on the verified Sigma experimental database.
  Review the designer, model snapshot and SQL, verify the applied baseline and
  dependencies, then confirm schema and EF history under Master7. Do not apply
  unrelated pending migrations. A direct phase-only, review-only or plan-only
  request retains its scope. Production, full reset and database drop require
  separate explicit authorization.
- Local builds of affected projects are authorized for implementation verification,
  including a test project when its source changes. Keep builds scoped. Tests,
  lint, commits, pushes and deployments require their existing authorization.
  Scoped experimental-database work follows the standing permission above;
  other database operations require their own authorization.
  Browser automation/application
  verification requires an explicit request for the current scoped workflow;
  mutation in other external systems requires explicit authorization. Skills grant no extra
  execution permission. Keep pending runtime acceptance explicit.
- Do not use the Sigma MCP server, scan the whole solution, refactor unrelated
  code, overwrite user/peer work, or change approved reference modules outside
  explicit scope. Graphify requires an explicit current-task request; no automatic
  queries, updates or hooks. Preserve the current verification and external-access boundaries.
- Never edit generated packets directly. Run the recipe drift check before use;
  reconcile derivative drift through canonical sources and the generator under
  the standing documentation-maintenance authorization, then recheck.

  `SIGMA_FRONTEND_REVIEW_GUIDE.md` or `SIGMA_BACKEND_REVIEW_GUIDE.md`, including
