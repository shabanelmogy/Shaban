## Quantity, billing and reservation rules

- PR source quantities are integer line capacities. ReservationsAsync excludes rejected and deleted PO roots/lines; pending and approved POs both reserve. Discount consumption is also cumulative and source-bounded. PO rejection releases PR use; no reinterpretation as invoicing.
- GRN receiving counts approved/legacy-effective nonvoid receipts. New drafts do not permanently reserve PO receiving capacity; approval rechecks fresh capacity while holding PR lock. A competing approved receipt can make a saved draft fail approval, which is explicit conflict behavior rather than over-receiving.
- Linked GRN source line ID, item/asset, UOM, price, ordered and already-received figures are server-derived. Repeated line identity is rejected. Legacy string LPO/item compatibility fails closed for ambiguous duplicate PO source items.
- Bill PrepareLinesAsync and GetGoodsReceivedNotesAsync agree on whole-GRN reservation: any live nonvoid BillDetail blocks receipt reuse, regardless of approval state; server expands all live selectable receipt lines. It is currently impossible to invoice only part of one receipt line, or part of one receipt document, through this writer.
- Owner confirmed **approved Bills count as invoiced; drafts reserve capacity**. Parent owns new derived status presentation. A PO can be partly invoiced across multiple GRNs, but claiming per-line partial billing within one GRN requires a separately approved source-line schema/writer contract.
- Bill Approve re-runs PrepareLinesAsync excluding itself and compares the complete saved SourceLineKey multiset and financial totals. It executes under allocation → PR locks, so source availability/quantity revalidation and posting remain one transaction.
- PR/PO/GRN approval, quantity use and billing are separate axes; supplier outstanding balance is a further financial settlement axis. Do not map Paid/Closed from source quantity use.

## Findings and exact bounded corrections

### P2 — Pending receipt report includes unapproved and rejected purchase orders

**Evidence:** StockReportsService.GetGrnPendingReportAsync, observed lines 463–470: orderLines filters only d.ItemId.HasValue, without ApprovedStatus. GRN GetPurchaseOrdersAsync/ReceivableOrderIdsAsync, observed lines 483/512, admits only approved Stock/Asset orders.

**Scenario/impact:** A pending or rejected Stock PO appears as an outstanding-to-receive order although no receipt can be created for it. Totals and pending order counts include a canceled/unapproved purchasing obligation.

**Safe minimal correction:** Add h.ApprovedStatus == ApprovalStatus.Approved to the existing orderLines predicate. This preserves current item-level grouping, paging, filters, legacy receipt matching and source identity. Parent was informed and owns any implementation.

**Parent integration observed:** A later source reread shows this predicate now present at StockReportsService.cs:468. The audit worker did not write that application change. Parent owns final scoped-diff and runtime acceptance.

**Compatibility observation:** This report still aggregates received quantity by LPO number + supplier + item (observed lines 493–497), whereas modern capacity uses stable PO and PO-detail IDs and has conservative legacy matching. Historical report matching is recorded in the prior GRN contract. Do not silently replace it without preserving that legacy contract and reviewing duplicate-item effects.

### P2 — Voided Bills remain an effective blocker for receipt Void

**Evidence:** GoodsReceivedNoteService.ProjectList.CanVoid, ReadDetailAsync.hasBill/CanVoid and HasEffectiveReferencesAsync check nondeleted Bill but omit !Bill.IsVoided (observed lines 168–169, 453–458, 869–874 after logging insertion). Bill source selector and PrepareLinesAsync explicitly exclude voided Bills from reservations.

**Scenario/impact:** Approve Bill → Void Bill releases receipt for another Bill and removes its ledger effect, but its retained BillDetail permanently prevents receipt Void. The effective-reference helper disagrees with financial effective/reservation policy.

**Safe minimal correction if the parent freezes effective cancellation dependency:** Exclude voided Bills only from CanVoid and HasEffectiveReferencesAsync; split detail hasBill into historical lock versus effective void lock. Keep historical BillNo and conservative edit/delete HasReferencesAsync unchanged. Preserve approved/legacy ItemIssue blocking; existing Void already excludes voided/rejected issues and atomically voids linked drafts. This is a cancellation-rule correction, not permission to edit historical approved receipts.

### P1 — Workshop Job PO source command remains a preexisting server-boundary gap

**Evidence:** PurchaseOrderService.AddCoreAsync accepts caller POType.JobPO and JobId after existence/type checks (observed lines 236–281); InvalidTypeFields requires a positive Job but no source-owned command; scoped search found no CreateFromJobAsync. Current real caller: Workshop/Job/components/list/list.component.ts:167 navigates /PurchaseOrder/create with sourceJobId. PurchaseOrder/components/details/details.component.ts:365–385 accepts it; :727–754 reads Job; :932 uses ordinary createOrder; services/purchaseorder.service.ts:38 posts ordinary PurchaseOrder.

**Impact:** The valid UI exists, but direct authenticated callers can create JobPO through the generic Add shape and independently supply header/line jobs. This repeats, rather than newly discovers, the 2026-10-21 upstream audit.

**Minimal complete correction:** Add source-owned CreateFromJob(pathJobId,payload), resolve live Job in authenticated tenant, derive Job type and header Job, reject unrelated line Job references; reuse same preparation/calculation/number/save path; update the real editor caller and reject JobPO in ordinary Add together. Blocking generic Add alone breaks the valid Workshop route. Root may retain this preexisting finding outside the current log/status slice.

### P2 — Purchase Return draft delete retains live owned children

**Evidence:** PurchaseReturnService.RemoveAsync returns base.RemoveAsync after pending-state validation (observed final combined method line524 before logging insertion). Base Service.RemoveAsync:942–960 deletes only root. PurchaseReturnConfig.ApprovalStatus is a concurrency token.

**Impact:** PurchaseReturnDetail remains live after draft root soft deletion; this violates owned-aggregate cleanup. It is a scoped instance of BE19 backlog23, not a new generic-engine finding. Inspected financial queries check posting/root identity, so no proven AP double count or posting corruption is claimed.

**Minimal correction:** Use RemoveWithChildrenAsync(id,...,return=>return.PurchaseReturnDetails) under the same JournalVoucherAllocation lock as approve/update, preserve pending/void guards and map concurrency failure to existing conflict result. Do not modify generic Service or historical approved returns. Concurrency token already prevents successful delete after a competing approval, so an orphan posted JV race is not asserted.

## Known boundaries / reconciliation for parent

- No physical supplier return exists in PurchaseReturn; it is a financial supplier debit instrument. Physical ItemReturn is a separate stock owner and must not be confused with it.
- No per-GRN-line invoice source ID is stored by current BillDetail; whole-receipt billing/reservation is the supported baseline. Parent must freeze any new granularity before labeling unsupported progress as known.
- Legacy GRN approval null is intentionally operationally effective; legacy PurchaseReturn approval null is intentionally unproven/read-only. A generic legacy-null policy across these documents would be wrong.
- Source-only audit does not prove production data is consistent, a build succeeds, transactions execute on deployment or historic reports agree. Owner acceptance must cover concurrent receipt approvals, draft Bill reservation/release, partial multi-receipt invoicing, canceled Bill/receipt locks, full supplier AP allocations/statement, GRN stock effect/void, foreign-currency rejection and closed-period rollback.
