# قرارات الموافقات داخل صفوف المراحل

## متابعة الأداء — ١٦ نوفمبر ٢٠٢٦

تفويض المالك «نفذ» بعد تفسير بطء فتح نافذة الموافقات: يعيد مزود موافقات ERP استخدام لقطة المستخدم الناجحة داخل طلب HTTP GET نفسه فقط، مع ربطها بالسياق والهوية ومطالباتها والشركة. فشل/إلغاء القراءة لا يحتفظ بنتيجة، وطلبات الكتابة لا تستخدم هذه اللقطة. تبقى مطابقة عضويات الأدوار وفحص فروع المصدر مباشرَين. لا cache عالمي ولا تعديل لمالك CurrentAccess العام. تُلغى قراءة SubmitApproval غير المستهلكة في شاشة المراحل ويظل endpoint البدء القديم يتحقق بنفسه عند استدعائه. يقل إسقاط السجل إلى أعمدة العرض فقط، ويعاد استخدام هوية أمر الشراء من إسقاط قراءته الأولى بدل استعلامها ثانية. حساب نسخة المستند وبنوده يبقى مطلوبًا للتحقق من تغير المحتوى؛ لا يُختصر عقد النسخة أو يُخزّن عبر الطلبات. لا تغيير شكل الواجهة أو مخطط البيانات. البناء المحصور متاح والاختبارات/HTTP/SQL وقياس الزمن معلّقة.

طلب المالك عرض المراحل مباشرة كصفوف مع الإجراء داخل كل صف، وإلغاء خطوة البدء المنفصلة ومراجعة تكرار التحميل بعد الحفظ. يحل هذا التعديل محل بدء المحاولة يدويًا في عقد التنفيذ السابق، مع الاحتفاظ بالفصل بين موافقة المراحل وأثر المستند الأصلي.

- القراءة تعرض مستويات السياسة عند عدم وجود محاولة للنسخة الحالية؛ لا تكتب القراءة بيانات. الصفوف تعرض الترتيب والاسم والحالة وصاحب القرار وتاريخه وسببه. الإجراء يظهر فقط للمرحلة الحالية المؤهل لها المستخدم.
- أول قرار ينشئ المحاولة ويلتقط السياسة ويسجل الموافقة أو الرفض في معاملة الخادم نفسها وتحت القفل الحالي. التحقق يشمل View وManageApproval والتعيين والفرع؛ لا يتطلب زرًا أو طلب SubmitApproval مستقلاً. يظل endpoint البدء القديم مستقلاً إن احتاجه مستهلك قائم، ولا تستدعيه نافذة الحالة.
- يستخدم ExpectedVersion القائم رمزًا غير فارغ قبل البدء مرتبطًا بإصدار السياسة ونسخة المصدر وأحدث محاولة. تغير أي منها يرفض القرار القديم. بعد البدء يستخدم إصدار المحاولة الحالي. يضاف ExpectedOrder اختياريًا إلى DTO للتوافق مع المستهلك الحالي، وترسله الواجهة المعدلة دائمًا لتحديد الصف وتحقق التسلسل. لا تجاوز لعضوية الدور باسم TenantAdmin.
- يضيف ملخص المرحلة ومرحلة المحاولة CanDecide وActor وDecidedAt وReason. تملأ البوابة الأصلية وواجهة السير هذه البيانات من نفس المالك. تختار واجهة السير مستويات النسخة الحالية؛ تبقى قرارات المحاولات السابقة في السجل.
- يعتمد عرض الصفوف على DataTable وActionList الحاليين، لا جدول أو قائمة إجراءات بديلة. يبقى تأكيد الموافقة الواحد وسبب الرفض. يبقى الإجراء التشغيلي الأصلي عند توفره بعد الموافقات تحت قواعده السابقة.
- يستخدم المكون المشترك نتيجة POST الموثوقة لتحديث المراحل مباشرة. نافذة سير فقط لا تحتاج GET متكررًا بعد نجاح الحفظ؛ المستند الأصلي قد يحتاج قراءة واحدة لتحديث صلاحية الإجراء التشغيلي. يمنع إعادة تحميل ذاتية دائرية عبر أحداث القراءة/الحفظ أو تغير الهوية المرجعية.
- قراءات السياسة والسير تشغيلية مباشرة بلا cache جديد. لا طلب لكل صف ولا lookup أسماء إضافي. لا تغيير مخطط أو اقتراح فهرس جديد بسبب هذا التعديل؛ فهارس RunKey ونوع المستند ومعرفه الحالية تحتاج قياس SQL عند القبول. لا ادعاء بتحسن زمني مقاس من المصدر.

الملكية: الجذر للمكوّن المشترك وعرض الصفوف والترجمة والدليل والمطابقة؛ عامل خلفية محصور للخدمة وDTO ومواصفاتها. البناء مسموح، تشغيل الاختبارات والمتصفح وقاعدة البيانات غير منفذ. مرجع الشكل UI7 وUI6 وUI22 ومكوّن DataTable الفعلي. مرجع Speed المؤرخ 2026-10-28 لشاشة أوامر الشراء يثبت الإجراءات الأصلية؛ تغيير المراحل مبني على طلب المالك وعقد Sigma، ولا توجد فجوة مفاهيمية تستدعي Odoo.
