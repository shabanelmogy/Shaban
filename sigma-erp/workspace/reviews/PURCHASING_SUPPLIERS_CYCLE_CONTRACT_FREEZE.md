## Owner clarification — posting and eligible movements (2026-10-21)
The owner confirmed that Approve must atomically post a **balanced** financial journal and persist the selected allocation, with manual approval in the record until Settings owns the policy. Official Odoo vendor-credit-note documentation was consulted as a comparison: the economic return/credit entry is distinct from subsequent reconciliation with open partner entries. This is a design inference for Sigma, not a copy of Odoo's reversal/void behavior; Sigma's terminal flag-only Void rule remains unchanged.

The owner corrected the initial bill-only reading of the screenshot. The selectable movements can originate from different supplier voucher types; show **only movements currently eligible for allocation**, not every historical movement. Eligibility requires same tenant/supplier, compatible payable control account, currency and branch policy, posted and not voided source, opposite signed open supplier balance, positive remaining capacity, and an unexpired/unchanged balance at approval. The server owns the eligible list and must re-read it under the allocation lock during Approve. Do not infer eligibility solely from voucher labels (Receipt, Bill, Credit Note or JV); the actual posted partner line and effective allocations decide. An individual purchase return cannot be linked to a source only by its printed voucher number.

The return's balancing credit account and any input-tax reversal must be derived from a selected original bill's posted lines **or** an explicit validated account/tax basis when the return is standalone. The existing PurchaseReturn schema and API contain neither basis, and its details have no stable source voucher/line keys; therefore financial implementation still requires a new typed contract and owner migration. Never create a one-sided journal, a same-account debit/credit to simulate posting, or allocations from the caller's `AlreadyAllocated`/`Due` fields. Approval must be absent or unavailable until that vertical slice is real, and retained legacy rows stay read-only/unproven rather than silently backfilled.

## Owner-derived contract selection — independent supplier return (2026-10-21)
Asked which scenario is clearest from the images, the reviewer identifies an independent supplier-return document: the header has no source-Bill selector and the table is a set of movements to reconcile, not original Bill expense/tax lines. The owner requires a balanced journal on approval. Add a positive return amount and explicit active expense/asset/return counter account to the header. Approve posts Dr the supplier's actual AP control account and Cr the selected counter account for the same amount, then writes allocations from this new debit AP line to eligible opposite credit AP lines. The sum allocated may be less than the return amount, leaving on-account supplier credit; it may never exceed the amount or any source's live remaining capacity. No tax reversal is inferred without an explicitly linked source tax document; no physical stock movement is implied. This follows the documented supplier debit-note accounting pattern (Dr AP / Cr cost-or-return account), while the selected movements implement reconciliation. It also resolves the legacy screenshot's one-sided journal error without fabricating a same-account balancing line.

New typed API owns amount/account/source-line IDs and approval state. Legacy stored rows contain no stable source IDs or proof of posting: keep them read-only with unknown approval and exclude them from automatic allocation/posting until individually repaired. Add the `PurchaseReturn` journal voucher type **at the end** of the persisted enum so existing numeric meanings do not shift. Owner migration is required for the new aggregate references/status and persisted allocation identity. PurchaseReturn stays independent from the existing Bill and DebitNote writers; no duplicate journal is created from those modules.
