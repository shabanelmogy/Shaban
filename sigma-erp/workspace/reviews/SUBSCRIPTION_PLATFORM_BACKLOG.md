## الحالة التشغيلية الحالية — ٦ نوفمبر ٢٠٢٦

ثبت تسجيل شركتين نشطتين وربط مديري Identity وERP بكودين واشتراكين
مختلفين، على قاعدة اشتراكات محلية بطلب المالك مع إبقاء Security/ERP على
الهوست. نجحت٦٣ حالة HTTP وأمكن إنشاء المستخدم العادي واستكمال فشل هويته
وتغيير الدور والمنح وحمايات المالك والعزل. نجحت تجربة شاشة الأدوار ووصول
المستخدم والعربية/RTL والداكن والموبايل في النطاق الموثق.

المرجع الحالي هو [قبول التشغيل](Authorization/TENANT_ACCESS_RUNTIME_ACCEPTANCE.md).
الأقسام التالية سجل تطور مؤرخ؛ عبارات configuration-only وauthenticated-only
وغياب الربط أو إذن التشغيل لم تعد تصف الشريحة الحالية. لا تغلق هذه النتائج
الفوترة والتجديد والحصص وCRUD القديم وبقية الملاحظات المفتوحة في الجدول.

## واجهة Roles & Permissions — توجيه المالك ٥ نوفمبر ٢٠٢٦

اعتمد المالك النص المرفق كمرجع الشكل التفاعلي للشاشة. ينطبق على المسار الموجود
`SiGmaAngularFrontEnd/src/app/modules/Administration/Roles` والمكوّن المشترك
`shared/components/permission-tree`؛ لا ينشئ API أو صلاحيات جديدة من أسماء
المثال. المطلوب المرئي: قائمة أدوار قابلة للبحث والفتح، محرر واسع للصلاحيات،
اختيار جزئي/كلي واضح، حالات تحميل/فشل/فراغ/تأكيد وحفظ، RTL/LTR والوصولية،
وعرض الصلاحيات الفعلية من الكتالوج الخادمي.

المصدر الحالي يطابق جزءًا كبيرًا من المرجع: `RolesComponent` و`RoleDetailsComponent`
و`PermissionTreeComponent` و`UserAccessEditorComponent` موجودة، ومعها حالات dirty,
conflict, retry, confirmation, direct grants وeffective preview. ويظل النص
«configuration only / enforcement deferred» صحيحًا حاليًا.

الفجوة التي لا يحلها الشكل: `AuthorizationController` وCRUD المستخدمين/الأدوار
يظهران مصادقًا فقط، و`AuthorizationConfigurationService.EnforcementEnabled=false`؛
التوكن الحالي يحمل Identity user id النصي، بينما شاشة User Access تحتاج ERP
`User.Id` رقميًا. لا يُحوّل prompt الواجهة هذه الفجوة إلى صلاحية فعلية.
قبل تفعيل الحراسة يجب إنشاء ربط ثابت IdentityUserId↔ERP User.Id داخل نفس
SubscriptionId، وإرجاع ERP user id أو current-user mapping، ثم إضافة evaluator
موحد للكتالوج نفسه إلى مسارات الخادم. المسارات غير المصنفة تظل غير قابلة للمنح
حتى يصدر لها تصنيف موثق؛ لا تُستخدم أسماء الأزرار كحماية.

قرار الشريحة التالية: تنفيذ bridge مالك Tenant أولًا، ثم إنشاء المستخدمين العاديين
بهوية Security وسجل ERP واحد، ثم تفعيل اتحاد الأدوار والمنح المباشرة على العمليات
القابلة للتصنيف فقط. الصلاحيات الموروثة/المنع المباشر/النطاقات الفرعية غير
مفعلة في العقد الحالي.

## جسر الهوية والصلاحيات — متابعة ٥ نوفمبر ٢٠٢٦

أضيفت مصدرّيًا خطوة ربط `ApplicationUser.ErpUserId` مع `User.IdentityUserId` و`IdentityRegistrationId`، وإنشاء ERP owner في قناة خدمة داخلية، مع دور نظامي `TenantAdmin` وإسناد أولي وتفعيل ERP بعد تفعيل Identity. أضيفت سياسة `TenantAdmin` لواجهات إعداد الصلاحيات، وحراسة permission filter للعمليات المصنفة، ومنع الكتابة عبر CRUD القديم لـPermission وRolePermission. الدور النظامي محمي من تعديل/حذف RoleService. ما زال هذا المصدر يحتاج هجرات المالك:

- `LinkIdentityUsersAndProvisionTenantOwner` لحقول User/Role/IdentityRegistration والفهارس.
- `AddTenantIdentityRegistry` لتخزين ErpUserId في Security.

يظل تقييم الصلاحيات غير المصنفة authenticated-only إلى أن تصنف بسمات كتالوج صريحة. إنشاء المستخدمين العاديين عبر Identity وربطهم بـERP User ودورة الإدارة من شاشة Users ما زال بندًا لاحقًا. لا تعتبر تسمية الدور وحدها إثباتًا للمالك؛ مسار المالك يعتمد claim Admin من Security وربط ERP الدقيق.

اعتمد المالك البرومبت المرفق كعقد شكل الشاشة: القائمة/المحرر/شجرة الصلاحيات/الحالات/RTL والوصولية. المصدر الحالي يملك هذه الشاشة والمكوّنات؛ التغيير الحالي يربط الخادم والحراسة ولا يعيد بناء الشكل من بيانات تجريبية.

## المصالحة الجارية — ٦ نوفمبر ٢٠٢٦

القراءات أعلاه مؤرخة؛ الحالة الحالية أحدث منها:

- فُلتر المنصة وملف التشغيل يضمان الآن MVC وSubscriptionAPI وSecurity وServerAPI مع تبعياته. تشغيل ERP لازم لخطوة إنشاء مالك الشركة، ولا يثبت ترتيب الإقلاع جاهزية HTTP.
- تُحفظ روابط Identity وERP في سجل التسجيل قبل التفعيل، وتعرض النتيجة معرف ERP صراحة. إعادة الطلب تطابق المعرفات ولا تغيّر كلمة المرور.
- منع تفعيل Security قبل وجود رابط ERP صحيح، وحماية الاسم والدور والإسناد النظامي، ومنع حذف/تعطيل المالك عبر إدارة المستخدمين.
- شريحة Users تنشئ مستخدمًا عاديًا في Security بمعرف تسجيل ثابت. عند الفشل الجزئي تعيد رقم ERP وإيصالًا بمسار الصورة المحفوظة؛ تعرض الواجهة الاستكمال بدل تكرار إنشاء الملف. لا كلمات مرور في كتابة ERP، ولا تعديل لاسم الدخول والبريد المسجلين عبر ملفه.
- تم تصحيح مقارنة Boolean في UserService، وجعل اختياري contact/branch nullable في DTOs حتى لا يتحول عدم الاختيار إلى FK بقيمة صفر.
- الكتالوج والحارس يستهلكان resolver واحدًا؛ الحارس يتحقق من الهوية الفردية ومستخدم ERP النشط لكل action غير مستثنى، ويفحص المنح للعمليات المصنفة. أعلام الواجهة والدليل أصبحت تصف هذا الإنفاذ الجزئي بدقة. ما زالت تغطية كل الإجراءات المخصصة قيد الجرد والتصنيف.

المخطط المطلوب عند المالك: `AddTenantDirectOnboarding` متضمنًا `ErpUserId`، و`AddTenantIdentityRegistry`، و`LinkIdentityUsersAndProvisionTenantOwner`، وإضافة correlation وفهرسي Identity عبر `AddIdentityUserRegistrationCorrelation` إن لم تُدمج في الهجرة الأولية. لا هجرات أُنشئت أو شُغلت.

التحقق المنفذ مصدرّي فقط، مع تدقيق مستقل لشريحتي التسجيل والمستخدم العادي. البناء والاختبارات والمخطط والتشغيل الفعلي والقياسات لم تُنفذ؛ الهدف الكلي ما زال Active، وتبقى تغطية endpoints وقبول الدورة الفعلية مطلوبين.

## تسليم المصدر الحالي — ٦ نوفمبر ٢٠٢٦

أُنجز التصنيف المصدرّي بقائمة ثابتة من ٥٩١ عملية مخصصة، وتمت مطابقتها
بالجرد بلا مفقود أو زائد أو مكرر. حُميت العمليات الـ١٧ السابقة بالمصادقة،
وصار غير المصنف مرفوضًا للمستخدم العادي؛ لا يتاح له endpoint جديد دون مراجعة.
أصلحت مفاتيح الموافقات الديناميكية، والتفعيل المدعوم مع الاستثناءات المرفوضة،
وتطابق Module/Action في المعاينة والحارس. أُغلق سباق ربط المالك مصدرًا
بمعاملة Serializable، مع بقاء قبول سباقات SQL عند المالك.

عناوين authenticated-only وpending inventory في الأقسام المؤرخة السابقة
تصف لقطتها فقط. الحالة الحالية موثقة في
[مصالحة دورة الوصول](Authorization/TENANT_ACCESS_FINAL_RECONCILIATION.md)
و[عقد الإنفاذ](Authorization/PERMISSION_ENDPOINT_ENFORCEMENT_CONTRACT_FREEZE.md)
و[جرد العمليات](Authorization/ENDPOINT_AUTHORIZATION_INVENTORY.md).
الواجهة تعرض ملخص المنح والسحب ومسودة النسخ ورسالة رفض الوصول؛ تفاصيل
البرومبت التي لا يدعمها العقد ما زالت مسجلة للتوسعة. يتبقى قبول المالك
للمخطط والبناء والتشغيل والقياسات، ولم يتحول الهدف إلى Complete.

متابعة إغلاق الدورة: أضيف نشاط الدور الحالي إلى snapshot الحفظ مع نسخة
التزامن، مع بقاء الدور النظامي محميًا. أصبحت نتيجة الوصول المحفوظة تعرض
اتحاد الخادم وتتيح التحديث، بينما الحساب المحلي للمسودة فقط. أُصلح أيضًا
استبدال اتصال ERP المهيأ من المضيف داخل OnConfiguring بحارس IsConfigured؛
لا تغيير لقيم الاتصال ولا أوامر قاعدة بيانات. تفاصيل التوافق والقبول في
ملحق تدقيق الإغلاق بملف المصالحة أعلاه. لا هجرة إضافية لهذه الإصلاحات.
