# مراجعة شاملة لنظام الصلاحيات

| البند | القيمة |
|---|---|
| Status | Review — source-only |
| التاريخ | ١٠ نوفمبر ٢٠٢٦ |
| الفرع | `codex/document-approval-workflows` في SigmaBackend وSiGmaAngularFrontEnd (نسخة العمل على الجهاز، شاملة أي تعديلات غير مسجلة) |
| النوع | مراجعة مستقلة من المصدر؛ لا build ولا تشغيل اختبارات ولا تجربة طلبات |
| Owner verification pending | yes |

> ملاحظة: أثناء المراجعة تغيّرت ملفات على الجهاز (`RentalAgreementController.cs`، `FileStore.cs`، `MediaController.cs`، `route-access-policy.ts`). المراجعة لقطة من لحظة القراءة.
>
> الأسرار المذكورة هنا مُخفاة عمدًا. لم تُنسخ قيمها في هذه الوثيقة.

## ١. الخلاصة

التصميم الأساسي قوي:
- مرشّح واحد يرفض أي عملية غير مصنّفة (fail-closed).
- محلّل واحد يستخدمه الكتالوج والتنفيذ معًا.
- نطاق الفروع محور مستقل يُطبَّق على القراءة بفلاتر EF عامة، وعلى الكتابة عند `SaveChanges`.
- توجد سجلات تدقيق، وتحكم في التعديل المتزامن، واختبارات كثيرة.

لكن أخطر المخاطر **ليست في منطق الصلاحيات نفسه**، بل فيما حوله:
- أسرار مسجّلة في Git، على رأسها مفتاح توقيع JWT.
- أداة مسح قاعدة بيانات تمسح كل الشركات معًا.
- توكن صالح ١٤ يومًا.
- واجهة إنتاج تتصل عبر HTTP.

أي واحدة من هذه تتجاوز كل طبقات الصلاحيات الأخرى.

| الخطورة | العدد | البنود |
|---|---|---|
| حرجة | ٢ | C1 الأسرار في Git · C2 مسح قاعدة البيانات لكل الشركات |
| عالية | ٤ | H1 عمر التوكن ١٤ يومًا · H2 HTTP في الإنتاج · H3 منح لا تعمل · H4 الاعتماديات غير معلنة |
| متوسطة | ٦ | M1 مصدران لصفة المدير · M2 هشاشة المفاتيح · M3 الرفع العام · M4 الأداء · M5 سهولة الكتالوج · M6 فجوات الاختبار |
| منخفضة | ٦ | L1–L6 |

## ٢. البنية كما هي في المصدر

```text
Angular ── Bearer (localStorage) ──► SiGma.ServerAPI
                                      │
  SiGma.Security (Identity) ─ JWT ────┤ 1) JwtBearer: توقيع/issuer/audience/عمر + تطابق subscription_id مع NameIdentifier
  claims: sub, subscription_id,       │ 2) PermissionAuthorizationFilter (Order -1000)
  erp_user_id, role=Admin|SuperAdmin  │    ├─ CurrentAccessService.ActorAsync: ربط sub+tenant+erp_user_id بمستخدم ERP نشط
                                      │    ├─ BranchAccessSnapshot لكل طلب (فروع العرض/التسجيل/التحويل)
                                      │    ├─ عمليات للمدير فقط (FiscalYear/MonthClose/OpeningBalance) بالاسم
                                      │    ├─ مدير = IsInRole("Admin"|"SuperAdmin") ⇒ تجاوز كامل للمنح
                                      │    └─ غير ذلك: مفتاح Resource.Action من PermissionEndpointResolver
                                      │       ∈ (منح مباشرة ∪ أدوار نشطة) + شروط اعتماد مكتوبة يدويًا
                                      │ 3) EF Global Query Filters: SubscriptionId + فروع (BranchScopeRegistry)
                                      │ 4) SaveChanges: PrepareBranchAccessWritesAsync يتحقق من ملكية الفروع
```

- **مصادر المفتاح** (`PermissionEndpointResolver.Resolve`): attribute صريح، ثم قواعد الاعتماد، ثم ربط CRUD العام، ثم قائمة `ReviewedPermissionOperations` (٥٩٦ عملية). أي شيء غير ذلك يصبح «Unreviewed» ولا يُسند.
- **الواجهة**: تقرأ `GET /Authorization/me` وتعيد القراءة كل ٦٠ ثانية وعند التركيز. فيها `RouteAccessPolicyRegistry` (١٩٧ سياسة مسار)، و`currentAccessGuard`، و`appAuthorize`. المسار غير المسجّل مغلق للمستخدم العادي.

## ٣. نقاط القوة

١. **الرفض الافتراضي**: أي endpoint جديد مغلق على المستخدم العادي حتى يُراجَع.
٢. **مصدر حقيقة واحد**: الكتالوج والتنفيذ يستخدمان نفس المحلل، فما يظهر في شاشة الأدوار هو ما يُطبَّق.
٣. **عزل الشركات على مستوى البيانات**: فلتر `SubscriptionId` عام على كل `EntityBase` (`BranchScopeRegistry.Apply`). إذا لم تُحل اللقطة يصبح الفلتر `SubscriptionId == 0` فلا تُرجع بيانات (fail-closed).
٤. **نطاق الفروع محور مستقل** عن صلاحية العملية، بثلاثة مستويات (عرض / تسجيل / تحويل)، ويُتحقق منه عند الكتابة أيضًا.
٥. **الدخول باسم مستخدم (impersonation)**: توكن ١٥ دقيقة بدور `User` فقط، ومنع انتحال المالك، وسبب إلزامي، وتسجيل التدقيق قبل تسليم التوكن، وإظهار هوية المدير في سجل التدقيق.
٦. **التعديل المتزامن**: `Role.AccessVersion` و`UserAccessRevision` و`UserBranchAccess.AccessVersion` مع Serializable عند أول إدراج.
٧. **مسارات الخدمة الداخلية** محمية بمفتاح خدمة لا يقل عن ٣٢ حرفًا ومقارنة ثابتة الزمن.
٨. **الملفات الخاصة** (حوادث، مستندات مركبات، تصحيحات، أوامر شراء، عقود): مخزنة خارج `wwwroot`، ويُمنع طلبها كملف ثابت، وكل قراءة تتحقق من الفرع والمنحة.

## ٤. الملاحظات

### C1 — حرجة: أسرار التشغيل مسجّلة في Git

**الدليل:** الملفات `SiGma.Security/appsettings.json` و`SiGma.ServerAPI/appsettings.json` موجودة في `.git/index` (متتبَّعة)، و`.gitignore` يستثني `appsettings.Local.json` فقط. تحتوي على:

| السر | الموضع |
|---|---|
| مفتاح توقيع JWT (٤٧ حرفًا، **نفس القيمة في الخدمتين**) | Security:13، ServerAPI:10 |
| سلسلة اتصال قاعدة الهوية بكلمة مرور (خادم مستضاف) | Security:10 |
| سلسلة اتصال قاعدة ERP بكلمة مرور (خادم مستضاف) | ServerAPI:7 |
| كلمة مرور RabbitMQ (CloudAMQP) | Security → RabbitMQ.Password |

هذا يناقض الـ README: «No credential is supplied by tracked settings».

**الأثر:** من يملك مفتاح التوقيع يستطيع صنع توكن فيه `role=Admin` و`subscription_id` و`erp_user_id` و`sub` لأي مستخدم ERP. معرف الهوية `sub` محفوظ في جدول `User.IdentityUserId`، وهو ليس سرًا. ERP API لا يرجع لخدمة الهوية ولا يتحقق من security stamp (`SigmaIdentityAuthentication.cs:35`)، وكل ما يتحقق منه `CurrentAccessService` هو وجود المستخدم وتطابقه. النتيجة: **تجاوز كامل كمدير لأي شركة**. وسلاسل الاتصال تعطي وصولًا مباشرًا لقواعد البيانات.

**الإجراء:**
١. تدوير الأسرار الأربعة فورًا، حتى لو كانت قيم الإنتاج مختلفة. لم أتحقق من قيم الإنتاج.
٢. نقلها إلى user-secrets أو متغيرات البيئة أو مزود أسرار، وترك قيم فارغة في الملفات المتتبَّعة. التحقق عند بدء التشغيل موجود أصلًا.
٣. تنظيف تاريخ Git (`git filter-repo`) أو اعتبار الريبو مكشوفًا.
٤. تفعيل secret scanning على GitHub.
٥. فصل مفتاح التوقيع، أو التحول لتوقيع غير متماثل (RS256): خدمة الهوية تملك المفتاح الخاص، وERP يملك المفتاح العام فقط. هكذا تسريب إعدادات ERP لا يسمح بصنع توكنات.

### C2 — حرجة: `DatabaseReset` يمسح بيانات كل الشركات

**الدليل:**
- `DatabaseResetService.cs:415` ينفّذ `DELETE FROM {table}` على كل الجداول المختارة **بدون فلتر `SubscriptionId`**.
- الحماية الوحيدة: إعداد `DatabaseReset:Enabled` (مفعّل في `appsettings.Development.json:6`)، وعبارة تأكيد، واسم القاعدة.
- العمليات `DatabaseReset.Preview/ResetAll/...` موجودة في `ReviewedPermissionOperations.cs:168-173`، أي **قابلة للإسناد لمستخدم عادي**، وأي مدير شركة (Identity Admin) يمر بالتجاوز.
- الـ README يذكر أن قاعدة ERP مستضافة. لو بيئة التطوير متصلة بها، فمدير شركة واحدة يمسح بيانات كل الشركات.

**الإجراء:**
١. إزالة `DatabaseReset.*` من القائمة المراجعة. **تقييد العملية لـ SuperAdmin فقط** مع شرط بيئة صريح.
٢. أو تقييد الحذف بـ `WHERE SubscriptionId = @tenant`، ورفض التنفيذ إذا كان في القاعدة أكثر من اشتراك.
٣. إضافة اختبار يتأكد أن هذه العمليات غير قابلة للإسناد.

### H1 — عالية: عمر توكن الوصول ١٤ يومًا وERP لا يتحقق من إلغائه

**الدليل:**
- `SiGma.Security/appsettings.json:16` → `TokenValidityInMinutes: 20160`، أي ١٤ يومًا. الـ README يقول ٣٠ دقيقة.
- التوكن محفوظ في `localStorage` (`auth-token.ts:25`).
- ERP لا يتحقق من security stamp.

**الأثر:**
- سحب دور Admin، أو قفل الحساب، أو تغيير كلمة المرور **لا يؤثر على ERP لمدة تصل إلى ١٤ يومًا**. تعطيل مستخدم ERP نفسه يؤثر فورًا.
- أي XSS يسرق توكنًا صالحًا أسبوعين.

**الإجراء:**
١. توكن وصول من ١٥ إلى ٣٠ دقيقة، مع التجديد بالـ refresh token الموجود.
٢. إضافة claim لإصدار الأمان، والتحقق منه في ERP بـ cache قصير (`OnTokenValidated`).
٣. على المدى المتوسط: جلسة بـ cookie HttpOnly كما أوصت وثيقة التصميم §٩.

**متابعة من المصدر — ١١ نوفمبر ٢٠٢٦:** تصدر Security بالفعل claim باسم
`security_stamp`. يتحقق منه مسار `POST /auth/refresh-token` ويستبدل رمز التجديد
عند النجاح. في Angular تحفظ شاشة الدخول رمز التجديد، لكن لا يوجد مستهلك
تشغيلي لمسار التجديد. أول 401 صادر عن رمز الجلسة العادية الحالي يمسح الجلسة
ويبدأ الخروج. الجلسة المفوضة قصيرة وبلا رمز تجديد وتحتفظ بإمكانية الرجوع.
الـERP يفحص صحة JWT وهوية الشركة، والتحقق الحي من الإصدار عنده ما زال مطلوبًا.
الـ١٤ يومًا قيمة ملف الإعداد الحالي، ولم تُقَس مدة خدمة الهوية المنشورة.

الترتيب المقترح للدفعة الأولى هو ربط التجديد بالـAngular واستخدام طلب تجديد
واحد للطلبات المتزامنة مع تنسيق التبويبات لأن رمز التجديد يُستبدل. يجب تجاهل
نتيجة التجديد إذا تغيّر الحساب أو الاشتراك، والحفاظ على المسودة، ومعالجة
انتهاء أو سحب الجلسة دون إعادة إرسال الكتابات تلقائيًا. اختبر انتهاء الرمز
مع أكثر من طلب وتبويب، ورفض رمز التجديد المسحوب، والجلسة المفوضة، واتصال
SignalR. بعد قبول التجديد، اجعل عمر الرموز الجديدة ٣٠ دقيقة. الرموز المصدرة
سابقًا تحتفظ بتاريخ انتهائها، لذلك يُعالج أثرها في خطة تحقق ERP من الإصدار
الحالي وسحب الجلسة. لم يتغير إعداد مدة الرمز في هذه المتابعة.

**تنفيذ الدفعة الأولى — ١١ نوفمبر ٢٠٢٦:** يطلب Angular التجديد قبل إرسال طلب
ERP إذا تبقّى على انتهاء رمز الجلسة العادية دقيقة أو أقل. يدمج الطلبات في
التبويب وينسّق التبويبات على المصدر نفسه باستخدام Web Locks. يستعمل الرمز
المخزّن حديثًا إذا جدّده تبويب آخر لنفس الجلسة. يتحقق من ملكية الجلسة قبل
حفظ النتيجة وقبل إرسال العمل المنتظر. وتستخدم حراس المسودات معرّف جلسة
ثابتًا، بينما يتابع SignalR رمز الوصول الفعلي. تبقى الجلسة المفوضة بلا
تجديد، وتستخدم الجلسة العادية مخرج الرفض الحالي إذا رفضت Security رمز
التجديد. في حال عطل عابر، يمكن استخدام رمز الوصول طالما لم ينتهِ.

تفعيل المسار يتطلب عنوان Security عبر HTTPS ومتصفحًا يدعم Web Locks.
مسار الهوست المضبوط حاليًا عبر HTTP يستمر على دورة الجلسة السابقة. تقبل
التجربة التشغيلية الدفعة عند إثبات حفظ مسودة مفتوحة، وإرسال طلبين أو
استخدام تبويبين قرب الانتهاء مع ظهور تجديد واحد في Network، ومنع إعادة
إرسال طلب كتابة، ومعالجة رمز تجديد مسحوب وتبديل الحساب أثناء التجديد
وإعادة اتصال SignalR. حالات الاختبار مكتوبة ولم تُشغّل. التحقق الحالي
مصدري. خفض المدة والتحقق الحي من سحب الجلسة في ERP متبقيان.

### H2 — عالية: واجهة الإنتاج تتصل عبر HTTP

**الدليل:** في `environment.prod.ts` كل من `remoteSecurityUrl` (سطر 6) و`baseUrl` (سطر 15) يبدأ بـ `http://`.

**الأثر:** كلمات المرور وتوكنات Bearer تمر بدون تشفير.

**الإجراء:** HTTPS مع HSTS، والتأكد من شهادة الاستضافة، وتحويل HTTP إلى HTTPS على الخادم.

### H3 — عالية: منح تظهر في الكتالوج ولا تعمل أبدًا

**الدليل:**
- `FiscalYear.CloseFiscalYear/Verify*` و`MonthClose.CloseMonth/ReopenMonth/ToggleStatus/Update` و`OpeningBalanceBatch.Configure` قابلة للإسناد (`ReviewedPermissionOperations.cs:225,395,409`).
- لكن المرشّح يرفضها لغير المدير (`PermissionAuthorizationFilter.cs:61-102`).

**الأثر:** المدير يسند المنحة ويظن أنها تعمل، والمستخدم يحصل على 403.

**الإجراء:** attribute مثل `[TenantAdminOnly]` يقرؤه المرشّح والكتالوج معًا. العملية إما تُستبعد من الكتالوج، أو تُعرض بعلامة «للمدير فقط». هكذا تحل محل مقارنة أسماء الدوال كنص.

**التنفيذ — ١١ نوفمبر ٢٠٢٦:** اعتُمد إخفاء العمليات الإدارية من الكتالوج. يقرأ
محلّل الصلاحيات علامة `[TenantAdminOnly]` على العمليات الاثنتي عشرة، ومنها
`PUT /MonthClose`. يستخدم المرشّح العلامة لإرجاع 403 لغير مدير الشركة حتى مع
منحة قديمة، ويستبعدها الكتالوج من منح الأدوار والمنح المباشرة. يرفض التحقق
القائم إرسال مفاتيحها صراحة، ولا تعاد إلى نماذج التعديل عند القراءة. تظل مفاتيح
قراءة السنة والشهر ودفعة الأرصدة خاضعة لمنحها الحالية. وُثّق القرار في دليل
الأدوار داخل التطبيق، وحُدّثت حالات الاختبار المصدرية. البناء والاختبارات
وتجربة الشاشة مؤجلة للتحقق التشغيلي.

**متابعة المراجعة:** يرث تعديل الشهر `PUT /MonthClose` من المتحكم العام،
وتظل علامة المدير على الدالة المعاد تعريفها. أضيفت حالة اختبار تقرأ مسارات
MVC وتتحقق من وجود مسار تعديل واحد يشير إلى تلك الدالة. تعرض نافذة الأخطاء
الرسائل العربية والإنجليزية لرموز مدير السنة والشهر والأرصدة الافتتاحية.

### H4 — عالية: اعتماديات الصلاحيات مكتوبة في الكود وغير معلنة في الكتالوج

**الدليل:**
- حوالي ١٢ شرطًا متتاليًا في المرشّح (`PermissionAuthorizationFilter.cs:132-247`)، مثل: `RentalQuotation.Update` يحتاج `View`، و`LeaseAgreement.*` يحتاج `View`، و`Vehicle.Update` مع التفعيل يحتاج `Activate`.
- في الواجهة: فتح `/journalvoucher/create` يحتاج **١٠ مفاتيح** (`route-access-policy.ts:268`).
- الكتالوج لا يعرف أي شيء من هذا.

**الأثر:** المدير يجب أن يعرف الاعتماديات بنفسه، والأخطاء تظهر كـ 403. كل شاشة جديدة تضيف شرطًا آخر للمرشّح.

**الإجراء:**
١. تعريف معلن، مثلًا `[RequiresGrant("X.View")]`، أو جدول `PermissionDependencies` واحد يقرؤه المرشّح والكتالوج.
٢. يرجع `PermissionOptionVM` قائمة `Requires`، وشاشة الأدوار تختار الاعتماديات تلقائيًا.
٣. «باقة شاشة» تجمع مفاتيح المسار (مثل العشرة الخاصة بالقيد) تحت خيار واحد.

**التنفيذ — ١١ نوفمبر ٢٠٢٦:** نُقلت اعتماديات الـAPI إلى `PermissionPrerequisites`.
يستخدمها المرشّح والكتالوج لعرض الشروط الثابتة والمشروطة، ويظهر نقص المتطلب
برسالة مميزة عند 403. لا تُسند متطلبات الطلب المشروطة تلقائيًا. تعرض شجرة
الأدوار المفاتيح الثابتة الناقصة وتضيفها للمسودة باختيار المدير. يمكن إزالة
المتطلب وحفظ دور جزئي، وتوضح معاينة وصول المستخدم ما ينقص من اتحاد أدواره
النشطة ومنحه المباشرة.

تستخدم باقتا إنشاء قيد اليومية (١٠ مفاتيح) وتعديله (١١) تعريفات المسار نفسها
التي تستخدمها القائمة والمحرر. تعرض المعاينة المفاتيح التي ستضاف قبل تطبيق
الباقة. تعرض شاشة الأدوار أيضًا شروط المسارات المركبة من سجل المسارات، بما
فيها البدائل. وُثقت طريقة العمل في دليل الإدارة داخل التطبيق.

حُدّثت حالات الاختبار لرفض الشروط الثابتة والمشروطة، وصحة مفاتيح الكتالوج
وعدم دوريتها، ومعاينة الباقات وإكمال المتطلبات وإزالتها. التحقق المنفّذ
مصدري. البناء وتشغيل الاختبارات وتجربة الشاشات والطلبات ما زالت معلقة.

**متابعة المراجعة:** تستخدم شجرة الصلاحيات ومعاينة وصول المستخدم خريطة واحدة
لمفاتيح ترجمة الشروط الكاملة. عنوان مجموعات «كل ما يلي» و«واحد على الأقل»
في محرر الأدوار يستخدم مفتاحين ثابتين. ثبت من المصدر أن محرر الأدوار
يستخدم الباقتين ووصف شروط المسارات في القالب، وأن نافذة الخطأ تترجم رمز
`AuthorizationPermissionPrerequisiteRequired`.

**المتبقي:** إعداد باقات مسماة لبقية الشاشات بعد مطابقة متطلبات فتحها مع
المصادر الفعلية. تُعرض شروط المسارات المركبة بالفعل في محرر الأدوار.
للقبول التشغيلي، امنح مستخدمًا عاديًا رفع مستند على عقد إيجار في فرع
مسموح، مع حجب عرض العقد وقراءة مستنداته. يجب أن يُظهر محرر الدور المفاتيح
الناقصة وأن يرجع طلب الرفع 403 برسالة المتطلبات. أضف المنحتين ثم أعد التجربة
للتحقق من عبور حارس الصلاحيات.

### M1 — متوسطة: صفة المدير لها مصدران ومخالفة لوثيقة التصميم

**الدليل:**
- التنفيذ يعطي تجاوزًا كاملًا لكل من معه claim الهوية `Admin` أو `SuperAdmin` (`PermissionAuthorizationFilter.cs:127`).
- في ERP يوجد دور نظامي `TenantAdmin` (`IsSystem`)، يُستخدم فقط لحماية المالك في شاشات الإسناد.
- وثيقة التصميم §٥ تقول: «لا يوجد تجاوز لكل العمليات يعتمد على اسم مدير».

**الأثر:** حساب هوية يُعطى Admin عبر `register-admin` أو `assign-role` (من SuperAdmin) يصبح مديرًا كاملًا لـ ERP، حتى لو لم يكن مالكًا في ERP. والعكس: مالك ERP بدون claim لا يحصل على شيء.

**الإجراء:** اعتماد قرار صريح ثم توثيقه، مثلًا: المدير = claim **و** إسناد `TenantAdmin` النظامي النشط. وتوحيد `IsSystemOwner` مع `IsTenantAdmin`.

### M2 — متوسطة: المفاتيح مشتقة من أسماء الكود

**الدليل:**
- `Resource` هو اسم الـ controller و`Action` هو اسم الدالة. الحالة الخاصة `PurchaseRequest→PurchaseRequests` (`PermissionEndpointResolver.cs:27`) دليل على أن ذلك حدث فعلًا.
- منح الأدوار تشترط تطابق `Module/Action` المخزنين مع الكتالوج (`PermissionGrantQueries.cs:40`)، بينما المنح المباشرة تتطابق بالمفتاح فقط.

**الأثر:** إعادة تسمية controller أو دالة تلغي المنح بصمت، ومنح الأدوار والمنح المباشرة تتصرف بشكل مختلف بعد أي تغيير.

**الإجراء:**
١. مفاتيح ثابتة صريحة في attribute.
٢. جدول aliases للانتقال.
٣. تقرير «منح يتيمة» في شاشة الأدوار.
٤. اختبار snapshot لقائمة المفاتيح يفشل عند أي تغيير غير مقصود.

**متابعة من المصدر:** المفاتيح الحالية هي العقد المرجعي. بعض أسماء العمليات
معرّفة صراحة، وبعضها يظل مرتبطًا بأسماء المتحكمات والدوال. ابدأ بجرد ثابت
للمفاتيح القابلة للإسناد وتثبيت موارد العمليات الموروثة وأسماء العمليات
المخصصة. أضف alias فقط للانتقالات الموثقة، وافحص منح الدور والمنح المباشرة
بشكل متسق. تقرير المنح غير المطابقة للكتالوج يأتي بعد مطابقة المفاتيح،
ويحافظ الجرد على `PurchaseRequests`.

### M3 — متوسطة: الرفع العام إلى `wwwroot`

**الدليل:** أي مجلد غير المجلدات الخاصة الستة يُحفظ في `WebRootPath/{tenant}/{folder}` (`FileStore.cs:504`)، ويُخدم عبر `UseStaticFiles` **بدون مصادقة**. اسم الملف GUID، ويصلح من أي شركة إذا عُرف الرابط. يكفي `Media.UploadMedia` للكتابة في جذر الويب العام.

**الإجراء:**
١. جرد المجلدات العامة المتبقية (مستندات العملاء والموظفين مثلًا).
٢. نقل كل ما فيه بيانات شخصية لنفس نمط الملفات الخاصة.
٣. قصر الرفع العام على قائمة مسموحة (شعار الشركة مثلًا).

### M4 — متوسطة: الأداء

**الدليل:**
- `ApiPermissionCatalog.GetEntities()` يبني الكتالوج بالـ reflection في كل نداء.
- `/Authorization/me` يُستدعى كل ٦٠ ثانية لكل تبويب مفتوح، وعند كل تركيز (`current-access.service.ts:69`)، ويستدعي الكتالوج (`CurrentAccessService.cs:72`).
- كل طلب ينفّذ من ٤ إلى ٦ استعلامات: الفاعل، والفروع، والمنح، والاعتماديات.

**الإجراء:**
١. Cache للكتالوج مرة واحدة بعد بدء التشغيل (لا يتغير).
٢. Cache لمجموعة مفاتيح المستخدم مربوط بـ `UserAccessRevision` و`Role.AccessVersion` كما اقترحت وثيقة التصميم §٩.
٣. نقل الشروط الإضافية في H4 إلى نفس المجموعة المحمّلة بدل استعلامات منفصلة.

**متابعة من المصدر:** نداء الدقيقة يعمل عند ظهور التبويب فقط، وتُدمج
الطلبات المتزامنة داخل التبويب. الكتالوج يُعاد بناؤه في الخادم رغم تسجيل
مالكه كخدمة singleton. البداية المقترحة تخزين بيانات الكتالوج الثابتة
بصورة تمنع تعديل اللقطة المشتركة، ثم تحميل مجموعة منح المستخدم مرة لكل
طلب وإعادة استخدامها للمنحة الأساسية واعتماديات H4. يأتي تخزين المنح بين
الطلبات بعد إثبات أن إبطال الذاكرة يغطي تعطيل الأدوار وتغييرات الإسناد
والمنح المباشرة. عدد الاستعلامات تقدير من المصدر حتى يُقاس تحت طلبات ممثلة.

### M5 — متوسطة: سهولة استخدام الكتالوج

قائمة مسطحة بمئات الموارد، والعمليات المخصصة وحدها ٥٩٦. الحقل `Permission.ParentId` موجود وغير مستخدم، ونظام سبيد المرجعي يعرض الصلاحيات كشجرة (`C0037 users.permissionsModal`).

**الإجراء:** تجميع حسب الوحدة بنفس أقسام `MODULE_PERMISSIONS_COVERAGE`، مع باقات الشاشات (H4) وقوالب أدوار جاهزة.

### M6 — متوسطة: فجوات الاختبار

- اختبارات الفلاتر تستخدم `UseInMemoryDatabase` في أغلبها. هذا لا يتحقق من ترجمة فلاتر EF العامة إلى SQL Server الفعلي (`Contains` على مصفوفة، والتنقل عبر عدة مستويات).
- لم أجد في الملفات التي قرأتها اختبار «اكتمال» يمر على كل endpoint ويتأكد أنه مصنف أو للمدير فقط، ولا اختبارًا يمنع إسناد العمليات المدمرة.
- **لم أشغّل أي اختبار.**

**الإجراء:**
١. مجموعة اختبارات تكامل على SQL Server (Testcontainers) لعزل الشركات والفروع.
٢. اختبار reflection يغطي كل الـ ActionDescriptors.

## ٥. ترتيب الإصلاح المقترح

١. **اليوم:** تدوير الأسرار (C1)، وتعطيل `DatabaseReset` أو قصره على SuperAdmin (C2)، وتقصير عمر التوكن (H1).
٢. **هذا الأسبوع:** HTTPS (H2)، و`[TenantAdminOnly]` (H3)، وفحص الـ stamp في ERP (H1).
٣. **قبل الإطلاق:** نموذج الاعتماديات والباقات (H4)، وقرار المدير (M1)، والمفاتيح الثابتة (M2)، والرفع العام (M3).
٤. **تحسينات:** Cache (M4)، وشجرة الكتالوج (M5)، واختبارات SQL Server (M6)، والبنود المنخفضة.

## ٦. نطاق المراجعة

**قُرئ من المصدر:**
- كل ملفات `SiGma.ServerAPI/Authorization` (١٥ ملفًا).
- مسح الـ attributes في كل الـ controllers (٣٤٨ ملفًا)؛ الاستثناء الوحيد `AllowAnonymous` هو `InternalTenantUserController` المحمي بمفتاح خدمة.
- `CurrentAccessService` و`PermissionGrantQueries` و`AuthorizationConfigurationService` و`BranchAccessAdministrationService` و`UserIdentityAdministrationController`.
- `BranchScopeRegistry`: البنية وآلية الفلاتر، وليس كل تعريف ملكية على حدة.
- `SiGmaDbContext.BranchAccess`: خريطة الدوال، وليس كل مسار تحقق.
- `Repository`، والتدقيق، وFileStore، وMedia.
- خدمة الهوية: التوكنات، والمصادقة، وإسناد الأدوار، والمسارات الداخلية.
- الواجهة: `CurrentAccessService` و`permission-requirement` و`route-access-policy` و`currentAccessGuard` و`appAuthorize` والـ interceptors وملفات environment.
- الوثائق: التصميم (§٥ و§٩ و§١١)، والقرارات المعلقة، ومرجع تغطية الوحدات (جزئيًا)، و`ui/26`.

**لم يُراجَع:**
- تبني كل شاشة في الواجهة (١٩٧ سياسة مسار والأزرار).
- كل تعريف ملكية في `BranchScopeRegistry` مقابل منطق المجال.
- خدمات الأعمال التي تستخدم `IgnoreQueryFilters` واحدة واحدة.
- SubscriptionAPI بالكامل، وPlatformAdminDashboard، وCustomerMVC.
- البناء والاختبارات والتجربة الفعلية.
- قيم الأسرار في الإنتاج.
