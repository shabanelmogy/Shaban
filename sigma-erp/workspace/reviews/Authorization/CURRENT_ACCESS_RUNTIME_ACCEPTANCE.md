## أسباب المشكلة الأصلية

الصورة٢٢٢ تثبت نجاح الدخول وظهور قائمة عامة مع أخطاء سياق الفرع والترجمة
ولوحة المتابعة؛ لا تثبت status HTTP لكل طلب. قراءة حساب البريد السابق
المذكور من المالك أثبتت حساب Identity للاشتراك١٠٠٧ مع ErpUserId=null
وعدم وجود ملف ERP مرتبط/مرشح مطابق في الاشتراك. لذلك يرفض ERP قبل
تقييم المنح. وأكد المصدر أن AuthGuard والقائمة والأزرار لا تستهلك منح
المستخدم الحالي، وأن الترجمات كانت تحتاج مفتاحي Language.Options و
Localization.Runtime في الكتالوج بدل اعتبارهما تهيئة تطبيق ذاتية.

لا يُرقّى حساب User تلقائيًا، ولا يُربط بالبريد، ولا تُنشأ له أدوار
لتجاوز الرفض. معالجة الربط إجراء إداري صريح مستقل؛ تقبل الطبقة الحالية
عرض رسالة إعداد واحدة للحساب غير المرتبط بدل سيل طلبات الأعمال.

## تحقق الخلفية المنفذ

- اختبار RED: GET /Authorization/me من مدير الشركة أعاد٤٠٤ قبل الإضافة.
- بناء ServerAPI بعد تنفيذ قارئ الوصول والمرشح والاستثناءات: نجح صفر
  أخطاء، مع١٥ تحذيرًا سابقًا في مالكيJob/Bill وResponse/XML/nullable خارج
  الشريحة. سجل البناء المحلي sigma-current-access-build.log.
- اختبار GREEN: /Authorization/me يعيد٢٠٠ للمدير والمستخدم٢٢، ويعرض
  isTenantAdmin الصحيح وERP user المطابق. المستخدم يستلم Branch.View فقط
  وفق الإسناد المحفوظ؛ لا workspace إداري مكرر أو معرّف عميل لاختيار مستخدم.
- تهيئة CurrentBranch.Options/Mine وLanguage.Options وLocalization.Runtime
  تعيد٢٠٠ للمستخدم المربوط بلا منح أعمال إضافية. workspace يظل٤٠٣؛ الطلب
  الذاتي دون جلسة٤٠١.
- إفراغ منح المستخدم يعيد قائمة مفاتيح فارغة ويمنعDashboard٤٠٣، وإسناد
  دور Branch.View ومنحة GetKinds يعيد اتحادهما، والسحب يزيل المنحة فورًا
  بنفس التوكن؛ revision يتغير. تعطيل مستخدم ERP يعيد٤٠٣ بكود ActorUnavailable.
  أعيد نشاط المستخدم وإسناده الأصلي في finally بعد التجربة.
- حساب الصورة القديم ما زال يدخل Security٢٠٠، وتعيد قراءة وصوله٤٠٣
  مع AuthorizationIdentityNotLinked وبدون DTO منح؛ لا تغيير ربط أو حساب أو كلمة مرور.
- مراجعة security_final_review مستقلة قراءة فقط لم تظهر مانعًا؛ شرط tenant/soft-delete/
  role activity ومطابقة Key/Module/Action محفوظ في القارئ والحارس ومعاينة الإدارة.

قيد معلوم: صفة المدير في JWT قد تبقى حتى تجديده/انتهائه بعد تغييرها في Identity؛
نشاط مستخدم ERP وربطه يُفحصان بكل طلب. لا تتحول هذه الإضافة إلى وعد بسحب JWT مركزي.

## تحقق الواجهة والتكامل

نجح بناء Angular النهائي بعد جميع الإصلاحات في نحو١٢٥ ثانية دون أخطاء. التحذير الظاهر هو
QuantityInputDirective غير المستخدم في PurchaseOrdersComponent، سابق وخارج
النطاق. أعاد الجذر تشغيل جميع اختبارات الشريحة معًا على ChromeHeadless؛
TOTAL:47SUCCESS. تشمل الخدمة والحارس والـpolicy projection والقائمة
وLayout و403 وMockData وأصحاب الأزرار والحوار وcompile-surface للمالكين
وBranch/Role/Users. لا يعتبر ذلك ادعاء نجاح مجموعة اختبارات المشروع كلها.
ملف `tsconfig.current-access.spec.json` يفصلها عن أخطاء specs قديمة خارج
النطاق؛ outDir نسبي ومُخرجه ضمن out-tsc المستبعد. ظهر تحذير Node قديم
util._extend وتحذير تأخر إنهاء Chrome بعد النتيجة؛ الخروج صفر والاختبارات ناجحة.

قبل الإضافة أثبت اختبار المتصفح RED أن المستخدم٢٢ ذو Branch.View يفتح
dashboard ويرسلSnapshot ويعرض كل القائمة. بعد البناء، نجحت الحالات
الثلاث الفعلية: المدير٢١ يرى مساحة الأدوار والقائمة الكاملة؛ المستخدم٢٢
يُحوّل إلى الفروع دون زر إنشاء أو روابطdashboard/roles/accounts، ويرفض
رابط Role المباشر، دون طلب dashboard أو MockData أو أخطاء API في مساره؛
حساب الصورة القديم يرى رسالة عدم ربط واحدة، وطلباه الوحيدان الدخول والقراءة الذاتية.
لا أخطاء JavaScript في المسارات الثلاثة. صور ونتائج التجربة محفوظة خارج المستودع
في [مجلد الأدلة](current-access-20261106)، بما فيه
[حالات المدير والعادي والربط الناقص](current-access-20261106/current-access-ui-results.json).

كشفت المراجعة المستقلة حالة portal: إخفاء غلاف الصفحة لا يخفي حوار
EditorDialog المنقول إلى body بعد سحب View. أكد المتصفح RED ذلك فعليًا
بمسودة Branch مع View+Update، ثم View مسحوبة وUpdate باقية. أُصلح المالك
المشترك بمتطلب صريح للحوار مع حفظ المسودة وعمر الكتابة المستقلة. أعيد
البناء ونفس الاختبار: اختفت الحقول والحفظ عند السحب، وأعاد إرجاع View
نفس قيمة المسودة، دون أخطاء متصفح أو HTTP. شمل المصدر Role dialog
ومتطلبات MockData التابعة وإغلاق قوائم Users المنقولة إلى body. اختبار
إكمال توليد دون preview بعد فقد الوصول أثبت إعادة تحرير النموذج دون

## الملفات والمطابقة والتسليم

الإدارة وترجمات العربية والإنجليزية. لا رفع frontend permissions إلى

الممنوح ومصدره وحالات الربط والرفض وحدود الشاشات غير المتبناة. المحتوى
مصدرًا ثنائي اللغة، ولا ادعاء تجربة كل روابط موضوعات الدليل.

## ترقية الحساب التجريبي بطلب المالك — ٦ نوفمبر ٢٠٢٦

غيّر المالك اختيار المعالجة بطلب «او عدل user الحالى الى admin بدل من User».
نُفذت صيانة بيانات للحساب نفسه `string1005@string1005.com` والاشتراك١٠٠٧؛
لا تغيير لعقد الشاشات أو منح المنصة. الوصف السابق للحساب غير المرتبط
يوثق حالته قبل هذا الطلب.

استُخدم مسار التجهيز الداخلي القائم لإنشاء ملف ERP رقم٢٤ وربطه بالهوية
المحددة ومعرف تسجيل ثابت، وإسناد الدور النظامي المحمي TenantAdmin.
رُبطت الهوية بالملف واستُبدل دور User بدور Admin داخل معاملة محددة للحساب،
مع شروط تطابق الهوية والبريد والاشتراك وعدد الصفوف. لا توجد قناة خدمة
لترقية حساب قديم؛ لذلك اقتصرت الصيانة المباشرة المأذونة على ربط الهوية
وإسناد دورها وإبطال refresh token وتحديث security/concurrency stamps.
تحققت المعاملة من بقاء كلمة المرور والاشتراك، ثم فُعّل ملف ERP بالمسار القائم.

نجحت ثمانية تحققات، منها الدخول بكود١٠١٠٠٧ وكلمة المرور الحالية، وHTTP200
من `/Authorization/me` مع `isTenantAdmin=true` والربط الصحيح، وHTTP200
من `/Authorization/workspace`. لم تُجرَ تجربة متصفح جديدة لهذه الصيانة؛
القبول هنا HTTP وقاعدة بيانات. يلزم خروج المستخدم ثم دخوله لتجديد توكنه.
الأدلة المنقحة دون توكنات أو أسرار في
`current-access-20261106/current-account-promotion.json`.
