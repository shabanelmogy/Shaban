## متابعة تنفيذ كل الشاشات والأحداث — ٦ نوفمبر

الهدف النشط الأحدث «تفعل الصلاحيات فى كل الشاشات بكل الاحداث المتاحة» يوسع التبني التدريجي تحت عقد CURRENT_ACCESS نفسه؛ ليس مجرد بناء النواة أو شاشة مثال. الجرد القائم ٢٦٢مسارًا يبقى قائمة عمل ولا يتحول مرشح resource-only إلى إذن مثبت آليًا.

آخر استكمال مصدرّي بتاريخ٧نوفمبر: تبني الأستاذ وميزان المراجعة ضمن
LEDGER_TRIAL_BALANCE_ACCESS_ADOPTION_CONTRACT_FREEZE.md ومصالحته. امتد مالك
التقارير الحالي بمداخل report/filter.accessRequirement مع reset/sanitization
وإلغاء القراءات والمراقبات والبحث/الطباعة المؤجلين واستعادة grant السريعة.
الجرد٢٢operation-confirmed و١٣٦resource-only و١٠٠unknown و٢context-only و٢alias؛
هناك child adoption صريح لميزان المراجعة تحت Reports الذي بقي unknown.
كل المواصفات/البناء/التشغيل معلقة، ولا مالك حسابات أو query/schema جديد.

الاستكمال السابق مصدرّيًا بتاريخ٧نوفمبر: تبني تقرير اليومية وقائمة ومحرر قيد
اليومية والتخصيص تحت JOURNAL_ACCESS_ADOPTION_CONTRACT_FREEZE.md ومصالحته.
ثُبتت GetJournals وGetById→View وManageApproval ومفاتيح bootstrap الفعلية؛
حُرست معاينة العملة وCSV والمرفقات والمصادر والطباعة والكتابات المرسلة.
الجرد الحالي٢١operation-confirmed و١٣٦resource-only و١٠١unknown و٢context-only
و٢alias من٢٦٢؛ كل التحقق مصدر فقط، والهدف العام active. متابعة أداء
GetJournals الذاكرية مسجلة خارج تعديل الصلاحيات، ولا query/schema جديد.

الاستكمال السابق مصدرّيًا بتاريخ٧نوفمبر: تبني سندات التسليم وفواتير الإيجار وكشوف
التشغيل الفردية/الدفعية في `DELIVERY_NOTE_ACCESS_ADOPTION_FINAL_RECONCILIATION.md`
تحت `EQUIPMENT_RENTAL_ACCESS_ADOPTION_CONTRACT_FREEZE.md`. استُخدمت GetDetailById
لتفاصيل التسليم وManageApproval للقرار، مع مصادر المحرر وMedia والطباعة المؤجلة
واستقلال الإرسال؛ صُنفت أربع قراءات خلفية كعرض كل فروع المستند. الجرد الحالي
عندها١٩operation-confirmed و١٣٧resource-only و١٠٢unknown و٢context-only و٢alias من٢٦٢.
المواصفات الجديدة غير منفذة والقبول التشغيلي معلق؛ الهدف العام ما زال active.

أول دفعة بعد استئناف الأصول، وفق التدقيق الفعلي للـroute/handler/service/controller:

| المسار/الحدث | العقد المثبت |
|---|---|
| قائمة الأصل، قراءته، البحث/الصفحات/تصدير النتيجة المحلية | Asset.View؛ فلتر النوع الاختياري لا يُطلب ولا يُعرض دون AssetType.Lookup |
| إنشاء الأصل | Asset.Create مع AssetType.Lookup وCostCenter.Lookup؛ الفرع سياق ذاتي عبر CurrentBranch/Options |
| تعديل الأصل | Asset.View وAsset.Update مع نفس تبعيات اختيارات المحرر؛ كل من الزر والـhandler والحفظ يتبع المتطلب |
| حذف الأصل | Asset.Delete مع حراس الحالة والتأكيد القائمين |
| عرض الأصل | Asset.View؛ لا bootstrap اختيار غير ممنوح في وضع العرض، وتعرض labels المحفوظة من detail |
| تجهيز الإهلاك وطباعة/تصدير المعاينة المحلية | Depreciation.Prepare |
| حفظ/ترحيل الإهلاك | Depreciation.Prepare وDepreciation.Save؛ يبقى canSave/token وحراس الخادم |
| تقرير تفاصيل الإهلاك | Asset.GetDepreciationDetailReport وAsset.Lookup وAssetType.Lookup وفق bootstrap الحالي؛ لا تغيير فلتر/حساب |
| تقرير ملخص الإهلاك | DepreciationSummary.Get وAsset.Lookup وAssetType.Lookup؛ adapter خلفي لنفس حاسبة الأصول وعقد التقرير المجمد |

حُسم انقطاع تقرير ملخص الإهلاك بإضافة adapter خلفي للمسار الذي تستهلكه الشاشة، يعيد العقد المجمد ويستخدم الحاسبة الموجودة دون تغيير الحساب. اعتمد مفتاحه المثبت في route والقراءة. شملت الدفعة إلغاء القراءات القديمة بسحب الصلاحية أو تغير actor/branch context، وحفظ CSV draft ونتيجة الإرسال، وتصحيح أسماء landing للتقارير والاستيراد. أحدث مجموعة واجهة **٧٧/٧٧** مع نجاح بناء التطوير بعد إصلاحات effects وإعادة المنح ومسودة محرر الأصل؛ جولة الخلفية النهائية **١٧٠/١٧٠** تشمل إصلاحات المراجعة المسجلة في المصالحة. قبول المظهر والترحيل الفعلي منفصل. لا API صلاحيات أو cache أو مالك أزرار جديد، ولا CRUD inheritance. تنفيذ دفعة لا يعني اكتمال بقية الشاشات.

### جرد البيع والأسطول وحالة التنفيذ — ٧ نوفمبر

المفاتيح التالية مثبتة من route/component/service/controller الفعلي. اكتمل تبني
الأسطول وتجهيز البيع مصدرّيًا وفق FLEET_ACCESS_ADOPTION_CONTRACT_FREEZE.md
ومصالحته: نجحت١٥١/١٥١حالة بعد تدقيق التأكيد والتنظيف وإعادة المنح؛ نجح
البناء النهائي بعد الاستكمال، والقبول المرئي معلق. عُدلت عدادات
الجرد إلى١٣operation-confirmed و١٤٣resource-only و١٠٢unknown و٢context-only
و٢alias من٢٦٢؛ هذا لا يعني اكتمال بقية الشاشات. **عقود البيع والإيصال المدمج
ما زالا غير متبنيين**، ولا يُضافان إلى سجل المسارات لمجرد الجرد. الشكل الحالي
للأسطول قائمة مع محرر موجه (UI02)، وتجهيز البيع حوار إجراء (UI09)؛ لا تغيير
شكل أو حساب هنا. مصدر القائمة `pages/routing.ts` ثم `Sales/Fleet/fleet.routes.ts`؛
مسار Fleet بحرفه المسجل، وتفاصيله `view/edit/create` مع alias details، وتجهيز
البيع overlay من `prepareEquipmentId`.

دليل الجرد: FleetService،CarModelService.getGetMakeAndModels،sale-preparation.service،list/details/preparation components،Receipt embedded،DocumentUploadTracker/FileUploadService،PermissionEndpointResolver وendpoint inventory. قُرئ مرجع Speed Sales/Fleet من لقطة٢٨أكتوبر، وكود C0784 بصورة منفصلة؛ يصف الوظائف لا مفاتيح Sigma. لا غموض مرجعي يحل سياسة التحصيل بين الفروع؛ سؤال المالك الجاري يخص تلك الجزئية المالية فقط، ولا يمنع التنفيذ المستقل لتبني بقية أحداث الشاشات بعد تجميد متطلباتها.

استكمال جرد إيصال عقد البيع المدمج من المصدر بتاريخ٧نوفمبر: `Receipt.Create`
و`Receipt.SalesAgreementContext` لا يكفيان لوصف bootstrap الحالي. هذا المسار
ينشئ سندًا فقط؛ لا Update/Delete/Approval/Journal/Log فيه، لكنه يطلب حاليًا
`Receipt.Parties`، `Branch.Lookup`، `PaymentMethod.Lookup` و`PaymentMethod.View`
عند اختيار طريقة، و`Bank.Lookup`، و`Currency.Lookup` و`Partner.GetCurrency`
و`Currency.PreviewConversion` من DocumentCurrency. كما يطلب حاليًا
`RentalAgreement.Lookup` و`Account.GetPostingSelect` رغم تثبيت سياق العميل،
و`Receipt.Receivables` رغم حجب allocation tab في fromSalesAgreement، وsettings/
financial policy إلزاميين للحفظ في مالك الإيصال نفسه. لا يُحوَّل ذلك كله
تلقائيًا إلى prerequisites؛ يُجمَّد تخطي القراءات غير المستخدمة أو التبعية
الفعلية لكل قراءة قبل تنفيذ تبني SalesAgreement/Receipt. لا يُغيّر تصميم
العملة أو التحصيل بين الفروع بهذا الجرد. تبقى المرفقات Media وMockData
الاختيارية على عقديهما المشتركين. الدليل: Receipt details configureParties/
configureAllocationLookup/loadDropdown، DocumentCurrency، وخدمات endpoints
المباشرة؛ لا شمول للإيصال standalone أو SalesQuotation standalone.

متابعة طلب المالك في المحادثة نفسها: فُعّل هدف «إنهاء وتجربة تصور معماري
كامل للصلاحيات». أصبح التنفيذ قائمًا لشريحة الجلسة والإظهار في
[العقد المجمد](CURRENT_ACCESS_IMPLEMENTATION_CONTRACT_FREEZE.md)، وأدلته في
[تقرير القبول الجاري](CURRENT_ACCESS_RUNTIME_ACCEPTANCE.md). تصميم النطاق
والحقول الحساسة والتفويض الإداري المتقدم يظل اقتراحًا مستقلًا حتى تتحدد
قواعد المجال؛ لا تعني عبارات المقترح هنا أنه أصبح مطبقًا في كل شاشة.

## ١. النتيجة المستهدفة

### متابعة تنفيذ عقود البيع — ٧ نوفمبر

تجري الدفعة تحت عقود مستقلة في مجلدAuthorization: شريحة action-dialog
للفوترة/التسليم، شريحة قراءات الإيصال المدمج غير المستخدمة، وشريحة وصول
DocumentCurrency الاختيارية. المصالحة الجارية:
SALES_AGREEMENT_ACCESS_ADOPTION_FINAL_RECONCILIATION.md. لا فتحroute أو
زيادةoperation-confirmed حتى تتبنى القائمة والمحرر والإيصال كل أحداثها.

نجحت٣٠حالة أولية لهذه الشرائح. ما زالت مراجعة نوافذ التزامن للمنتقي المشترك
جارية، ولا يُعتمد النجاح الأولي نهايةً للتبني. أُصلح تسربid مسارالعقد إلى
هويةإيصالembedded جديد بعدRED صريح؛ ينتظر GREEN النهائي مع باقي الشريحة.

بعد المنتقي تبقى قراءات الإيصال الفعلية: Receipt.SalesAgreementContext،
Branch.Lookup،PaymentMethod.Lookup/View،السياسة والاختيارات ومعاينة العملة.
Partner.GetCurrency قابل للتخطي تحت source lock المعتمد؛ لا يُستبدل
ConversionPreview أوsnapshot. Bank.Lookup مطلوبة عندBankTransfer فقط بحسب
source الحالي؛ قبل تبنيها يجب فصل preload العام من شرط الحفظ الفعلي، دون
إخفاء طرق دفع لا يحمل lookupDTO نوعها. غياب هذه المنحة يمنع إكمال طريقة
bank transfer ويتيح طريقة أخرى مصرحًا بها؛ لا يفترض منحة بنك منReceipt.Create.
SettingsCommonModel.GetMySetting لتحسين amount-in-words مرشحةfallback اختياري
منquote المحفوظة، لا شرطًا إداريًا لفتح الإيصال؛ تُجمّد بعد إثبات source.
لا قرار مالي جديد أو تخصيص آلي عبر الفروع من هذه الملاحظات.

جرد المحرر المحدود من العامل بتاريخ ٧ نوفمبر يثبت مجموعتي Create وView+Update
مع Customer.Lookup وBank.Lookup وSalesAgreement.GetAvailableUnits؛ قراءة
SalesQuotation.View تابعة لوجودsourceQuotationId فقط. العرض والطباعة يحتاجان
View دون اختيارات التحرير. تتبع عمليات الحذف والإغلاق والإلغاء مفاتيحها
الفعلية مع View وحراس الحالة؛ الفوترة والتسليم تحت عقد الحوار الجديد.
المرفقات تتبنى مالك Media الحالي (Upload+Delete لرفع جديد وDelete للتنظيف).

النقاط المطلوبة قبل فتح مسار المحرر: denied$ لكل finite read وwatch؛
context fence للتفاصيل والعرض والسياسة والضريبة؛ المحافظة علىdraft عند
سحب الصلاحية فقط، واستعادة bootstrap المفقود عند إعادة المنح؛ حراسة نتيجة
كل إنشاء أو تعديل أو إجراء أو تنظيف أو حوار ابن ضد سياق وسجل قديمين؛
إلغاء قرارات التأكيد مع الحفاظ على كتابة أُرسلت؛ ومحاولة التنظيف لا تعيد
الحفظ ولا تُحجب خلف مسار غير متاح حين تعود منحة Media وحدها. لا تغيير
مالي من هذا الجرد؛ المصدر الحالي وحالاته يبقيان سلطة المجال حتى العقد الكامل.

### متابعة Receipt المستقل — ٧ نوفمبر

بدأ تنفيذ القائمة المستقلة تحت
`RECEIPT_ACCESS_ADOPTION_CONTRACT_FREEZE.md` و
`RECEIPT_ACCESS_ADOPTION_FINAL_RECONCILIATION.md`. أضيفت سياسات المسار
والفعل لكل قراءة وإجراء في القائمة، وبدأت حراسة محرر Receipt وقراءات اختياراته
والاعتماد والتخصيص والمرفقات. التغطية الوظيفية المجمعة الحالية ٢٢/٢٢؛ ما زال
قبول أحداث المحرر المرئية والكتابية الكاملة شريحة مستقلة قبل إعلان Receipt
مكتملًا.

بدأ الاستكمال المصدرّي بتاريخ٧نوفمبر تحت ملحق العقد نفسه: تُحفظ مفاتيح
View/Create/Update الأساسية للمسارات، وتحرس القراءات التابعة وجاهزية الحفظ
حسب النوع/المصدر. تشمل الدفعة القائمة والمحرر المستقل مع حفظ المستهلك
المدمج؛ القراءة في View من DTO/snapshot دون edit lookups، وsame-context
regrant يحفظ draft بينما ينهي تبديل السياق جلسة المحرر. المراجعة الجارية
تعالج إلغاء delete/approval المرسلة وتجاوز dirty exit عند denial وتبني
DocumentApprovalCycle الحالي. نتائج٢٢/٢٢ والبناء أعلاه تخص الدفعة السابقة
فقط؛ لا تشغيل build/tests/browser/DB في الاستكمال الحالي.

### متابعة Payment — ٧ نوفمبر

اكتملت شريحة المدفوعات تحت
`PAYMENT_ACCESS_ADOPTION_CONTRACT_FREEZE.md` و
`PAYMENT_ACCESS_ADOPTION_FINAL_RECONCILIATION.md`. القائمة والمحرر المالي

المرسلة مستقلة. التحقق التشغيلي والبناء والاختبارات وقبول الفروع عند المالك؛
لا تُعد هذه الدفعة إغلاقًا للجرد العام.

إضافة التدقيق المصدرّي: تطابقت متطلبات الإنشاء والتعديل الكاملة بين الزر
والمسار والمحرر، بما فيها سياسة الأرقام المالية؛ فلاتر القائمة اختيارية.
أُصلحت استعادة pending edit detail وحجب القائمة والـportals وتصفير سياق العمل.
تبنت المدفوعات مدخلَي قراءة/قرار مالك الاعتماد المشترك وحجب السياق، مع
استعادة revision/regrant وحفظ reason draft وعدم قطع sent write. لا نتائج
اختبارات أو بناء منفذة لهذه الإضافة. طلب قائمة Payment ما زال غير مقسم
خلفيًا ويتبعه تقسيم محلي؛ سُجل كمتابعة أداء دون تغيير العقد في دفعة المنح.

### متابعة CustomerDeposit — ٧ نوفمبر

اكتملت شريحة ودائع العملاء تحت عقدها المجمد ومصالحتها المصدرية. يعتمد فتح
المسار على `CustomerDeposit.View + CustomerDeposit.SearchDeposits`، وتُفصل
قراءات `Customer.Lookup` و`CustomerDeposit.GetTypes`، بينما التمديد والتحويل
يتطلبان مفاتيح السياق والعملية الفعلية. الاستخدام والرد والتخصيصات الخلفية
ما زالت بلا مستهلك واجهة في Sigma الحالية، لذلك بقيت خارج هذه الدفعة مع تسجيلها
كفجوة واضحة.

إضافة التدقيق المصدرّي: صنفت SearchDeposits/GetTypes/GetActionContext/
GetTransferAgreements كقراءات WholeDocument في مالك BranchOperationRules،
مع بقاء ExtendDeposit/TransferDeposit تحت التسجيل. أضيفت تغطية مصدرية لعمر
القراءة/المسودة/التحويل والكتابة المرسلة؛ التنفيذ والاختبارات غير مشغلة.
لا schema أو migration أو تغيير لحساب مالي في الدفعة.

يمر المستخدم من تسجيل الدخول إلى واجهة تخصه: القوائم والشاشات والأزرار
والتقارير والأقسام الحساسة تتبع قرار صلاحيات مركزيًا. يحمي الخادم نفس
العملية والبيانات حتى عند استدعاء رابط أو API مباشرة. لا يتطلب تغيير دور
تشغيلي أو منحة مباشرة إعادة الدخول كي يسري منع الخادم.

صفة المدير تعني مدير الشركة الموثق من Security والمرتبط بمستخدم ERP نشط
في الشركة نفسها. إنشاء دور ERP اسمه Admin أو تفعيل IsDefault لا يرقّي صاحبه
إلى مدير. صلاحية المدير لا تتخطى عزل الشركات أو قواعد الترحيل والإقفال
والموافقات أو حالة السجل أو عملية غير مدعومة أصلًا.

هذه طبقة تكميلية فوق التنفيذ الحالي، وليست إعادة إنشاء قواعد الأدوار أو
تخزين كلمات المرور في ERP. يبقى مدير المنصة منفصلًا عن مدير شركة العميل.

## ٢. ما هو موجود وما هو ناقص

| الجانب | الدليل المصدرّي الحالي | قرار التطور |
|---|---|---|
| إثبات الدخول | Security يصدر هوية واشتراكًا وأدوار هوية وerp_user_id عند الربط | Keep؛ لا نسخ آلاف الصلاحيات إلى JWT |
| ربط الحساب | IdentityUserId/IdentityRegistrationId وErpUserId مثبتة في دورة التسجيل | Keep؛ الحساب القديم غير المرتبط حالة إعداد غير مكتمل، وليس وصولًا عامًا |
| صلاحيات الأعمال | UserRoleAssignment وRolePermission وUserPermissionGrant | Keep؛ الاتحاد الحالي للأدوار النشطة والمنح المباشرة |
| إنفاذ الطلبات | PermissionAuthorizationFilter مع PermissionEndpointResolver | Extend؛ توحيد حساب المنح مع مصدر وصول الجلسة، وحفظ قواعد المجال |
| الكتالوج | ApiPermissionCatalog يستهلك resolver نفسه؛ آخر قبول: ٢٦٧٨ مفتاحًا قابلة للإسناد | Keep؛ أسماء العمليات الفعلية مرجع العقد، وليس اسم زر مترجم |
| إدارة المنح | AuthorizationController تحت TenantAdmin | Keep؛ لا إتاحة workspace الإداري لمستخدم عادي كي يرسم قائمته |
| حراسة Angular | AuthGuard يتحقق من وجود جلسة فقط | Extend؛ حارس وصول مستقل ومصدر صلاحيات جلسة |
| القوائم والاختصارات | MenuCatalogService وSidebarMenuComponent والاختصارات تستهلك كتالوجًا عامًا | Extend؛ إسقاط مرئي موحد من السياسة نفسها لكل نقاط التنقل |
| أفعال الصفوف | ActionButtonComponent يحترم ActionList.visible/disabled فقط | Extend؛ شرط الصلاحية بالإضافة إلى شرط حالة السجل |
| الأزرار المشتركة | ButtonsComponent وPrimaryActionButtonComponent لا تستهلك سياسة وصول | Extend؛ ربط اختياري صريح في العقد، ثم تبنٍّ كامل للأفعال المحمية |
| صلاحيات الحقول ونطاق الفروع | لا يثبت العقد الحالي نموذجًا مطبقًا لهما | شريحتان لاحقتان بعقد مستقل، لا ادعاء وجودهما |

فحص حساب الصورة الذي قدمه المالك قراءة فقط أثبت حساب Identity واحدًا
للاشتراك١٠٠٧، مع ErpUserId=null وغياب IdentityRegistrationId، ودون ملف ERP
مرتبط أو مرشح مطابق داخل الاشتراك. يسمح الدخول الحالي بإصدار التوكن له،
ثم يرفض مرشح ERP الطلب قبل تقييم المنح. هذا عائق ربط مستقل عن نقص صلاحية
لوحة المتابعة، ولا يُحل بجعل دور User مديرًا أو بالربط التلقائي عبر البريد.

## ٣. نموذج المنح المقترح

القرار الحالي المعتمد للأعمال:

`الصلاحيات الفعلية = اتحاد صلاحيات الأدوار النشطة + المنح المباشرة للمستخدم`

المستخدم العادي يبدأ بلا منح أعمال. قد ينتمي لأكثر من دور مثل المحاسب
ومسؤول التحصيل. الاسم وصف إداري؛ المفاتيح هي ما يحكم التنفيذ والإظهار.
تعطيل الدور يبقي إسناداته ويوقف مساهمته في الاتحاد، وتعطيل المستخدم يوقف
وصوله ولو بقي التوكن. لا Deny أو توريث أدوار في الإصدار الأول؛ إضافة منع
يتغلب على المنح لاحقًا تتطلب مصفوفة تعارض واختبارات منفصلة.

لا يوحي منح Create بمنح View أوUpdate أوDelete. كل واجهة تجمع متطلبات
عمليتها الحقيقية: محرر التعديل الذي يقرأ سجلًا ثم يحفظه يحتاج صلاحية قراءة
السجل وصلاحية تعديله؛ lookup له مفتاحه إذا كان بيانات أعمال. تعرض الإدارة
المتطلبات التابعة المقترحة قبل الحفظ، دون إضافة صلاحيات ضمنية.

تبقى إدارة هوية المستخدمين والأدوار والمنح حاليًا للمدير، وفق سياسة
TenantAdmin. تفويض مدير صلاحيات مساعد توصية اختيارية لاحقة بعقد يمنع
ترقية الذات وتعديل المالك أو منح وصول أعلى من نطاق المفوّض؛ لا يُفعّل من
مجرد تحديد مفتاح في دور عادي.

## ٤. مسؤولية كل مشروع

| المشروع | المسؤولية |
|---|---|
| خدمة Security | هوية الدخول وكلمة المرور والجلسة وصفة مدير الشركة الموقعة وروابط ERP؛ لا تفاصيل أزرار كل شاشة |
| واجهة ServerAPI وطبقة Business | التحقق من مستخدم ERP والاشتراك والنشاط، حساب المنح، قراءة وصول الجلسة، حراسة العمليات والبيانات والتصدير والملفات والأحداث |
| واجهة Angular | تحميل snapshot الجلسة، فلترة القوائم، حراسة المسارات، إظهار الأفعال والأقسام، ورسائل الرفض وعدم اكتمال الربط |
| منصة SubscriptionAPI | دورة الشركة والاشتراك وخطة المنتج؛ لاحقًا مصدر أهلية الميزة عند إقرار عقدها، وليست مخزن أدوار ERP |
| بوابة CustomerMVC | تسجيل الشركة ومديرها ومتابعة التفعيل؛ لا نسخة ثانية من محرر صلاحيات أعمال ERP |

قواعد Security وERP لا تدمجان. قاعدة الاشتراكات المحلية الحالية لا تغير
ملكية الصلاحيات. أهلية الخطة شيء مستقل عن إذن المستخدم؛ تفعيل تقاطع الخطة
مع الصلاحية يحتاج عقد أهلية فعليًا، وليس افتراضًا أن الفوترة الحالية مكتملة.

## ٥. مصدر وصول الجلسة — عقد مقترح، غير موجود حاليًا

يوصى بواجهة قراءة ذاتية واحدة، مثل:

`GET /Authorization/me`

يوضع مسارها خارج سياسة المتحكم الإداري العامة؛ يحتاج دخولًا صحيحًا ثم
يتحقق من روابط الهوية وERP والنشاط. لا يقبل userId أوsubscriptionId من
الواجهة. لا يعيد workspace أو أدوار مستخدم آخر ولا يحتاج صلاحية من قائمة
الأعمال كي يستطيع المستخدم معرفة ما أُسند إليه.

اللقطة المقترحة عند النجاح تشمل هوية المستخدم والاشتراك وERP user، وعلم
isTenantAdmin محسوبًا بالخادم، وpermissionKeys الفعلية وrevision. تنفذ خدمة
قراءة مشتركة نفس قواعد المنح المستخدمة في المرشح ومعاينة الإدارة؛ لا نسخة
ثانية من SQL ذات فروق خفية. تُصفّى المفاتيح بالكتالوج القابل للإسناد.

النتيجة غير المكتملة تعيد سببًا typed واضحًا: عدم ربط ERP، حساب غير نشط،
أو رابط غير مطابق. الواجهة تعرض رسالة واحدة قابلة للفهم وتوقف تحميل
الأعمال؛ لا تستبدل الرفض بقائمة فارغة توحي أن الحساب سليم. الـ401 ينهي
صلاحية الجلسة، والـ403 لصلاحية عملية لا يسجل خروج المستخدم كله.

يمكن حساب revision من حالة الوصول والمفاتيح المرتبة دون عمود جديد؛ لا
يفرض هذا التصميم migration. لا يُحفظ snapshot كإذن موثوق في localStorage.

## ٦. طبقة Angular المشتركة

| المكوّن المقترح | عقده ومسؤوليته |
|---|---|
| خدمة وصول الجلسة | لقطة واحدة مرتبطة بهوية الجلسة والاشتراك؛ ready/loading/error/not-linked؛ can(key) وcanAll/canAny |
| سجل سياسات التنقل | ربط صريح بين المسار الحقيقي وقراءة الشاشة وعمليات Create/Edit والإدارة؛ يعالج aliases والتقارير والإعدادات |
| حارس المسارات | ينتظر القراءة ثم يمنع فتح الرابط غير المسموح، بما فيه الروابط المكتوبة يدويًا ومسارات الأبناء |
| موجه الإظهار المشترك | فكرة AuthorizeView/Can مملوكة في shared؛ تنشئ المحتوى فقط عند السماح، مع بديل اختياري للرسالة |
| مالكو القوائم والأزرار الحاليون | يستهلكون الخدمة نفسها داخل ActionList/ButtonModel والمالكين المشتركين؛ لا wrappers تصميم موازية |
| إسقاط التنقل | نفس فلترة القائمة والبحث والمفضلة وآخر الزيارات والاختصارات؛ إخفاء المجموعة عندما لا يبقى طفل مسموح |

لا استدعاء HTTP لكل زر أو صف، ولا قراءة DOM لاستنتاج الصلاحية، ولا استنباط
المفتاح من نص الترجمة أو HTTP verb. يعمل الفحص محليًا على Set للمفاتيح بعد
قراءة الجلسة. تُربط الأفعال ذات أكثر من شرط صراحة بمعنى all أوany.
المسار أو الفعل غير المصنف يرفض للمستخدم العادي ويظهر في تقرير نقص التبني؛
لا يصبح مسموحًا بسبب غياب metadata. المدير يبقى خاضعًا لدعم العملية وحالة السجل.

يشمل عقد تبني كل شاشة: رابط القائمة، الحارس، طلبات bootstrap، أفعال
الصفوف، أدوات القائمة، محرر Create/Edit/View، الأفعال المالية، الطباعة
والتصدير والروابط المرتبطة. إعداد الموجّه المشترك وحده ليس اكتمالًا للتبني.

## ٧. سياسة الإظهار والحالات

| الحالة | سلوك الواجهة | سلوك الخادم |
|---|---|---|
| مدير شركة صالح ومربوط | كل الشاشات المتاحة ووظائفها مع حراس حالتها | تجاوز منح الأدوار العادية فقط؛ حراس المجال والعزل مستمرة |
| غياب صلاحية العرض | إخفاء رابط الشاشة؛ منع الرابط المباشر؛ لا طلب بياناتها | 403 للطلب المباشر |
| العرض مسموح والإنشاء ممنوع | عرض البيانات دون زر أو مسار إنشاء | رفض Create مستقلًا |
| العرض مسموح والتعديل ممنوع | عرض للقراءة فقط دون حفظ التعديل | رفض Update مستقلًا |
| الصلاحية موجودة والحالة تمنع الإجراء | زر معطل مع سبب مفهوم، أو إخفاء حسب عقد الشاشة | رفض الانتقال المخالف ولو كان مديرًا |
| لا أي وظيفة مسندة | صفحة «لم تُسند لك وظائف بعد» مع الإرشاد للتواصل مع المدير | لا استدعاءات أعمال تلقائية |
| الحساب غير مربوط بـERP | رسالة إعداد حساب غير مكتمل؛ لا dashboard أو أخطاء فرع وترجمة متراكمة | سبب رفض محدد؛ لا تخمين الربط |
| تعذر تحميل سياسة الوصول | StateMessage مع Retry؛ لا عرض محتوى الأعمال قبل الجاهزية | يظل enforcement مستقلًا |
| سحب صلاحية أثناء الجلسة | تحديث اللقطة وإزالة الوظيفة والتعامل مع403 دون تكرار محاولات | يسري المنع في الطلب التالي |

مثال مفاتيح فعلية حالية:

| المفتاح | ما يتيحه في تجربة الواجهة |
|---|---|
| Branch.View | قائمة الفروع وقراءة تفاصيلها |
| Branch.Create | عملية إنشاء الفرع؛ لا تعني Update/Delete |
| Branch.Update | حفظ تعديله؛ محرر القراءة يحتاج View أيضًا |
| Branch.Delete | حذف وفق حارس حالة الفرع |
| Dashboard.Snapshot | قراءة لوحة المتابعة؛ ليست حقًا تلقائيًا لكل User |

لصفحة البداية أولوية مسارات مسموحة معلنة. إن لم تُمنح لوحة المتابعة، لا
تفتحها الواجهة ثم تعرض فشلها؛ تنتقل لوظيفة مسموحة أو صفحة لا وظائف. الروابط
الراجعة بعد الدخول لا تتخطى الحارس، وتحافظ على query/fragment المسموحين.

## ٨. تحميل الهيكل والترجمات والفرع

المقترح تقسيم طلبات النظام الأساسية عن منح الأعمال، بعقد صريح جديد في
الحارس: قراءة سياسة الجلسة، واختيارات لغة التطبيق وقاموس نصوصه، وسياق الفرع
الذاتي للمستخدم المربوط. لا يتطلب استخدام التطبيق منح إدارة شاشة Languages.
لا يسمح هذا الاستثناء بقراءة ملفات ترجمة إدارية أو تغييرها أو عرض بيانات
مستأجر آخر. CurrentBranch مستثنى سياقيًا حاليًا؛ Language.Options و
Localization.Runtime ما زالا مفاتيح أعمال في القائمة الحالية ويحتاج نقلهما
إلى الاستثناء مراجعة وعقدًا؛ هذا اقتراح غير منفذ.

لا تعتبر MockData.Settings حقًا أساسيًا تلقائيًا؛ يُراجع استهلاكه كميزة
تجريبية، ويوقف طلبه/إظهاره لمن لا يملك عقد استعماله. لا تفتح كل Lookup
تجاري تحت اسم bootstrap. اختيار الفرع الحالي تفضيل؛ لا يثبت أن نطاق أمن
بيانات الفروع مطبق. تبقى صفحة dashboard واتصالها الحي مشروطين بوصولها.

الترتيب المقترح: إثبات الجلسة → قراءة وصولها → تحديد حالة الربط → تهيئة
الهيكل الأساسية → اختيار المسار المسموح → قراءة بياناته. مالك التحميل واحد
وفق UI22، وdialog بمالكه المحلي؛ خطأ403 لا يظهر كتعذر شبكة يستمر Retry عليه.

## ٩. الوظائف والخصائص والبيانات الحساسة

الوظيفة قد تكون شاشة، زرًا، تبويبًا، قسمًا، عمودًا، تقريرًا أو تنزيل ملف.
يستخدم العرض نفس طبقة القرار؛ لكن إخفاء حقل حساس لا يكفي إذا بقيت قيمته في
JSON أو ملف التصدير أو حدث SignalR.

تُنفذ صلاحيات الحقول لاحقًا بعقد صريح لكل مجال: هل يجوز مشاهدة التكلفة أو
الراتب أو تعديل الخصم مثلًا؟ هذه أمثلة مقترحة وليست مفاتيح موجودة. يحدد
العقد ما يحذف من DTO وما يرفض عند الكتابة، وأثر ذلك في الإجمالي والبحث
والطباعة والتصدير. لا ينشأ محرك حقول عام أو استبدال القيم بأصفار تبدو مالية
صحيحة. يشمل المنع الخادم وصلاحية السجل والحقول في طلبات التعديل الجزئي.

نطاق البيانات شريحة مستقلة: الشركة حد إلزامي حاليًا؛ «فرعي فقط/فروع محددة/
كل الفروع/سجلاتي» تحتاج إثبات predicate في القراءات والكتابات والتقارير
والروابط المباشرة، وليس فلتر شاشة. لا يُسوَّق BranchAccess أو الاختيار
الحالي كحماية منفذة دون هذه المراجعة.

التصدير والطباعة والمرفقات والمهام الخلفية والأحداث الحية حدود وصول فعلية
وتحتاج تبني السياسة في مالكها. إعادة403 من Controller لا تثبت حماية Hub
أو رابط تنزيل منفصل؛ يُجردان ويختبران ضمن الشاشة المستهلكة.

## ١٠. إدارة الأدوار والمستخدمين

تستمر شاشة الأدوار الحالية وشجرتها كمالك. يضاف إليها تنظيم بحسب الوحدة
والشاشة والعملية الفعلية، وتسميات مفهومة وبحث وإظهار الممنوح فقط، وبيان
العمليات غير المدعومة والمتطلبات التابعة. لا مصفوفة بأعمدة وهمية لعمليات
لا توجد في كتالوج الخادم، ولا بيانات مستخدمين/وصف دور غير متاحة في DTO.

تظل شاشة المستخدم تجمع ملف ERP وحالة ربط الهوية وإسنادات الأدوار والمنح
المباشرة ومعاينة الاتحاد ومصدر كل منحة. تعرض «من دور كذا» أو «منحة مباشرة»،
وتبين أن دورًا غير نشط لا يساهم. يسبق الحفظ ملخص الإضافة والسحب، ويُحتفظ
بـExpectedVersion وتعارض409 والتأكيد قبل تجاهل المسودة والحماية النظامية.

يفضل إدارة المنح من الأدوار، والمنحة المباشرة استثناء واضح. إسناد أي دور
أو منحة يتحقق من المستأجر والكيان والمفتاح والدعم. لا يملك المستخدم تعديل
إسناده الخاص لمجرد وصوله إلى شاشة تشغيلية. سجل تغييرات الوصول يسجل الفاعل
والمستهدف والوقت والقيم السابقة واللاحقة والسبب عندما يقتضيه العقد؛ يُراجع
مالك التدقيق الموجود قبل اقتراح جدول موازٍ. لا كلمات مرور أو tokens فيه.

## ١١. عمر اللقطة والإبطال

تصفّر خدمة الجلسة حالتها عند logout أو تغير المستخدم/الاشتراك. يمنع معرف
جيل الجلسة استجابة قديمة من فتح وظائف مستخدم تالٍ. تُشارك قراءة bootstrap
واحدة بين المستهلكين ولا تحفظ قراءة فاشلة كمعلومة ناجحة.

يستمر الخادم بفحص المنح الحالية. الواجهة تحدث snapshot بعد حفظ مؤثر في
الجلسة الحالية، وعند استعادة تركيز التطبيق، ومرة واحدة عند403، وبفحص صلاحية
محدود كل٦٠ ثانية أثناء نشاط التطبيق. يمكن لاحقًا إضافة إشعار policy-changed
مخصص للمستخدم/المستأجر لإبطالها؛ لا يرسل جميع منح المستخدمين لكل العملاء.
تحديث الواجهة ليس ضمانًا فوريًا في غياب ذلك الإشعار؛ المنع الخلفي هو الفوري.

إذا سُحبت صلاحية أثناء محرر، يمنع حفظ جديد وتعرض الحالة بوضوح. القراءات
القديمة تلغى من مالكها؛ الكتابات المرسلة تحافظ على عمرها ونتيجتها المستقلة
ولا يعاد إرسالها تلقائيًا. لا تحويل كل403 إلى logout أو حلقات refresh.
تغيير صفة المدير في Security له سياسة جلسة مستقلة؛ لا يُدعى أن تعديل دور
ERP يسحب claim إداريًا موجودًا في JWT.

## ١٣. مراحل التنفيذ المقترحة ومقاييس الإغلاق

| المرحلة | المخرجات وحدودها | القبول اللازم |
|---|---|---|
| الأولى: سياسة الجلسة والهيكل | تجميد DTO الذاتية، إعادة استخدام قارئ المنح، حالات الربط والنشاط، bootstrap اللغات/الفرع، صفحة البداية/الرفض | مستخدم بلا منح لا يرى أعمالًا ولا يفشل الهيكل؛ غير المربوط يرى رسالة واحدة؛ المدير يرى المتاح كله |
| الثانية: تبني التنقل والأفعال | حارس route/children، سجل صريح للخرائط، القوائم والبحث والاختصارات، الموجه وأصحاب الأزرار والأفعال والمحررات | جدول تغطية لكل مسار وعملية؛ كل منها مربوط بمفتاح/سياسة أو مستبعد بسبب موثق، ولا سماح ضمني للمجهول |
| الثالثة: دورة الإدارة والتحديث | متطلبات العمليات وسبب المنحة والتدقيق والإبطال، دليل الإدارة وإرشاد حالات الفشل | منح/سحب/تعطيل/تفعيل وتعارض ونقل جلسة بلا تسرب لقطة؛ توضيح حدود تأخر العرض |
| الرابعة: النطاق والحقول الحساسة | عقود الفروع والسجلات والحقول والتصدير والأحداث لكل مجال | منع تسريب GET/JSON/Export/Hub ومنع الكتابة والـID المباشر خارج النطاق |

يطبق الاختبار أولًا على مدير ومستخدمين عاديين في شركتين، ثم يتوسع بتغطية
معلنة. ليس مرور مثال Branch إذنًا بادعاء اكتمال كل الشاشات. لا تُطبق
قيود حقول/فروع/تفويض إداري جديدة بالحدس. لا migration أو snapshot في طلب
التصور؛ أسماء هجرات محتملة تقدم بعد إثبات حاجة مخطط بعقد نطاق مستقل.

اختبارات القبول الرئيسية: المدير؛ بلا منح؛ عرض فقط؛ إنشاء دون حذف؛ مسار
مباشر؛ ActionList وأزرار ثابتة؛ منحة مباشرة مع دور؛ سحب بنفس التوكن؛ دور
ومستخدم غير نشطين؛ ربط مفقود أو خاطئ؛ مستأجر آخر؛ تغير الجلسة أثناء الطلب؛
فشل السياسة وRetry؛ أحدث نسخة409؛ dashboard غير ممنوحة؛ القاموس والفرع؛
بحث ومفضلة قديمان؛ تقارير/تحميلات/أحداث؛ العربية وRTL والثيمات والموبايل.

لا قراءة لكل زر أو صف ولا فحص صلاحيات منفصل لكل عنصر. تقاس قراءة اللقطة
واستعلامات المنح بحجم البيانات الحقيقي. فهارس tenant/user/role/permission
الحالية نقطة البدء؛ لا فهرس جديد قبل SQL plan وقياس الكلفة. لا توجد مقارنة
أداء قبل/بعد منفذة لهذه الطبقة لأنها ما زالت تصميمًا.

## ١٤. الأدلة والحدود وتسليم التنفيذ

قُرئت قواعد مساحة العمل ومهارة Sigma؛ UI26 يؤكد غياب مستهلك frontend
لصلاحيات الجلسة واشتراط عقد له قبل التنفيذ. روجعت ملفات المرشح/resolver،
ومتحكم Authorization وطبقة إعداد المنح، وAuthGuard وAuthService، ومسارات
التطبيق والقائمة والاختصارات، ومالكو الأزرار والأفعال وسياق الفرع ولوحة
المتابعة. قُرئ عقد الإنفاذ وتقارير القبول والمراجعة السابقة والمؤجلات.
لا فحص شامل لكل ملفات الحل؛ تبني العمليات المخصصة يحتاج جدول خريطة الشاشة.

مرجع Speed: دليل٢٧ أكتوبر، الجزء الخاص بالإدارة والصلاحيات؛ وشاشتا Roles
وUsers في لقطة٢٨ أكتوبر، مع كود C0032/C0033. يثبت الكود تصريح canCreate/
canEdit/canDelete واختيار الأدوار، ولا يثبت أمان API أو قواعد حقول سيجما.
هذا matched لوظائف الإدارة وmissing لربط إظهار Sigma؛ لا تُنسخ مفاتيح
Pages.Administration إلى كتالوج Sigma. قُرئ مدخل Odoo المثبت؛ لا يلزم
استنتاج عقد جلسة Angular أو حماية مالية منه.

تطبق عند التنفيذ كتل Master1/4/5/7 وUI2/7/22/26/28/29 وحدود backend
للإثبات والعزل والحساب. لا تُعدَّل الكتب أو المهارة بحلول مقترحة قبل إثبات
تنفيذ مشترك قابل لإعادة الاستخدام. يلزم تحديث UI26 وUI7 والمهارة ودليل
الإدارة وحزمها من مولدها عند تحقق تلك الإضافة، ضمن مرحلة مصالحة التنفيذ.

استُخدمت مهارات Superpowers للتشخيص والعصف والتخطيط، المتاحة فعليًا في
مسار المهارات المحلي، مع أولوية قواعد Sigma. اقتصر تعديل مرحلة التصور على
هذا التصور وفهرس المراجعات. فحص الحساب كان قراءة محدودة ضمن تفويض تشخيص
البيئة التجريبية السابق؛ لا تغيير بيانات. لا إنشاء endpoint أو guard أو
تعديل أمان أو بناء/اختبارات/متصفح أو هجرات أو commit/push/deploy في مرحلة
التصور. لم يُستخدم وكلاء أثناء صياغة التصميم؛ ثم فُصل عمل التنفيذ بين
الخلفية والواجهة والجرد بعد تجميد عقده، والجذر يملك التكامل.

القرار المعتمد من المالك هو سلوك المدير مقابل المستخدمين؛ ثم فُعّل هدف
الإنهاء والتجربة وجُمّد عقد API الذاتية والإظهار. الحالة التنفيذية الفعلية
وحدود التبني في تقرير القبول، بينما توسعات النطاق والحقول تبقى مقترحات
مسجلة هنا، وليست موجودة أو مفعّلة لمجرد توثيقها.
