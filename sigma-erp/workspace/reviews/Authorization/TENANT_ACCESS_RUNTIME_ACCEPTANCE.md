## الحالة الحالية المعتمدة — ٦ نوفمبر ٢٠٢٦

قال المالك بعد رفض إنشاء قاعدة الهوست: «انشئها Local». استُخدمت قاعدة
`SiGmaSubscriptionPlatform` على `(localdb)\MSSQLLocalDB`؛ جرى التحقق من
جداولها الـ٢٥ وحقل `TenantOnboarding.ErpUserId`. ملف الاتصال الفعلي:
`SigmaBackend/SiGma.SubscriptionAPI/appsettings.Local.json`، والمفتاح
`ConnectionStrings:SubscriptionConnStr`. الملف مستبعد من Git والنشر ولا تُعرض
أسراره هنا. تظل قاعدتا Security وERP على الهوست بإعداداتهما الحالية.

ظل `EnsureCreatedOnStartup=false` و`SeedOnStartup=false` في الإعداد الدائم.
شُغلت تهيئة البيانات المرجعية مرة واحدة بعلم تشغيل صريح، فتوفرت الخطة
العامة الفعلية رقم١؛ لا fallback لخطط وهمية في التسجيل، ولا إنشاء مخطط ضمني
عند كل إقلاع. لا migrations جديدة ولا تعديل snapshots.

## دليل مخطط الهوست — قراءة فقط

جرت القراءة باستخدام اتصال كل مشروع الحالي من إعداده؛ لم تُطبع سلاسل الاتصال
أو كلمات المرور. لا تغيير لقيمة اتصال ERP أو Security.

- قاعدة ERP المستضافة: توجد `User.IdentityUserId` و`User.IdentityRegistrationId` و`Role.IsSystem` وجداول UserRoleAssignment/UserPermissionGrant. هذا يثبت جزءًا من تطبيق مخطط ERP، ولا يثبت كل المخطط الجديد أو نجاح الكتابة.
- قاعدة Security المستضافة: جدول `TenantIdentity` غير موجود. حقلا `AspNetUsers.ErpUserId` و`AspNetUsers.IdentityRegistrationId` غير موجودين. سجل الهجرات يحتوي أربع هجرات فقط، أحدثها `20260212120024_AddRequiresPasswordChangeToApplicationUser`؛ لا أثر لهجرات التسجيل/الربط الجديدة.
- مشروع SubscriptionAPI: كلا الاتصالين في appsettings الأساسي وDevelopment محليان. لم يوجد ملف Local باتصال مستضاف وقت الفحص. لم يُفترض اسم قاعدة هوست أو يُنسخ اتصال ERP/Identity إلى هذا السياق.

أثناء التشغيل الأول قبل توجيه المالك باستخدام الهوست، نفذ SubscriptionAPI
بنفسه EnsureCreated على القاعدة المحلية `SiGmaSubscriptionPlatform` بسبب
العلم الموجود في إعداد Development؛ لم يكن أمر migration من الوكيل. أوقف
استخدامها عند توجيه المالك، ولم تُحذف أو تُنقل بياناتها. عُطل
`SubscriptionPlatform:EnsureCreatedOnStartup` في Development لمنع إنشاء
مخطط ضمني عند الإقلاع. لا seed أو tenant أو أدوار اختبار أُنشئت في تلك القاعدة.

## تفويض استكمال مخطط Security — ٦ نوفمبر ٢٠٢٦

قال المالك صراحة: «نفّذ تغييرات المخطط اللازمة» مع الحفاظ على البيانات.
أصبح مسموحًا استكمال مخطط Security المستضاف في هذه الشريحة؛ لا يوسع ذلك
التفويض إلى مخطط الاشتراكات على قاعدة مفترضة أو حذف قاعدة/جدول أو تعديل
snapshots أو تسجيل migration غير موجودة في EF history.

أُعد السكربت الإضافي `SECURITY_TENANT_REGISTRY_HOST_SCHEMA.sql` من النموذج
والـEF configuration الحاليين: عمودان nullable في AspNetUsers، وجدول
TenantIdentity وعلاقته وفهارسه الفريدة. يحميه XACT_ABORT ومعاملة rollback؛
لا أوامر لتغيير بيانات الحسابات أو كلمات المرور أو التاريخ.
أكد الفحص السابق للتنفيذ وجود ٤٤ حسابًا، ومفتاح Id من النوع nvarchar450،
وحقل SubscriptionId nullable، وغياب الجدول والعمودين المطلوبين.
تُسجل نتيجة التنفيذ وإعادة الدخول في الملحق التالي بعد حدوثهما.

قاعدة الاشتراكات منفصلة حسب سياقها الحالي. مفتاحها
`ConnectionStrings:SubscriptionConnStr` في appsettings.json/Development؛
يحمّل Program ملف appsettings.Local.json في التطوير بعدهما. لم يحدد المالك
حتى الآن اتصال الهوست المقصود لهذا السياق، بل سأل عن مكانه؛ أجيب عن المسار
دون عرض أسرار أو تحويله تلقائيًا إلى قاعدة ERP/Security.

## نتيجة استكمال مخطط Security — ٦ نوفمبر ٢٠٢٦

بعد المراجعة المستقلة للسكربت، نُفذ على قاعدة Security المستضافة الحالية
بنجاح داخل المعاملة. جرى فحص الأعمدة والجدول والـPK/unique indexes وfilters
بعد التنفيذ: تطابق النموذج المصدرّي. ظل عدد AspNetUsers قبل التنفيذ وبعده
٤٤، وبقي checksum للهوية والاسم والبريد وكلمة المرور المجزأة وsecurity stamp
والاشتراك وrefresh token كما هو. لا تحديث لحساب قائم ولا EF history مزيفة.

أعيد POST الفعلي للحساب التجريبي الذي قدمه المالك:
`/auth/consolelogin` بكود101007؛ النتيجة HTTP200 وisSuccess=true وتوكن
والاشتراك1007. لا سر أو توكن في هذا التقرير. بذلك أُغلق عائق جدول
TenantIdentity الذي سبب500 سابقًا. ما زال هذا الحساب القديم غير دليل على
قبول تسجيل شركة جديدة أو ربط ERP؛ تلك التجربة تحتاج قاعدة الاشتراكات.

## طلب قاعدة الاشتراكات المستضافة ونتيجته — ٦ نوفمبر ٢٠٢٦

طلب المالك صراحة: «ظبط الاتصال وانشئ قاعدة البيانات». استُخدم سيرفر الهوست
القائم من إعداد ERP، مع استهداف قاعدة مستقلة باسم SiGmaSubscriptionPlatform؛
لم تُستبدل قاعدة ERP أو Security ولم تُدمج الجداول في أي منهما.

أكد فحص صلاحيات اتصالي ERP وSecurity أن CREATE ANY DATABASE وdbcreator
غير ممنوحين، وأن الهدف غير موجود/غير متاح. المحاولة الفعلية المحدودة
`CREATE DATABASE [SiGmaSubscriptionPlatform]` رُفضت برقم SQL262:
`CREATE DATABASE permission denied in database 'master'.`
لم تُنشأ قاعدة مستضافة ولا يوحي إعداد الاتصال بنجاح ذلك.

أُعد ملف `SiGma.SubscriptionAPI/appsettings.Local.json` بمفتاح
ConnectionStrings:SubscriptionConnStr على نفس الهوست وInitialCatalog
الجديد، مع الحفاظ على IdentityProvisioning وPlatformIntegration. ظل الملف
git-ignored ولم تُطبع بيانات اعتماده. عُطل EnsureCreatedOnStartup وSeedOnStartup
محليًا أيضًا؛ لا fallback تلقائي إلى قاعدة محلية عند نقص قاعدة الهوست.

المتبقي خارج صلاحية الحساب الحالي: إنشاء قاعدة مستقلة من لوحة الاستضافة
وإسناد مستخدم لها، ثم ضبط اتصالها الفعلي إذا فرضت الاستضافة اسمًا/مستخدمًا
مختلفًا. لا حاجة لموافقة بناء أو تجربة جديدة؛ كلاهما مفوض. بعد توفير القاعدة
يمكن تجهيز مخططها المعتمد واستكمال اختبار الشركة والمالك والأدوار.
