الحالة الحالية وأدلة التشغيل في
[قبول الدورة](TENANT_ACCESS_RUNTIME_ACCEPTANCE.md). أقسام الفحص المصدري
والموانع والتسليم السابقة أدناه محفوظة كسجل مؤرخ؛ لا تعني أن إذن التشغيل
أو إنشاء القاعدة المحلية ما زال معلقًا. يتبقى قبول المالك للنشر والسباقات
وقياسات الأداء والتفاصيل المرئية التي لم تدخل التجربة، كما يفصل التقرير.

## قبول التشغيل الحالي — ٦ نوفمبر ٢٠٢٦

بتوجيه «انشئها Local» ثبتت قاعدة الاشتراكات المحلية، مع الإبقاء على
Security/ERP في الهوست. ثبت تسجيل شركتين نشطتين برمزَي دخول واشتراكين
مختلفين ومديرَين مرتبطين بلا تكرار، وإنشاء مستخدمين عاديين واستكمال فشل
كلمة المرور بنفس ملف ERP. نجح البناء للخلفية وAngular، وأحدث نتائج
HTTP هي٦٣/٦٣ ناجحة من٦٧ محاولة محفوظة؛ فشلان تاريخيان عولجا وأعيدا.

جرت تجربة الواجهة النهائية للدور إنشاءً ونسخًا وتجاهلًا وعرضًا وتعديل نشاط،
وحماية النظام ومعاينة منح المستخدم والعربية وRTL والداكن والموبايل، دون
أخطاء متصفح/طلبات فاشلة في المسارين المجربين. لا ادعاء تجربة كل endpoint
مالي أو قياس أداء شامل. الكتالوج الفعلي٣٣٤ موردًا و٢٦٧٨ مفتاحًا قابلة
للإسناد، والعمليات المخصصة٥٩١/٥٩١ موجودة. أُصلح استعلام الموافقات TPT
الذي كشفه الطلب المسموح؛ وعُدّل baseline الترجمة من مصدره مع حفظ overrides.

تفاصيل الأدلة والملفات والحدود في [تقرير القبول](TENANT_ACCESS_RUNTIME_ACCEPTANCE.md)،
و[HTTP](TENANT_ACCESS_HTTP_CHECKS_20261106.json)،
و[الربط والنصوص](TENANT_ACCESS_DATABASE_CHECKS_20261106.json)،
و[صور ونتائج الواجهة](acceptance-20261106).
تعليقات «معلق عند المالك/مصدر فقط» أدناه تخص التسليم السابق؛ لا يلزم
تكرار الهجرات أو إذن البناء الحالي. تبقى سباقات الربط وقياسات SQL والنشر
والجوانب الأخرى من سجل الاشتراكات خارج القبول المجرب.

## مسار التنفيذ ومسؤولية كل مشروع

| المشروع | المسؤولية ومصدر التنفيذ |
|---|---|
| بوابة العميل MVC | نموذج التسجيل المباشر ونتيجته ودليل الدورة؛ `TenantRegistrationController` و`Views/TenantRegistration` و`TenantRegistrationClient` |
| منصة الاشتراك | تجهيز الشركة والاشتراك، سجل `TenantOnboarding` وlease والتكرار وتسجيل نتائج الهوية وERP قبل التفعيل؛ `TenantRegistrationService` |
| خدمة الهوية | حساب الدخول وكلمة المرور المجزأة والتوكن والجلسة وclaim Admin للمالك وربط ERP؛ `TenantIdentityService` و`IdentityTokenService` |
| واجهة ERP | الملف التشغيلي للمستخدم، الدور النظامي وإسناده، الأدوار والمنح المباشرة والكتالوج وحارس التنفيذ؛ `InternalTenantUserController` و`UserService` و`AuthorizationConfigurationService` |
| واجهة Angular | إدارة مستخدمي ERP وأدوارهم ومنحهم؛ `Administration/Users` و`Administration/Roles` والمالك المشترك `PermissionTreeComponent` |

السلسلة المصدرية الحالية:

`CustomerMVC → SubscriptionAPI → Security provision → ERP owner provision → Identity/ERP link → activation`

هوية الدخول والملف التشغيلي سجلان مرتبطان بمعرفات صريحة؛ لا يكرر ERP حفظ
كلمة المرور. تظل الخدمتان مالكتين لقاعدتيهما الحاليتين؛ لا دمج لقواعد البيانات.
لا يتغير ربط كود الدخول القديم 101007 بالاشتراك 1007.

## قرارات العقد ومصالحتها

| القرار | المصدر/الدليل | النتيجة الحالية |
|---|---|---|
| التسجيل المباشر الآن والدعوة مؤجلة | توجيه المالك وعقد التسجيل المباشر | مصدر النموذج والخدمات ينفذ التسجيل بكلمة مرور وتأكيدها؛ لا إرسال دعوة وهمية |
| كود وSubscriptionId جديدان لكل شركة | `TenantIdentityService.RegisterAsync` | سجل موحد للتسجيل ورفض تعارض المعرفات؛ القبول التشغيلي معلق |
| اتصال داخلي | عملاء خدمة SubscriptionAPI/ERP وServiceKey filters | HTTPS، منع redirects، وإخفاء headers الحساسة من تسجيل العميل |
| التكرار والاستكمال | RegistrationId وfingerprint وlease والنتيجة المحفوظة | إعادة نفس التسجيل لا تعيد تعيين كلمة المرور؛ تحفظ نتائج كل حد مستقل |
| هوية ERP غير نشطة حتى الربط | InternalTenantUser وUserService | مزامنة Active/IsActive، ورفض تفعيل المستخدم غير المرتبط |
| حماية المالك | SystemRoleNames وIsSystem وحراس الخدمة | لا إنشاء اسم TenantAdmin عامًا، ولا تغيير إسناده أو حذف/تعطيل مالكه من الإدارة العادية |
| إدارة الشركة | claim Admin/SuperAdmin وسياسة TenantAdmin مع ERP actor | اسم دور ERP ليس مصدر claim؛ التحقق من الهوية والاشتراك والمعرف والنشاط يسبق عمليات المجال |
| منح العمل | اتحاد الأدوار النشطة والمنح المباشرة | لا Deny أو توريث أدوار أو نطاق فروع جديد أو إسناد تلقائي لـIsDefault |
| مفاتيح كل عملية | resolver مشترك وقائمة ثابتة | CRUD المجمد محفوظ؛ ٥٩١ عملية مخصصة بمفاتيح أسمائها الفعلية؛ Async النهائية فقط تزال |
| الموافقات | DocumentApprovalCatalog وقواعدها | مفاتيح المورد الفعلي للمستند؛ النوع غير المدعوم مرفوض؛ لا مفتاح عام إضافي مخفي |
| العمليات المجهولة | PermissionAuthorizationFilter | لا تنفذ للمستخدم العادي؛ إضافة endpoint لا تمنح وصولًا ضمنيًا |
| كتابة الأدوار القديمة | LegacyAuthorizationWriteBlockFilter | 410 لمسارات Role/Permission/RolePermission القديمة؛ الحفظ في مساحة Authorization ذات ExpectedVersion |
| توافق المعاينة والحارس | RoleKeysAsync وHasPermissionAsync | مطابقة Key وModule وAction لمنح الدور؛ لا منح من ربط قديم لا يظهر في المعاينة |

عملية ربط ERP بالمالك محمية الآن بمعاملة Serializable حول القراءة والقرار
وحفظ الرابطين؛ اختلاف التسجيل أو ERP user أو الاشتراك أو هوية Admin مرفوض.
يتطلب قبول سباق الربط اختبارًا من المالك؛ قراءة المصدر لا تثبت سلوك SQL تحت التزامن.

## واجهة الأدوار والبرومبت

المرجع المرفق من المالك دليل متطلبات مكتوب، وليس screenshot أو نتيجة تشغيل.
تظل شجرة الإعدادات الحالية هي الشكل المجمد؛ لا مصفوفة أفعال مفترضة، ولا بيانات
تجريبية في الشاشة الإنتاجية. توثق الفجوات في
`ROLES_PERMISSIONS_SCREEN_PROMPT_REVIEW.md`.

| المتطلب | مصالحة المصدر |
|---|---|
| قائمة الأدوار | بحث بالاسم ونوع النظام/المخصص ومسح الفلاتر وعدد النتائج؛ حالتا لا أدوار ولا نتائج منفصلتان |
| الإنشاء والعرض والتعديل | محرر مشترك؛ الحقول name/isDefault/isActive، والصلاحيات permissionKeys؛ version للكتابة المتفائلة |
| النسخ | مسودة محلية باسم نسخة، بلا إرسال حتى الحفظ، وبحالة dirty وتأكيد قبل تجاهلها |
| الدور المحمي | عرض ونسخ متاحان، ومنع التعديل/الحذف وإسناد النظام في الواجهة والخادم |
| البحث والمنح | شجرة بالموارد والأفعال الفعلية، بحث وفلتر الممنوحة وتحديد جزئي؛ bulk selection على النتائج الظاهرة عند الفلترة |
| عرض العمليات | ترجمة الأفعال المشتركة وأسماء العمليات المخصصة الفعلية المقروءة، والمفتاح الدقيق في title؛ دون translation key خام |
| مراجعة الحفظ | قوائم المفاتيح المضافة والمسحوبة وعددها، والحفاظ على المسودة عند الفشل |
| الوصول المرفوض | رسالة 403 واضحة من شاشة الأدوار؛ لا اختراع API لتقييم جلسة المستخدم |
| الجدول/الوصف/عداد المستخدمين/آخر تعديل | ليست في DTO الحالي؛ لا أرقام وهمية، وتظل شريحة توسعة موثقة تحتاج عقدًا ومصدرًا قبل التنفيذ |

القائمة workspace وليست grid paged؛ المقارنة الحالية:
`RoleAccess = id/name/isDefault/isSystem/isActive/version/permissionKeys`.
المعروض الاسم ونوع الدور وisDefault والصلاحيات؛ بقية الحقول لهوية السجل وحالة
الإجراء والتزامن. لا ListVM أو تصدير مالي أو حسابات مجال جديدة لهذه الشريحة.

## التحميل والكاش والسرعة

| المسار | المصدر/التصنيف | المالك والقبول |
|---|---|---|
| فتح الأدوار | `/Role` → Role_Routes → RolesComponent → GET Authorization/workspace | قراءة policy مباشرة، بلا reference cache؛ start داخل defer وrelease في finalize عند النجاح/الفشل/الإلغاء؛ shell global loader الافتراضي هو العرض الوحيد |
| حفظ/حذف دور | POST/PUT/DELETE Authorization/roles | حفظ dialog يعرض EditorDialog.saving؛ قائمة الأدوار تحدث snapshot المحفوظة، والحذف يستخدم التأكيد المشترك ثم يحدث القائمة |
| وصول مستخدم | GET/PUT Authorization/users/{id}/access | سياسة مباشرة مرتبطة بالمستخدم، ليست reference lookup أو cache عام؛ ExpectedVersion يمنع الاستبدال الصامت |
| شجرة الصلاحيات | بيانات workspace المحملة، لا HTTP داخل PermissionTree | توسيع وبحث وتحديد محلي؛ لا قراءة لكل permission أو تحميل per-row |
| إنفاذ API | linked user ثم direct grant أو role join حسب الحاجة | لا cache صلاحيات بين المستخدمين؛ استعلامات متسلسلة على DbContext الواحد |

يصل الدور من `pages/routing.ts` إلى المسار الصحيح، ويعرض
`layout/layout.component.html` مؤشر الصفحة عندما showPageLoading ليس false؛
أزيل مؤشر قائمة الأدوار الداخلي المكرر مع بقاء aria-busy والحراس.
حفظ dialog له مؤشره المشترك المرئي فوق المحتوى. لا إثبات بصري أو توقيت فعلي.

الفهارس الحالية على المستأجر/المستخدم/الدور/الصلاحية هي التغطية الأولية
لاستعلامات المنح. لا فهرس أداء إضافي مبرر من المصدر دون SQL plan وبيانات واقعية.
فهارس التسجيل والربط الفريدة هدفها الثبات ومنع التعارض، وتحتاج المخطط عند المالك.
يقيس المالك أول فتح وRefresh وحفظ دور وتقييم طلب مسموح/مرفوض، بنفس حجم
المستخدمين والأدوار والصلاحيات، وحالة الكاش والفلاتر، مع network وSQL plans
وعينات متكررة. لا مقارنة زمنية قبل/بعد منفذة ولا ادعاء تحسين سرعة مقاس.

## المراجع والمكونات والوثائق

قُرئ مدخل الكتب والفهرس ومهارة سيجما، وكتل BE6 وMaster5/7 وUI23/26، مع
الحزم الحالية والتحقق من drift. شجرة الإعدادات ومحرر dialog الحاليان مالكا
التنفيذ؛ لم تنشأ مكتبة تصميم أو wrapper موازية.

دليل سبيد S039 يثبت إنشاء الأدوار بواسطة المدير وإسنادها للمستخدم. وقُرئت
لقطة ٢٨ أكتوبر: `sidebar/24-administration/screens/32-roles.md` والكودان
C0032 وC0033؛ يثبتان عرض/إنشاء/تعديل/حذف الدور وخدمات getRoleForEdit و
createOrUpdateRole وشجرة الاختيار، ولا يثبتان تحقق الخادم أو claim الهوية.
تطابق هذا السلوك مصدرًا مع مساحة Sigma؛ النسخ والملخص إضافتان من طلب المالك.
قُرئ مدخل Odoo وفهرسه المثبت؛ لا صفحة مخصصة لحارس endpoints أو تسجيل مالك
الشركة ضمن المجموعة المحلية، ولذلك لا يُستنتج منه عقد تفويض جديد.

وُحدت أسماء العمليات وعرضها في PermissionTree المشترك حتى تستفيد منه شاشتا
الأدوار والمنح المباشرة. حُدث UI26 والمهارة وسجل التغيير لتوضيح أن backend
enforcement لا يعني وجود frontend permission guard. أعيد توليد الحزم الثماني
بالمولد، لا بتحرير الناتج مباشرة، ثم نجح drift check؛ التغيير الدلالي يحافظ
على المصدر والخادم كحد التفويض ولا يحول snapshot الإدارة إلى API جلسة.

دليل المستخدم الحالي:
`SiGmaAngularFrontEnd/src/app/modules/UserGuide/content/administration-guide.ts`،
ضمن دليل الإدارة الحالي عبر `UserGuide`، بموضوعي `/Role` و`/User`؛ يشرح
الإنشاء والنسخ والتحديد الظاهر والملخص والحماية وحالات الربط والاستكمال.
دليل التسجيل في MVC ضمن `Views/TenantRegistration/Guide.cshtml`.
المحتوى ثنائي اللغة في Angular، وقبول الظهور والتنقل وRTL/themes عند المالك.

رابط دليل المجموعة في قائمة «المستخدمون والنظام» هو
`/UserGuide/admin-system`، وتبقى صفحة الإدارة العامة
`/UserGuide/administration` متاحة من ترويسة التطبيق. يستهلك GuideReader
المحتوى الحالي عبر ADMINISTRATION_GUIDE وADMINISTRATION_GROUP_GUIDES.

## المخطط والقبول المتبقي عند المالك

لم تُنشأ أو تُعدل أو تُشغل migrations أو snapshots. يراجع المالك هجراته
القائمة قبل إنشاء المزيد؛ الأسماء المقترحة لا تعني وجوب أربع هجرات منفصلة:

- مقترح منصة الاشتراك: `AddTenantDirectOnboarding`، متضمنًا ErpUserId في سجل التسجيل.
- مقترح الهوية: `AddTenantIdentityRegistry` وحقول الرابط والتسجيل والفهارس الفريدة.
- مقترح ERP: `LinkIdentityUsersAndProvisionTenantOwner`، متضمنًا User links وRole.IsSystem وفهارس العمر الكامل.
- مقترح استكمال الهوية إن كانت الهجرة الأولى سابقة: `AddIdentityUserRegistrationCorrelation`.

السجلات القائمة التي لا تحمل correlation تحتاج backfill يراجعه المالك؛ لا
ربط تلقائي بالبريد أو الاسم. كلمة المرور لا تحفظ في ERP، وإزالة أعمدة ERP
القديمة قرار schema مستقل.

قبول التشغيل المطلوب:

١. تطبيق المخطط الذي راجعه المالك وبناء المكونات وAngular.
٢. تشغيل ملف Sigma Platform للخدمات الأربع، ومراجعة الإعدادات المحلية/المستضافة ومفاتيح الاتصال الداخلية دون نشرها.
٣. إنشاء شركة ومدير من MVC، التحقق من اختلاف الكود والاشتراك وربط ERP، ثم الدخول بالكود الجديد.
٤. إعادة التسجيل بعد فشل كل حد، وتجربة طلبي ربط متزامنين، وإثبات عدم إنشاء هوية/مالك ثانٍ أو تغيير كلمة المرور.
٥. إنشاء مستخدم عادي من سيجما، واستكمال الفشل الجزئي بنفس UUID؛ مراجعة الصور وعدم تفعيل غير المرتبط.
٦. إنشاء دور ونسخه وحفظه وإسناده ومنح صلاحية مباشرة، ثم تنفيذ طلبات مسموحة ومرفوضة؛ سحب المنح وتعطيل الدور وإعادة الطلب.
٧. تجربة مستأجر آخر، مستخدم ERP غير نشط/محذوف، ERP claim غير مطابق، مستند موافقة مجهول، وendpoint غير مصنف.
٨. مراجعة مقصودة قبل منح عمليات reset/import/seed واختبارات الخرائط والهوية؛ الأسماء الفعلية لا تغير حراس المجال ولا تجعل كل عملية مناسبة لكل دور.
٩. قبول شاشة الأدوار والملخص والحماية والخطأ وRetry باللغتين والاتجاهين والثيمين وعروض الشاشة، ثم قياس الطلبات والاستعلامات.

## التحقق والتسليم

- تحقق المصدر: فحص فروق النطاق في كل مستودع منفصل، وفحص whitespace، ومطابقة القائمة ٥٩١/٥٩١، ونوع resolver وimports ومرجع Helpers وSDK inclusion.
- تحقق العقود: المنتج/المستهلك لـisSystem وERP links وUserSaveReceipt وregistrationId وExpectedVersion، وXML الموارد وJSON ملفات التشغيل وإدراج runtime TS الصريح.
- تحقق مستقل: security_audit امتلك ملف الجرد فقط؛ security_final_review راجع الربط والنشاط والحارس ثم الواجهة قراءة فقط. استُخدم الوكيلان القائمان بملكية غير متداخلة لتقليل انتظار الجرد وتوفير مراجعة مستقلة، دون إنشاء فريق إضافي.
- مراحل التنفيذ: استُكملت العقود القائمة، backend والمحرر وربط التشغيل ودليل المستخدم والمصالحة مصدرًا. لا مالية أو ترحيل مستند جديد، والدعوات مؤجلة بطلب المالك. التنفيذ التشغيلي والمخطط خارج التفويض الحالي.
- تحقق التنفيذ: لم يُنفذ build/tests/lint أو طلب HTTP أو قاعدة بيانات أو browser أو migration أو commit/push/deploy؛ لا ادعاء compiler أو runtime pass.

رسالة commit مقترحة للخلفية:
`feat: provision tenant owners and enforce reviewed ERP permission operations`

رسالة commit مقترحة للواجهة:

## سجل فحوص التسليم الحالية

- نتيجة مطابقة القائمة المصدرية: ٥٩١ من ٥٩١، دون مفقود أو زائد أو تكرار.
- نتيجة مفاتيح ترجمة authorization بعد استكمال حالة الدور: ١٠٤ مفاتيح في كل لغة، دون اختلاف أو تكرار.
- نتيجة الموارد: ملفا GeneralMessage صالحان كـXML، وكل مفتاح حماية مطلوب موجود مرة واحدة.
- نتيجة ملفات التشغيل: slnf وslnLaunch صالحان كـJSON، وكل مسارات المشاريع موجودة، وSigma Platform يضم أربع خدمات.
- نتيجة إدراج الواجهة: save-receipt هو ملف runtime الجديد المضاف صراحة؛ PermissionTree ملف قائم مستورد من محرري الأدوار، ولا يتطلب إدراجًا جديدًا. فحص أولي افترض خلاف ذلك وصُحح وفق import graph، دون تعديل إعدادات غير لازم.
- نتيجة فحص الفروق والـwhitespace: نجح النطاق في المستودعين، مع تحذيرات Git العادية عن تحويل LF/CRLF فقط. لا merge markers في المصدر المحدد.
- نتيجة الوثائق: الحزم الثماني مجددة عبر المولد، ثم drift check ناجح؛ فحص whitespace لنطاق الوثائق ناجح. لا تعديل يدوي للناتج المولد.

هذه فحوص قراءة ومطابقة مصدرية فقط، ولا تعادل lint أو compile أو اختبارات سلوك.

يبقي الإسنادات والمنح محفوظة ويُستبعد من اتحاد صلاحيات المستخدم.

٢. تعرض حالة وصول المستخدم المحفوظة `effectivePermissions` من رد الخادم،
ولا تعيد استنتاجها من نسخة workspace قديمة. الحساب المحلي معاينة للمسودة
المعدلة فقط. زر إعادة التحميل متاح للحالة المحفوظة والعرض أيضًا؛ ويحافظ
المسار القائم على تأكيد تجاهل المسودة عند وجودها. صُححت ترجمة مصدر المنح
لتعرض اسم الدور بدل عبارة «من الدور» وحدها.

دون فحص IsConfigured، ما قد يوجه إنشاء مالك ERP إلى قاعدة مختلفة عن إعدادات
المضيف. أُضيف حارس IsConfigured فقط؛ لا تغيير لقيم الاتصال أو استبدال عمل

الإعداد فقط دون قيمته، ولم يُفتح اتصال بقاعدة.

يجب تحديث الواجهة والخلفية معًا: طلب حفظ الدور القديم الذي لا يرسل isActive
يُرفض validation، بدل إعادة تفعيل دور غير نشط ضمنيًا. الإضافة لا تحتاج هجرة.
يلزم عند المالك أيضًا اختبار حفظ دور غير نشط وإعادة تفعيله، تعارض الإصدار،
حماية المالك، وتحديث الصلاحيات بعد تعديل الدور من نافذة أخرى، والتحقق من
قاعدة ERP الفعلية المختارة للمضيف قبل إنشاء بيانات الاختبار.

تمت مراجعة هذه الإضافة قراءة فقط بصورة مستقلة: لم تظهر ملاحظات مانعة في
الأنواع أو false/true أو حماية النظام أو ExpectedVersion أو نتيجة الاتحاد.
اجتاز النطاق فحص diff/whitespace بالمستودعين، وتحققت مطابقة ١٠٤ مفاتيح
ترجمة دون نقص أو تكرار. صحّح الجذر إضافة غير مقصودة نفذها وكيل المراجعة

البناء فقط كخطوة مستقلة. لا تشغيل هجرات أو كتابة بيانات مفترضة دون هذا
