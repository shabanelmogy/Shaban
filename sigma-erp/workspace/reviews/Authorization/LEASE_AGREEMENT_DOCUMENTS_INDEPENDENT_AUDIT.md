## الحدود

أُعيدت قراءة المصدر الحالي بعد إصلاح مسار فشل تحديث metadata. لم يُعدل كود
التطبيق، ولم تُشغل build أو tests أو typecheck أو lint أو browser أو قاعدة بيانات.

## النتيجة

- يحتفظ نجاح الرفع المرئي بكائن صف الوثيقة نفسه الذي يملكه اشتراك
  `FileControl.valueChanges`، ويحدّث `hasDocument` عليه. لذلك يظل فحص membership
  بالهوية صالحًا إلى أن تنجح قراءة metadata جديدة تستبدل الصفوف والاشتراكات معًا.
- إذا فشلت قراءة metadata يبقى العقد المحتفظ به ظاهرًا وتبقى محاولة رفع صريحة
  لاحقة قابلة للإرسال؛ لا يعاد تشغيل الملف القديم لأن قيمة control تُصفّر دون
  emission بعد النجاح.
- أصبح `retryLoad()` متاحًا مع retained contract متى انتهى loading والرفع، ويعرض
  القالب زر Retry لأي `errorMessage`. الفشل لا يدخل auto-retry loop؛ الاستعادة
  اليدوية تعيد الصفوف والاشتراكات من المصدر الموثوق.
- المواصفة المصدرية تضيف حالة: نجاح رفع، فشل metadata refresh، رفع صريح ثانٍ، ثم
  manual Retry ناجح. لم تُشغل المواصفة وفق حد المصدر فقط.
- بقيت حراسة write-state بلا حلقة، و`recoveryPending` مؤجلًا إلى نهاية busy tail،
  ورفع الملف المرسل مستقلًا عن destroy مع تحرير global loading، وتغير الممثل أو
  `agreementId` terminal عبر session.
