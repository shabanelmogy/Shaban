## Confirmed defects

### P1 — Valid Workshop `JobPO` creation has no server-owned source boundary

**Scenario.** The current valid Workshop flow is real: Job list navigates to `/PurchaseOrder/create?sourceJobId=<job>`, the PO editor reads that Job and then calls the ordinary `POST PurchaseOrder` endpoint. The public aggregate writer cannot distinguish this valid caller from any other authenticated caller: it accepts caller-supplied `POType.JobPO`, header `JobId`, and optional per-line Job ids after existence checks only. Thus this is not evidence that JobPO has no legitimate producer; it is a confirmed missing server source boundary around that legitimate producer.

**Evidence.** Frontend producer: `Workshop/Job/components/list/list.component.ts:184` opens the route; PO editor reads and renders source state at `details.component.ts:355-375,715-754`, seeds header/line Job ids at `details.component.ts:501-514`, and posts through ordinary `createOrder` at `details.component.ts:889-922`. Backend: `PurchaseOrderService.cs:157-195` accepts the ordinary add; lines 163 and 170 validate the caller values and lines 186-195 persist them. `InvalidTypeFields` at lines 859-872 requires only a positive header Job id and descriptions; `InvalidDetailReferenceAsync` at lines 879-892 only proves supplied line Job ids exist. Approval repeats existence/type validation at lines 448-479. `PURCHASE_ORDERS_CONTRACT_FREEZE.md`, “Owner clarification — Workshop type in Create PO”, defines Workshop/Job as the producer.

**Impact.** The valid UI prefill is presentation evidence, not server provenance. A direct caller can produce the same `JobPO` shape without using the Job route, can supply a different live header Job, and can supply live line Job references unrelated to the selected source Job. The saved record cannot prove which Job transition created it.

**Minimal correction.** Add a dedicated `CreateFromJobAsync(pathJobId, payload)` action. Resolve the live Job tenant-side, derive `POType.JobPO` and header `JobId`, reject conflicting line Job/source references, then reuse the same PO validation, tax, calculation, numbering and one-save writer. Reject `JobPO` in ordinary Add. Update the existing Job-list/PO-editor consumer to call the source action. Existing historical JobPO rows remain readable. No schema change is required merely to make the command source-owned; a separately queryable provenance/history requirement would need a frozen schema decision.

### P1 — `BillStatus` is a freely reversible manual toggle with no bill evidence

**Scenario.** `POST PurchaseOrder/{id}/ToggleBillStatus` toggles `Billed <-> NotBilled` for any approved PO and saves immediately. It does not resolve a Bill, GRN, BillDetail, or other downstream source, and accepts no expected-current-state/reason. The frozen PO review explicitly leaves CreateBill/GenerateBills without an owning conversion contract, while the GRN/Bill relationship is the actual known billing evidence.

**Evidence.** `SiGma.ServerAPI/Controller/PurchaseOrderController.cs:43-49` exposes the mutation. `SiGma.Business/Services/VouchersServices/PurchaseOrderService.cs:499-525` performs the reversible toggle and checks only that approval is Approved. `IPurchaseOrderService.cs:23` exposes it as a domain action. `PURCHASE_ORDERS_CONTRACT_FREEZE.md` classifies CreateBill/GenerateBills as Missing and says no fake accounting action should be introduced.

**Impact.** The server can claim an approved order is billed without any bill, or clear the status while downstream financial evidence may exist. The value is then consumed by list/action state and rejection/delete guards, so it is not merely decorative.

**Minimal correction.** Freeze the owner of PO billing state before implementation. With current source evidence, remove/disable the public manual toggle and derive `BillStatus` from the confirmed bill/receipt relationship, or replace it with a typed Bill conversion action that atomically creates real evidence. If legacy deployments intentionally use a manual marker, that is a **Missing business decision**, not evidence for a reversible toggle; define allowed transitions, proof/reason, concurrency and audit before retaining it.

## Confirmed invariants

- **Tenant and soft-delete boundary.** Normal `Repository.Query<T>` applies authenticated `SubscriptionId` and live-row filtering (`SiGma.Repos/Repository/Repository.cs:33-56`). `QueryReport<T>` independently fails closed without a tenant, applies the tenant predicate and soft-delete predicate (`Repository.cs:59-115` and continuation). Cycle queries use one of these owners rather than raw `DbSet` access.
- **PR approval is terminal and audited.** Only Pending/`NotApproved` may become Approved or Rejected; readiness and all live detail references are revalidated before approval, an approval log is appended, and the root concurrency token is saved under the shared write lock (`PurchaseRequestService.cs:176-205`, `PurchaseRequest.cs`, `PurchaseRequestConfig.cs:22`). Approved/rejected requests cannot be edited, removed, activated or re-decided (`PurchaseRequestService.cs:282-320,483-502`).
- **Partial PR conversion is capacity-bound.** Live, nondeleted source-linked PO lines reserve quantity. Conversion accepts only distinct source detail ids and positive command quantities, derives supplier/type/price/source ids server-side, checks aggregate capacity and allocates the saved request discount cumulatively (`PurchaseOrderService.cs:658-744,746-837`). Soft-deleted orders/lines release capacity by query filtering.
- **PR basis is protected after conversion.** Once a live PO exists, supplier/type/discount, live line membership, quantities, prices and source reference identities cannot change; header-only fields may still change (`PurchaseRequestService.cs:338-385`). Removed children are checked for inbound use before reconciliation.
- **PO approval/edit/delete receipt lock.** PO update, reject, remove and activation paths detect both linked receipts and conservative legacy `(LPO No, supplier)` receipts. List/detail flags use the same live-receipt concept (`PurchaseOrderService.cs:102-126,230-240,353-356,388-447,529-580,797-819`). Voided receipts no longer lock the PO.
- **GRN linked-source values are server-owned.** For a linked GRN, PO must be approved Stock/Asset with matching type and supplier; every input line must name one unique live PO detail. Item/asset/description/UOM/unit price/ordered quantity and already-received quantity are overwritten from source/current receipts before calculation (`GoodsReceivedNoteService.cs:260-375`).
- **GRN quantities fail closed.** Received quantity must be positive and no greater than fresh remaining quantity. Other live nonvoid linked receipts are summed by PO detail id. Legacy unlinked receipts matching PO number/supplier/item-or-asset reserve capacity; ambiguous duplicate source lines are rejected (`GoodsReceivedNoteService.cs:286-345,462-634`).
- **Server owns receipt totals and VAT.** GRN Add/Update DTOs omit `AlreadyReceived`, Amount, Tax and AmountPlusTax. The service validates representable price/amount bounds, recalculates lines, allocates once-rounded document VAT and persists those results (`GoodsReceivedNoteService.cs:361-393`; GRN detail Add/Update VMs).
- **Issue-to-Job is atomic and Stock-only.** Add validates Stock GRN plus a live Job, groups positive received item quantities, adds GRN and source-linked `ItemIssue` to the same scoped context, then saves once (`GoodsReceivedNoteService.cs:139-182,249-257`). A live issue makes the GRN read-only and blocks void/delete (`GoodsReceivedNoteService.cs:400-415,644-680`).
- **Void preserves history and releases receiving capacity.** Void requires a reason, is terminal, and is blocked by a live BillDetail or ItemIssue. Linked capacity and the directly related pending-stock report ignore voided receipts (`GoodsReceivedNoteService.cs:644-671`; `StockReportsService.cs:357-425`). No inventory/accounting reversal is invented.
- **Atomicity/concurrency is coherent across source quantities.** PR, PO conversion/update/actions and GRN add/update/void/delete all participate in `ExecuteUniqueWriteAsync<PurchaseRequest>`. The helper opens one read-committed transaction, acquires an exclusive tenant/entity application lock before reads/mutations, and commits only a successful result (`SiGma.Repos/UnitOfWork/UnitOfWork.cs:65-100`). Aggregate adds and issue-to-job use one `SaveChangesAsync`; no redundant nested transaction was found.
- **Job deletion sees purchasing/stock consumers.** Job removal checks header/line PO, PR line, GRN, ItemIssue, ItemRequisition and ItemReturn references before deletion (`JobService.cs:1205-1221`). This protects existing cross-module references, though it does not establish Workshop as the only JobPO writer; that is the defect above.

## Generic writer and parent-scope follow-up

- **No public inherited AddList/UpdateList route was found for these aggregates.** `SiGmaControllerBase` exposes ordinary POST, PUT, DELETE, list/detail and `handleActivate`, but not service `AddListAsync`/`UpdateListAsync` (`SiGmaControllerBase.cs:26-66`). PO inherits the unsafe generic service `AddListAsync` implementation (`Service.cs:62-77`), but the scoped controller/caller search found no HTTP or business caller, so this is a dormant service-surface risk rather than a demonstrated cycle bypass. Minimal hardening during PO correction: override it to reject aggregate batch creation, matching GRN, or route it through the same prepared PO writer if a real caller is later frozen.
- **PO bulk Update is guarded, not inherited.** `PurchaseOrderService.UpdateListAsync` routes all rows through `UpdateOrdersAsync` under the PR lock (`PurchaseOrderService.cs:209-337`). It validates distinct roots, tenant FKs, owned child ids, approval/receipt state and PR source identities; it excludes every edited PO from existing reservations, combines the complete edited snapshots, then checks source capacity once (`lines 282-312`). I found no over-consumption path through this method.
- **PR AddList/UpdateList are feature-owned.** AddList invokes the same reference/type/pricing preparation per row before one save (`PurchaseRequestService.cs:248-279`). UpdateList takes ItemRequisition then PR locks, rejects decided requests and linked requisition sources, prepares every snapshot before mutation, and preserves the same linked-PO basis lock (`lines 305-330,337-409`). No inherited batch bypass was confirmed.
- **GRN closes all three generic aggregate bypasses.** AddList, UpdateList and activation return `GoodsReceivedNoteUseAggregateEditor` (`GoodsReceivedNoteService.cs:683-687`). This prevents bypassing linked capacity, server totals, ItemIssue creation and void state.
- **Activation is reachable but does not release quantity.** The base controller exposes `POST {aggregate}/handleActivate`. PR and PO overrides reject terminal approval states; PO also rejects billed/live-receipt records (`PurchaseRequestService.cs:495-502`; `PurchaseOrderService.cs:555-580`). Reservation and receipt queries do not treat `IsActive` as lifecycle state, so deactivating a pending source-linked PO cannot release PR capacity. No quantity bypass was confirmed. These document activation endpoints are semantically unnecessary and may be rejected in a later cleanup, but current source does not prove a cycle corruption.
- **Child FK ownership is aggregate-scoped.** There are no PurchaseRequestDetail, PurchaseOrderDetail or GRN-detail controllers/services exposing direct CRUD. Root updates load live children and apply `OwnsAll`; linked PO lines preserve their saved `PurchaseRequestDetailId`; linked GRN lines preserve/resolve saved `PurchaseOrderDetailId` and verify it belongs to the selected PO (`PurchaseOrderService.cs:230-329`; `GoodsReceivedNoteService.cs:199-244,260-345`). Cross-parent child-id takeover was not confirmed.

## Assumptions and open decisions

- **PurchaseReturn is a supplier financial credit/allocation instrument, not a physical GRN reversal.** The owner's corrected evidence says its allocation selector includes eligible supplier movements of different supported types, and approval must persist the allocation and post a balanced journal. It therefore must not increase PO receivable capacity or authorize GRN void. The actual eligible-source/allocation/ledger implementation is outside this upstream slice and remains to be audited against that corrected contract; no physical stock-return behavior is inferred here.
- **Zero-quantity PR lines are intentional only as inert lines.** PR Add/Update metadata permits zero, approval readiness rejects negative rather than zero, and conversion exposes no remaining capacity for zero. Existing frozen evidence explicitly says zero has no capacity. Changing approval to require every line positive is a business-rule change, not a confirmed defect.
- **Legacy receipt matching is conservative compatibility.** `(PO No, supplier, item/asset)` reservation can fail closed on ambiguous duplicate PO lines but cannot reconstruct line provenance. Automatic historical linking/backfill remains out of scope and must not be inferred.
- **GRN tax is a saved receipt estimate.** No journal/posting owner was found in this upstream cycle. Its tax values must not be described as posted tax or used to imply accounting completion.

## Proposed correction order

1. Freeze and implement the ordinary-PO rejection/dedicated Workshop producer boundary for `JobPO`.
2. Resolve the Missing BillStatus ownership decision; then remove the manual toggle or replace it with a real evidence-producing action.
3. Re-run source reconciliation across PO list/detail action flags, approval and Workshop consumer after those corrections. Owner build/runtime/database checks remain mandatory.
