# إصلاح بنية Security وتوافقه

## العقد والنطاق

يعتمد المالك المشروع المحلي SiGma.Security. تأكد منه صراحة أن كود الدخول101007 يقابل رقم الاشتراك1007؛ هذا ربط إعداد صريح، لا اشتقاق حسابي. الخدمة الخارجية السابقة كودها غير متاح ولا يعود عقدها مصدرًا للتنفيذ. العمل تنفيذ مصدر فقط؛ لا build/test/lint/DB/browser/migrations/commit/push/deploy. تحفظ تغييرات المجالات والموافقات القائمة. التطبيق في checkout الحالي لوجود تكاملات جارية يجب الحفاظ عليها؛ لا نسخ أو إعادة عمل تغييراتها في worktree قديم.

التقسيم المعتمد: Controllers للنقل والسياسات؛ خدمات مستقلة للدخول والجلسة وإدارة الهوية والتوكن؛ Options/Extensions لتهيئة المضيف؛ Models/DataAccess لIdentity مع إبقاء أسماء أنواع EF وnamespace القديم لتجنب تغيير schema؛ contracts كل نوع بملف. لا فرض generic ERP CRUD على IdentityUser.

## قرارات مستهلكة

- التوكن يحمل sub=معرف Identity، وsubscription_id=رقم المستأجر، ويحافظ NameIdentifier=رقم المستأجر المتطلب حاليًا في ERP، وName=اسم المستخدم وRole=الأدوار. مستخدم منصة بلا مستأجر لا يحمل معرف مستأجر صالحًا. داخل Security يقرأ المستخدم منsub وليس منNameIdentifier.
- توحيد issuer/audience إلى Sigma.Security/Sigma.ERP مع حقن نفس JWT:Secret الآمن في مصدر التوقيع وERP، وعدم كتابة قيمة بديلة ثابتة. لا إعادة استخدام قيمة سرية متتبعة أو طباعة أسرار. التوكنات القديمة تحتاج دخولًا جديدًا بعد التحويل.
- ربط كود الاشتراك إلى رقمه بخيار SubscriptionAccess:Codes؛ القيمة المعتمدة101007→1007. التحقق من المستخدم وكلمة المرور واشتراكه يسبق إصدار التوكن. العقد auth/consolelogin هو Result<UserLoginRm> الذي تستهلكه الواجهة. المسارات القديمة api/Authenticate تبقى aliases للنفس المالك والخدمات.
- إنشاء أول SuperAdmin بإجراء CLI إداري صريح لمرة واحدة، ببيانات خارجية فقط، دون نداء من الدخول أو HTTP ودون تشغيل هجرة تلقائي. لا تنفذ أداة CLI في هذه المهمة.
- إدارة الهوية عبر سياسات الأدوار القائمة: SuperAdmin للمنصة/الأدوار الإدارية، وAdmin لإدارة مستخدمي مستأجره، وسياسات Customer/Dashboard القائمة للفروع القديمة مع حارس ملكية المستأجر في الخدمة. أي تغيير role متصاعد/عبر المستأجرين يرفض. لا أسماء أدوار اعتباطية من العميل. التسجيل العام الذي يمنح Admin يصبح مسار إدارة محميًا؛ لا بوابة self-signup مجهولة تنضم لمستأجر مرسل من العميل.
- تغيير كلمة المرور ذاتي، وإبطال جلسة الآخرين إداري، والإبطال العالمي SuperAdmin. refresh يعيد قراءة الأدوار والهوية من المخزن ويستخدم توكنًا دوارًا مع كشف التعارض، ولا ينسخ claims قديمة. تسجيل الدخول لا يعتمد على توافر RabbitMQ.
- أدوار Identity عامة لحماية حسابات الخدمة. أدوار شاشات ERP وصلاحيات الإجراءات والفروع تبقى لدى Authorization الحالي، ولا يُدعى تفعيل EnforcementEnabled=false. ربط إدارة شاشة المستخدم ERP بإنشاء Identity حساب آخر شريحة لاحقة محددة؛ لن تتحول حقول Password الخام في ERP إلى مصدر مصادقة.
- ربط الواجهة محليًا إلى Security على منفذه الموجود7120؛ عنوان production مسار نفس الأصل /identity/ يحتاج reverse proxy لدى النشر، دون تخمين عنوان خادم خارجي. لا تغير عنوان ERP أو بيانات مجالات أخرى.

## المقارنة والمراجع

المالكون الفعليون Identity UserManager/RoleManager وIdentityDbContext بالمشروع؛ Legacy AuthenticateController وProgram يخلطان العمل والنقل. master1/4/5/7 وBE3/5/6/8/18 وقواعد source-only تنطبق. recipe check نجح للحزم الثماني. مهارة Sigma ومهارات brainstorming/systematic-debugging/writing-plans/verification تطبق بشكل متناسب مع التفويض القائم. Speed ودليله وكوده وOdoo غير منطبقين على تنظيم خدمة الهوية دون تغيير شاشة عمل تجارية. لا screenshot أو grid أو مال أو AutoMapper جديد. UI auth/service/env/دليل المشتركين فقط إن تغير مستهلك الدخول. لا هجرات أو snapshot.
