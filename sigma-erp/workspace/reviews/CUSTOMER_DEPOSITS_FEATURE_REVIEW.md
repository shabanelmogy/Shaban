## Performance and indexes

Before: no customer-deposit route existed; the vouchers link ran an unrelated banking workflow. Server Search used count + projected page without real TotalCount or paging clamps; source date/customer/agreement branches did not consistently cover opening/PDC sources. Transfer ignored its amount. No elapsed-time baseline was run.

After: list Search remains two sequential source materializations (filtered Count and bounded projected page); no per-row requests, Includes, full entity materialization or parallel EF operations. Usage totals join by tenant-owned live usage and deposit identity; the count shares the same filter/used-only scope. The usage aggregate can still scan a large tenant's usage population depending on SQL optimization; plan/IO verification is pending. The page contains at most100 rows, default15. Enum type names are converted after materialization. Search returns authoritative clamped page and exact count; the consumer adopts those values and updates the same-path route without a duplicate request.

Types performs three distinct scalar source reads sequentially on its DbContext (receipt labels, PDC enum, opening enum), then merges small labels; it runs in parallel with the initial list and Customer bootstrap at the HTTP level. It is not a critical-path prerequisite for showing rows. ActionContext is one projected identity read with correlated usage existence; TransferAgreements is one eligibility/source projection plus one same-customer agreement projection, rather than reloading action context and customer in separate queries. The transfer dialog reads context/candidates concurrently over separate HTTP scopes. Candidate lists are complete for that customer; very large agreement histories remain a payload measurement consideration. Extend has a tracked lookup and save inside its existing unique-write boundary; Transfer adds authoritative source/context/history/target validation before its one source-link save. These are one-record operations, with no collection write loop. The existing generic GET now inherits the controller route and calls the feature's projected GetManyAsync instead of the recursive navigation loader; its count and page size are corrected too. No speed claim follows from fewer source calls or a visible loader.

Complete reports/Excel request sequential100-row pages through fetchAllPages, aborting the whole output on any failed page. Rendering is local15-row paging; print preparation disables scroll/pagination so the complete loaded result flows to paper. Reports can legitimately consume more time/memory than one list page. There is no new bulk export endpoint or financial cache.
