# Equipment Rental — implementation and source reconciliation

## السبب الفعلي لاختلاف الاتفاقية المعروضة — ٣٠ أكتوبر ٢٠٢٦

بعد استمرار المشكلة أعيد الفحص من نسخة Business.dll المجمعة في مسار العملية20564 الجاري. شُغّلت خدمة QuotationService.GetManyAsync للقراءة فقط بنفس شركة1007 ومرشحات أكتوبر٢٠٢٦ وصفحة١ بحجم١٥ وفرز التاريخ تنازليًا، خارج HTTP دون استخراج رمز أو تزوير جلسة HTTP، باستخدام هوية الشركة المحددة للفحص المباشر المصرح به. أعدت الاعتماديات من مجلد التطبيق وASP.NET Core المحلي دون تثبيت أو build. النتيجة الوحيدة: Id5 / internalApproval1 / customerApproval1 / masterAgreementId2 / canCreateMasterAgreement=false. هذا اختبار قراءة للخدمة المجمعة نفسها، لا مشاهدة للمتصفح أو التقاط استجابة HTTP.

المطابقة المباشرة: Agreement1 / Quotation3 / Subscription1007 / IsDeleted=true. Agreement2 / Quotation5 / Subscription1007 / IsDeleted=false / ApprovalStatus1 (NotApproved) / IsClosed=false / LiveRates4. رأس العرض٣ مؤرخ2026-09-23، ورأس العرض٥ مؤرخ2026-10-27، واعتماداهما1. إذًا الصف الموجود في قائمة أكتوبر يملك اتفاقية أخرى حية بالفعل؛ كان الاستمرار في فحص١/٣ بعد انتقال المالك إلى عرض جديد خطأ تشخيصيًا. عدم إظهار إنشاء اتفاقية أخرى لهذا الصف يطابق عقد منع الازدواج الحالي، ولا يلزم مسح FK أو تجاهل اتفاقية٢ الحية. وجود٤ بنود محفوظة للاتفاقية٢ يثبت أن إنشاءها الجديد لم يحفظ الرأس وحده. لم تُحذف الاتفاقية٢ أو تُعدّل حالتها أو أسعارها أو روابطها.

روجع SQL المولد من GridFilterProjection المجمعة للعرض٣ تحديدًا: masterAgreementId=null بعد استبعاد IsDeleted=true. يُنتج SQL الخام لـHasValue في بعض flags مقارنة scalar-subquery الفارغ مع0، فتكون CASE=false في SQL ثلاثي القيم؛ GetManyAsync يصحح CanCreateMasterAgreement بعد materialization كما سجل سابقًا. ليس هذا سبب رابط٢ الحالي الذي أثبتته الخدمة والقاعدة. لم يُغير هذا التشخيص بقية قواعد الفرز أو التصفية، ويظل تحسين إسقاط flags الأخرى ملاحظة منفصلة تحتاج نطاقها عند صيانة حالاتها.

شفافية التشغيل: احتاجت محاولة قراءة EF إلى تحميل SNI المحلي، ثم منع تعداد IQueryable التلقائي من PowerShell باستعمال object holders، ثم تحميل الاعتماديات قبل async لمنع resolver script على thread بلا runspace. إحدى محاولات reflection قبل تقييد IQueryable أدت إلى تعداد قراءة مجموعة Quotations بسبب تفكيك PowerShell للنتيجة؛ لم يطبع محتواها، ولم يكتب أو يحفظ أي كيان. النتائج المثبتة أعلاه من الاستدعاء النهائي المقيد بالشركة/فترة القائمة ومن SELECT هويات الحالة المحددة. لا build/tests/lint/migration/commit/push/deployment أو كتابة قاعدة بهذه الجولة.

أُزيل تعديل التركيز التخميني المضاف وحده في الجولة السابقة من قائمة العروض؛ كان غير كافٍ ولم يثبت سببًا للمشكلة. بقية تعديلات المالك وحراس حفظ التفاصيل محفوظة. أُحدث الدليل /UserGuide/equipment-rental لتوضيح مطابقة أرقام العرض والاتفاقية وأن حذف اتفاقية عرض آخر لا يحرر العرض الحالي. القراءة/الكاش/التحميل/الأداء عادت إلى المسار المباشر السابق دون طلب focus جديد أو index/schema جديد. لا ادعاء قياس زمن تحسن أو تحقق مرئي. لا عمال لأن التشخيص متسلسل. الحالة: هوية العلاقة الحالية مثبتة، لا خلل حذف حي مثبت لهذه العينة، ولا حاجة إلى migration. اقتراح commit للواجهة `docs(equipment-rental): clarify quotation and agreement identity after deletion` دون تنفيذه. قبل حذف أو تغيير أي اتفاقية أخرى يلزم تحديد رقمها الصحيح؛ لا تُكرر استعادة١ أو تفترض أن٢ محذوفة.

## تحديث رابط عرض السعر بعد حذف الاتفاقية — ٣٠ أكتوبر ٢٠٢٦

الحالة Implemented — source-only؛ مطابقة HTTP/الشاشة بعد الحذف pending. طلب المالك أن يزول الارتباط التشغيلي عند حذف الاتفاقية لأنه ما زال يرى المحذوف. نُفذ SELECT محدود بهويات وحذف الاتفاقيات المرتبطة بالعرض٣ فقط ضمن إذنه بالتجربة على البيانات التجريبية؛ النتيجة الوحيدة Id1 / QuotationId3 / SubscriptionId1007 / IsDeleted=true. لم يُعدل صف أو مخطط. لا يوجد دليل أن الحذف فشل، ولا أن التاريخ يجب مسحه.

المصدر الحالي QuotationService.GetManyAsync/GridFilterProjection في Services/VouchersServices يختار MasterAgreementId من Repository.Query<EquipmentMasterAgreement> الحي، ويؤكد شرط الشركة/QuotationId/IsDeleted!=true، وتُشتق منه CanCreateMasterAgreement وبقية الحالات. QuotationController يرث GetListAsync الذي يستدعي هذا GetManyAsync بالفعل. AddAgreementAsync يمنع ازدواج الاتفاقيات الحية عبر Repository.ExistsAsync؛ الحذف soft-delete في DbContext.HandleAudit يحتفظ بقيم الرأس الأصلية ويكتب IsDeleted/DeletedAt/DeletedBy. لم تُغير هذه الملاك الصحيحة أو تمسح FK تاريخيًا. لا يثبت فحص قاعدة البيانات أن استجابة GET القائمة نفسها تعيد المحذوف؛ يبقى ذلك مع فحص بقاء شاشة قديمة فرضية تشغيلية مفتوحة.

الإصلاح المصدرّي المؤكد في الواجهة هو غياب تحديث عند الرجوع إلى تبويب/نافذة القائمة المفتوحة بعد إجراء في شاشة أخرى: أضيف HostListener للـwindow:focus وdocument:visibilitychange إلى EquipmentQuotationsComponent، مع DOCUMENT من Angular common. يشترط ظهور التبويب وعدم listBusy (تحميل/تصدير/كتابة/تأكيد/محررات الشراء) وعدم تحميل/فشل الخيارات المشتركة. يستخدم requestList/currentQuery بالمرشحات المطبقة نفسها والصفحة/الفرز الحاليين، ولا يأخذ تعديلات مرشح لم يُضغط Search لها. التحميل المتزامن يمنع طلب العودة الآخر أثناء نفس القراءة؛ لا مؤقت أو polling أو cache أو event bus أو API جديد. يشترك الطلب في switchMap وإلغاء السياق/destroy وglobal page loader وfinalize وerror/Retry القائمة؛ host listeners تنتهي مع المكوّن. دخول المسار من جديد ما زال يجري القراءة الابتدائية القائمة. تبقى نوافذ التحرير والكتابة مستقلة دون إعادة ضبط.

المطابقة: شريحة S، Master1/2/4/5/7 وBE7/8 وUI2/5/22/28 وScreen01 لقائمة العرض (المحرر خارج الشريحة). الحزم الثماني بلا drift؛ استُخدم PHASE02 بعد فحصه. مراجعة فهرس دليل التحليل وشاشتي المعدات وC1487 السابقة تبقى دليل دورة فقط؛ هذا التصحيح مصدره سياسة الحذف الحي القائمة وطلب المالك، لا استنتاج من صلاحيات/خادم المرجع. لا عمود/ListVM/filter/mapper/مالية أو permission تغير. لا استخراج مشترك: هذا هو قرار إعادة قراءة قائمة تشغيلية بعينها بعد تغير مستندها المرتبط، ويعيد استخدام مسار القراءة الحالي دون تقديم مكون أو خدمة عامة موازية. لا عمال لأن العمل محدود ومتسلسل.

الكاش/الأداء: GET Quotation في EquipmentQuotationService.getList يبقى قراءة تشغيلية مباشرة بلا كاش؛ لا مصادر reference أو invalidation تغيرت. يضيف الرجوع المرئي قراءة صفحة واحدة عند السكون، وليس استعلامًا لكل صف أو لكل حدث خلال التحميل، ويحفظ count/page/tenant/live. لا مؤشر مناسب جديد لأن SQL القائمة لم يتغير؛ تبقى فهارس العلاقة والأداء الموثقة سابقًا، ولا ادعاء زمن مقاس. الدليل الداخلي equipment-rental-guide.ts على /UserGuide/equipment-rental يشرح أن المحذوف ليس رابطًا حيًا، وعودة إجراء الإنشاء عند بقاء الاعتمادين وغياب اتفاقية حية أخرى مع إبقاء المرجع التاريخي.

تحقق المصدر: روجعت imports/الدالة والحراس ومسار requestList الحالي وحقول DTO/actions والتغييرات السابقة دون إرجاعها. تحقق diff --check والتحليل النحوي منفصل عن فحص الأنواع/البناء. لم يُبنَ التطبيق أو تُشغل اختبارات/lint/migration/commit/push/deployment. اتصال المتصفح ظل غير متاح في التجربة السابقة؛ لا ادعاء مشاهدة اختفاء زر العرض أو نجاح إعادة الإنشاء. تحقق التشغيل: حذف مسودة غير مستخدمة، ثم العودة إلى قائمة العرض المفتوحة والتحقق من GET Quotation: masterAgreementId=null وcanCreateMasterAgreement=true عند اكتمال الاعتمادين؛ وجود اتفاقية حية أخرى يبقي زر العرض لها، ونافذة شراء/تأكيد/كتابة جارية تمنع القراءة التلقائية. إذا ظل GET نفسه يعيد Id1 بعد قراءة حديثة فهذه مشكلة خادم تحتاج الدليل الفعلي، ولا يغطيها ادعاء أن تحديث الواجهة أصلح SQL. لا حاجة إلى Add-Migration؛ اقتراح commit للواجهة `fix(equipment-quotation): refresh agreement links when returning to the list` دون تنفيذه.

## منع اتفاقية عرض سعر بلا تفاصيل وإعادة تجربة الإنشاء — ٣٠ أكتوبر ٢٠٢٦

الحالة Implemented — source-only، والتحقق التشغيلي pending. أوضح المالك أن تفاصيل العرض يجب أن تحفظ مع الاتفاقية، ثم أفاد بأنه حذف الاتفاقية التجريبية وطلب العودة إلى العرض وإعادة الإنشاء. لا تُعاد استعادة الاتفاقية١ ولا يُفترض أن الحذف شوهد في قاعدة البيانات؛ هذه إفادة المالك. جُمد شرط الشريحة في عقد التفاصيل قبل تعديل المصدر.

النتيجة المصدرية المؤكدة: كانت ValidateRatesAsync تقبل قائمة Rates فارغة عند الإنشاء والتحديث، ويستطيع عقد طلب فيه QuotationId مع Rates=[] حفظ الرأس وحده. لا يثبت ذلك الطلب التاريخي الذي أنشأ الاتفاقية١. ينقل إجراء قائمة العرض quotationId إلى مسار إنشاء الاتفاقية، ثم يجهز seedQuotationRates صفوف الكمية وهوية المعدة ووحدة الفوترة؛ save يأخذ getRawValue ويرسل Rates مع بقية الرأس. AddAgreementAsync ينشئ entity.Rates صراحة عبر CreateAgreementRate، وRepository.AddAsync يضيف الرسم عبر DbContext.AddAsync ويضبط ملكية الأطفال؛ CodeCreateService.SetDocumentNumbersAsync يعيد نفس الكائن دون إسقاط البنود، والحفظ يتم في SaveChanges واحد. إعداد EF الحالي يملك FK طفل الاتفاقية؛ لا دليل مصدرّي على أن الحفظ الحالي يسقط قائمة صحيحة غير فارغة.

الإصلاح: مُرر requireRates عند QuotationId موجب إلى ValidateRatesAsync في Add/Update؛ تُرفض القائمة الفارغة قبل أية استعلامات أو كتابة باستعمال EquipmentAgreementRatesInvalid الموجود. أضيف حارس الواجهة نفسه قبل فحص الحقول/تكوين الطلب، يعرض equipmentBilling.ratesInvalid ويفتح تبويب rates دون إرسال HTTP. تحقق الاعتماد الحالي يظل رافضًا للصفر، والمسودة المستقلة تحتفظ بعقدها السابق. لا مصدر/DTO/mapper/جدول/فهرس أو migration جديد، ولا حذف أو تعديل آخر لقاعدة في هذه الجولة. أسعار المشغّل المختلفة لا تختار تلقائيًا؛ وحدات الكمية المتكررة تتطلب معدات فعلية متميزة كما جُمد سابقًا، ولا وعد بتحويل كمية٤ إلى٤ معرفات مجهولة.

التناسب والمطابقة: شريحة S، Master1/2/4/5/7، BE8/14، UI13/14/19 وScreen02، وPHASE03 بعد نجاح drift check للحزم الثماني. أعيدت قراءة فهرس دليل التحليل، قسم Equipment Rental وشاشتي Quotations/Master Agreements في لقطة٢٨ أكتوبر ومقاطع C1487، مع قرارات C1487 السابقة في العقد. المقبول هو رابط التحويل والحفظ الوظيفي؛ قواعد أسعار/خادم المرجع غير المكشوفة لا تُستنتج. يظل المرجع الإنشائي shared editor/EditableRows، ولا تغيير markup أو PrimeNG API أو شكل جدول/listVM بهذه الشريحة. لا عمال لأن الحارسين تغيير صغير متسلسل.

التحميل/الكاش/الأداء: لا طلب جديد أو تغيير finite bootstrap/watch/finalize/context/Retry أو مصدر مباشر/كاش. القراءات التشغيلية القائمة كما في الجداول السابقة، وحفظ القائمة الفارغة يتوقف الآن قبل استعلامات lookup/save؛ لا ادعاء زمن مقاس أو query plan أو تسريع للحفظ الصحيح. لا فهرس جديد مناسب لحارس في الذاكرة، وتبقى نتائج قياس الحمل الأصلية معلقة. الدليل الداخلي equipment-rental-guide.ts على /UserGuide/equipment-rental يشرح شرط البنود في الإنشاء والتعديل والحفظ المشترك وفتح العرض بعد الحفظ قبل الاعتماد/التسليم.

التحقق: روجعت فروق الخدمة والمكوّن والدليل ضمن مستودعيهما مع الحفاظ على التغييرات السابقة، ونجح diff --check؛ تحذير تحويل LF/CRLF للدليل فقط دون خطأ whitespace. تحليل TypeScript النحوي للمكوّن والدليل أعاد صفر parseDiagnostics، وهو لا يثبت فحص الأنواع أو build/runtime. أعيد طلب inventory المتصفح بعد طلب العودة إلى العرض؛ بقي mcpapps بلا تبويبات وnative app-server os error3. طلب الخادم السابق أعاد401 للأداة بلا جلسة. لم تُستخرج رموز أو تتجاوز المصادقة، ولا build/tests/lint/DB/migrations/commit/push/deployment لهذه الجولة. اختبار الإنشاء والحفظ ثم GET تفاصيل الاتفاقية وOperationalSources لم يُنفذ ولا يُدعى نجاحه.

التحقق التشغيلي المطلوب عند توفر الجلسة: تشغيل الخلفية المعدلة، فتح عرض٣ من القائمة المحدثة، إنشاء الاتفاقية، مراجعة صفوف المعدات الأربع وتمييز الوحدات واختيار الأسعار والتواريخ، حفظ ثم فتح العرض والتأكد من Rates غير فارغة قبل الاعتماد، وبعده فحص معدات مصدر التسليم. محاولة حذف كل صفوف مسودة مرتبطة ثم حفظها يجب أن تبقى في المحرر برسالة نقص، ويجب أن يفشل الطلب الفارغ من أي عميل بلا إنشاء رأس. لا حاجة إلى Add-Migration. اقتراحا commit دون تنفيذهما: backend `fix(equipment-agreement): require equipment rates for quotation-linked saves`، frontend `fix(equipment-agreement): prevent saving empty quotation details`.

## تنفيذ التصحيح المشروط بعد إذن المالك — ٣٠ أكتوبر ٢٠٢٦

أجاب المالك «أسمح بالتصحيح المشروط للاتفاقية رقم ١»، ثم أكد أن البيانات تجريبية وسمح بالتجربة. نُفذ اقتراح الاستعادة نفسه مرة واحدة، مع تغيير @Apply إلى١ في نص الأمر بالذاكرة فقط والإبقاء على صفر في الملف للمراجعة. اجتازت الاتفاقية جميع محددات الهوية/الشركة/العرض/الاعتماد وعدم الإغلاق والحذف، وغياب أي EquipmentAgreementRate / SaleOrder / DeliveryNote / TimeSheet / EquipmentAgreementFinancialLog مرتبطة، بما فيها المحذوفة والتاريخية. نفذ UPDATE لحالة صف واحد داخل المعاملة ثم COMMIT؛ قراءة التحقق المضمّنة أعادت Id1 / SubscriptionId1007 / QuotationId3 / ApprovalStatus1 (NotApproved). لم تُنشأ بنود معدات أو أسعار، ولم يتغير أي مستند آخر أو مخطط. تمت استعادة قابلية التحرير، لا ادعاء استكمال المعدات أو نجاح دورة التسليم.

حاول الوكيل استكمال اختبار الشاشة ضمن إذن التجربة: أعادت cua.getState المتصفح mcpapps وحده بلا تبويبات، مع خطأ Native apps: failed to launch codex app-server / system cannot find the path specified / os error3. أعاد مدخل computer-use المعتمد @oai/sky في node_repl الخطأ نفسه عند list_apps؛ لا fallback خفي أو مساعد مخصص أو تثبيت. فحص HTTP للخادم المحلي بالمسار الفعلي /EquipmentMasterAgreement/1 أعاد401 لغياب جلسة مستخدم للأداة؛ لم تُستخرج رموز دخول أو تُتجاوز المصادقة أو تُنشأ جلسة مفبركة. لذلك اختبار إضافة المعدات والحفظ والاعتماد ثم مصدر التسليم متعطل باتصال أدوات التحكم، لا ينقصه إذن جديد من المالك. الكمية٤ بالمصدر لا تكفي لتخمين٤ هويات معدات، ولم تُدخل بيانات أسعار أو معدات مباشرة لتجاوز الكاتب. لا build/test/lint/migration/commit/push/deployment. التحقق الحالي يؤكد إصلاح الحالة في قاعدة البيانات فقط؛ إكمال البنود والتحقق من الشاشة ينتظران اتصال المتصفح أو استعمال المالك للمحرر الحالي.

## نتيجة الفحص المصرّح به وقرار إصلاح الاتفاقية١ — ٣٠ أكتوبر ٢٠٢٦

### القراءات والتحميل والأداء

لم تدخل مصادر GET جديدة. يظل جرد URLs والخدمات والكاش في القسم السابق أدناه ساريًا؛ أضيف عمر جلسة وإلغاء للمستهلك الفعلي فقط. قراءات sale-orders وpurchase-order history وapproval تشغيلية مباشرة بلا source cache opt-in، ولها StateMessage محلي ضمن EditorDialog خلف overlay. خيارات العملاء/الفروع تبقى في مصادرها المشتركة مع bootstrap ثم watch وteardown؛ لا كاش للماليات أو التوافر. قراءات القوائم/التصدير/التقرير تتبع عداد الصفحة، وحفظ/قرار المجال يحتفظ بbusy/guard/finalize ومالك التقدم الموجود. إبطال جلسة الاعتماد يمر عبر recordId=null وallowActions=false من العقد المشترك، مع بقاء الطفل مركبًا حتى تنتهي الكتابة الجارية؛ لا إلغاء كتابة لمجرد إلغاء قراءة.

تضيف حماية لقطة التسليم عمودين إلى إسقاط المصدر الموجود دون query جديد. تحقق التواريخ بحت داخل المسار قبل فحص الترتيب/التوافر. دفعات العرض غير المدعومة تتوقف قبل كل read/map/write، بدل استدعاء mapping/repository/save العام غير المحمي؛ ليس ذلك تحسين زمن مقاس. الإلغاء يمنع نشر نتائج جلسة قديمة، ولا يثبت أن الخادم أوقف SQL. لا predicates/joins/order جديدة تبرر index جديد لهذه الجولة، لذلك لا مقترح فهرس إضافي؛ المقترح السابق ومطلوباته عند المالك كما هما. القياس القابل للتكرار عند توفر التطبيق: نفس tenant/dataset/search/page، مقارنة cold/warm للطلبات والأحجام والـSQL plan/reads والوقت، ثم reset أثناء read/export/confirmation/write ومراقبة عدم صدور كتابة مؤجلة أو مخرجات مختلطة؛ القياس والظهور الفعلي معلقان.

### المطابقة النهائية وتسليم الجولة التشغيلية

نُفذت الإصلاحات التسعة المحددة أعلاه في المصدر. استكمل الأصل ما تبقى من مراجعة عمر القوائم بعد انتهاء العامل، وراجع مسح البيانات/الأعداد والتقاط revision عند التأكيد، وموضع takeUntil داخل HTTP مع بقاء trigger، وإلغاء getAllList كاملًا للتصدير/التقرير. حُفظت callbacks الكتابة السابقة حتى finalize دون تطبيق نتيجتها المحلية إذا تغير السياق. يتحقق فتح الإجراءات من وجود الصف في مجموعة القائمة الحالية؛ وتمنع نوافذ التشغيل المعطلة Retry أو Save حتى إعادة الفتح. أضيف تحقق required وعلامته داخل محرر التسليم عند عدم وجود تسليم فعلي، ويعاد تقييمه عند تغيير التاريخ وبعد تحميل التفاصيل، مطابقًا لشرط الخادم دون تغيير null الاختياري لسند مسلّم فعليًا.

ملفات هذه الجولة: في الواجهة قوائم العرض والاتفاقية والتسليم والساعات؛ محرر عرض السعر وقالبُه؛ نافذة سجل أوامر الشراء وقالبُها؛ نافذة ربط أوامر البيع وقالبُها؛ قالب قائمة الساعات؛ ومحرر التسليم وقالبُه (١٣ ملفًا داخل الوحدة)، مع `shared/service/report-print.service.ts` و`UserGuide/content/equipment-rental-guide.ts`. في الخلفية `DeliveryNoteService.cs` و`VouchersServices/QuotationService.cs` وموردا الرسائل. لا DTO/ListVM أو أعمدة أو AutoMapper تغيرت في هذه الجولة، فمطابقة الأعمدة/النماذج السابقة سارية. الدليل على `/UserGuide/equipment-rental` بمدخله الحالي يشرح تاريخ التجهيز واللقطة والخروج من أمر الشراء والسياق والتصدير وتحضير الطباعة، ولا يعرض منطق العميل المؤجل كميزة موجودة.

المراحل المطبقة: اكتشاف متناسب وعقد إضافي مجمد، تصحيح backend/الكتابة والواجهة والتكامل وعمر العمليات ثم المطابقة والدليل. لا إجراء مالي أو schema جديد يتطلب مرحلة مجال مستقلة؛ فُحصت المسارات المالية القائمة للتكامل فقط. استُخدمت ثلاثة مسارات عمال مستقلة بعد التجميد: تدقيق/تصحيح خلفية التسليم وحد كتابة العرض؛ تدقيق/تصحيح الواجهة؛ ومقارنة المرجع للقراءة. النماذج موروثة دون override، والملكيات فصلت الموارد/الكتب/الدليل/المشتركات عند الأصل عن ملفات العمال لتقليل زمن الجدار دون تعارض. انتهى عامل الواجهة بحد استخدام أثناء امتداد القوائم، فاستكمل الأصل فحص الملفات الموجودة وتصحيح محرر التسليم والتكامل النهائي؛ لا يُعد تعطل العامل قبولًا أو تحققًا ناجحًا لجزء لم يراجعه الأصل.

نجحت الفحوص النهائية: تحليل بناء الجملة لـ٨٥ ملف TypeScript/قالب في نطاق المعدات مع خدمة الطباعة والدليل، بلا diagnostics؛ وفحص whitespace في نطاق المستودعين؛ وXML وتطابق١٩١٥ مفتاحًا فريدًا لكل مورد خلفي؛ وفحص الحزم الثماني وروابط الكتب والتحقق الرسمي للمهارة. المفتاح الخلفي الجديد `EquipmentQuotationBulkUnsupported` موجود باللغتين، ورسالة السياق المعاد استخدامها موجودة بالقواميس. روجع فرق خدمة الطباعة العام ومدخلاتها ومستهلكها، ودعم المشروع للواجهات المستعملة؛ لا runtime file inclusion مفقود أو namespace جديد في هذه الجولة. الفحوص مصدرية فقط، وليست typecheck/build/tests أو SQL plan أو قبولًا بصريًا. أعيدت الحزم بالمولد بعد UI13/21/28 وقالبPhase5 وروجعت دلاليًا حدود closed/cancel/context مقابل مصادرها.

توضيح المالك بشأن البيانات التجريبية يلغي سبب الحفاظ على دقة عرضية قديمة. لكنه لا يحول السعر أو النسبة أو المعرّف إلى كمية؛ أظهر جرد مستهلكي التوجيه المباشرين533 استعمالًا بأدوار مختلفة. لذلك صُنفت حقول النطاق فعليًا، وأُلزمت الشاشات الجديدة والمراجعة بالتصنيف والسياسة المشتركة في UI14/19 وBE18 والمهارة وتعليمات مساحة العمل. الاستخدامات الأخرى غير المصنفة فجوة جرد قائمة، ولا يُدعى ترحيل البرنامج كله. الساعات عشرية:1.5 تعني ساعة ونصف، وليست صيغة HH.MM. لا إعادة تسعير أو حذف بيانات تجريبية.

### مطابقة الأعمدة والنماذج

قائمة العرض تستهلك حقولها السابقة مع `CustomerName` و`ContactName` منفصلين. قائمة الاتفاقية تستهلك حقولها السابقة مع `QuotationType?`. قائمة الساعات تقابل الـListVM: Date/DateRangeStart/DateRangeEnd، DeliveryNoteNo/MasterAgreementNo/CustomerName/PlateNo/ChassisNo، Shift?، HoursToInvoice/BreakHours/StartHM/EndingHM/OperatorOvertimeHours، ApprovalStatus/IsBilled، وId لهوية الإجراءات؛ تبقى IDs الثلاثة للنقل والبحث المتوافق. لا يُرسل مستند في ListVM لأنه يستهلك في التفاصيل فقط. خرائط AutoMapper تضيف الإسقاطات المقيدة للقراءة، وتبقى كتابة الساعات صريحة مجمعة وكتابة تجهيز الصفوف موحدة عبر CreateAgreementRate، دون Ignore أو ReverseMap إضافيين.

### التحميل والكاش والإلغاء

الطرق الفعلية من قوائم العرض/الاتفاقية/الساعات إلى محرريها هي نطاق الفحص. خيارات فروع مرشح الاتفاقية تتبع BranchService والمصدر المشترك: bootstrap محدود ناجح قبل watch منفصل، ومسح السياق وفشل/Retry وحفظ الاختيار؛ required routed bootstrap يملكه page ReferenceLookupStatus. بقية مصادر الخيارات القائمة على عقودها كما في جرد المراجعة أدناه. مصدر خيارات سندات الساعات وقراءة تفاصيل السند تشغيلية مباشرة، وليسا reference-cache opt-in؛ لا كاش جديد لقرار التوافر/المصدر. لا طلب لكل صف في الإدخال اليومي.

قراءات نافذة الساعات والدفعة خلف overlay محلية عبر ReferenceLookupStatus/StateMessage؛ حفظها عالمي مع `EditorDialog.saving` ليظهر مالك النافذة عندما يحجب overlay تقدم القالب. start/finalize والإلغاء عند الإغلاق وتغير السياق موصولون؛ تتوقف المدخلات والرفع والخروج أثناء الكتابة والتنظيف/التأكيد. يحتفظ refresh في السياق الجاري بعقوده، ولا تؤدي query-only navigation إلى إعادة ضبط loader. التحقق المرئي والتوقيت الفعلي معلقان؛ المصدر وحده لا يثبت ظهورهما.

### الأداء والفهارس

تصفية البحث الجديدة قبل count/page/export بإسقاط حقول مستهلكة فقط؛ لا join يكرر الاتفاقيات. حفظ الساعات يقرأ مصادر السندات كمجموعة، والصفوف المطلوبة وحماية فواتيرها/اتفاقياتها كمجموعة، ومالكي الملفات اختياريًا كمجموعة، ثم حفظًا واحدًا. أزيل InvalidInputAsync المكرر من مسارات الحفظ الأربعة بعد إثبات أن المراجع الثلاثة القابلة للتحرير يغطيها المصدر؛ لا UniqueColumns أو child graph آخر، ورابط الفاتورة خادمي. يقل العمل المصدرّي بمقدار3 قراءات للمفرد و3×N للـbulk القديم؛ لا يُدعى زمن مقاس أو عدد SQL كلي من ذلك. مسار الترقيم يحتفظ بمالك UOW وفallback الساعات الموجود بلا سياسة أرقام موازية.

الفهرس الجديد المنفذ في EF هو سلامة ملكية المستند: `(SubscriptionId,DocumentPath)` فريد بمرشح `[DocumentPath] IS NOT NULL`، يشمل المحذوف قصدًا، ومفتاح المسار المحدود400 مع tenant ضمن حد SQL المعتاد؛ كلفة كتابة/مساحة لكل ملف غير فارغ. لا فهرس بحث جديد نُفذ. فهارس FK الحالية أحادية لا تثبت تغطية طلبات الفوترة. مقترح للتحقق فقط: `TimeSheet(SubscriptionId,DeliveryId,ApprovalStatus,DateRangeStart)` مع INCLUDE `(DateRangeEnd,HoursToInvoice,EquipmentRentalInvoiceId,Id)` ومرشح `[IsDeleted]=0`؛ يفيد مساواة الاشتراك/السند/الاعتماد ثم نطاق البداية، والنهاية وحالة الفاتورة residual. تعبير `.Date` وعلاقة الفاتورة وترتيب Id يحتاجان SQL plan فعليًا؛ لا وعد seek أو إلغاء sort. قارن التداخل مع فهارس الإنتاج وكلفة كل حفظ/اعتماد قبل اعتماد المقترح. بحث Contains في اللوحة/الشاسيه لا يبرر فهرس B-tree بسيطًا، وفرع السند متعدد القيم يحتاج خطة واقعية قبل إضافة فهرس مركب آخر.

شروط القياس عند المالك: نفس tenant وعدد السندات والكشوف، دفعات1/50/200 مع/دون ملفات، قائمة بالمرشح نفسه وpage/count/Excel متطابقين، cold ثم warm، قياس الطلب/حجم الرد/SQL reads+plan+duration وزمن العرض؛ مقارنة median وp95 قبل/بعد. لم تُشغل قاعدة بيانات أو تطبيق أو benchmark.

### الدليل والترحيل والتحقق

حُدث `UserGuide/content/equipment-rental-guide.ts` في المسار القائم `/UserGuide/equipment-rental` ومدخله الحالي: البحث الجديد، ساعات العرض العشرية، تجهيز الاتفاقية، الوردية والمستند والإدخال اليومي، ومعنى الساعات العشرية والتنظيف والنتيجة غير المؤكدة. لا دليل لوظيفة غير منفذة.

يلزم ترحيل المالك. الاسم المجمع المقترح `UnifyEquipmentQuantityAndHourDetails` (فُحص عدم وجود اسمَي الشريحتين ثم الاسم المجمع قبل التسليم): تحويل أعمدة الساعات الخمسة وQuotation.HoursAllowed إلى decimal(18,6)، إضافة Shift وDocumentPath/Name وفهرس المسار، وإضافة موعد/عداد التجهيز. يمكن استخدام اسمَي الشريحتين السابقين إذا فصل النشر، مع إدراج HoursAllowed صراحة. لا ملفات ترحيل أو snapshot عدلها الوكيل؛ التغييرات القائمة خارج النطاق محفوظة. ينشر المخطط مع الخلفية والواجهة المتوافقتين، بلا إعادة حساب للفواتير أو حذف بيانات.

المراحل: تخطيط وعقد مجمد ثم القراءة/التفاصيل والكتابة والتكامل والمطابقة؛ لا إجراء مالي جديد ضمن هذه الشرائح. استُخدم ثلاثة عمال ورثوا النموذج: خلفية الساعات؛ واجهتها وقوائم القراءة؛ وتجهيز الاتفاقية ثم ساعات العرض/جرد الأدوار الرقمية. كانت الملكيات منفصلة بعد التجميد، ثم دُققت القراءة والماليات مستقلًا ودمج الأصل المخرجات والمشتركات والموارد والدليل والوثائق. راجع الأصل الفروق المجمعة ذات الصلة؛ بقي قبول الأنواع/compiler وSQL/runtime/RTL/theme/scroll/file lifecycle عند المالك. رسائل commit المقترحة: للخلفية `feat(equipment-rental): unify quantity precision and daily work sheets`؛ للواجهة `feat(equipment-rental): add daily sheets and shared numeric profiles`؛ للوثائق `docs(sigma): define shared numeric foundation and reconcile equipment details`. اقتراح فقط؛ لا commit أو push.

الفجوات المرجعية الباقية محددة في خطة التكافؤ: رسوم وسماحات وحد أدنى وقواعد شهور بديلة، اختيار المشغّل والملحقات والفحص، أثر اعتماد/رفض التسليم، نسخ العرض والاستبدال، الودائع والحجز البنكي، والتأجير المنتهي بالتمليك. الشاشات الحالية البسيطة ليست سبب استبعاد؛ لكن كود الواجهة المرجعي لا يثبت أثرها الحسابي أو انتقال الخادم، فلا تدعي الشرائح المنفذة تكافؤها الكامل.

حصيلة التحقق النهائي: فحص بناء الجملة المصدرّي لـ٩٢ ملف TypeScript/قالب شمل نطاق المعدات والمشتركات المتأثرة والموارد والدليل دون تشخيصات. مجموعات ترجمة الفوترة٣٧ والساعات٩١ والتحقق٢٥ مفتاحًا متماثلة وبلا تكرار؛ أزيل تكرار مفتاح الوردية وأعيد استعمال shiftDay/shiftNight الموجودين. الموردان الخلفيان XML صالحان، كل منهما١٩١٤ مفتاحًا بلا تكرار أو اختلاف. نجح diff --check لكل نطاق مستودع، وفحص الحزم الثماني وروابط الكتب، والتحقق الرسمي للمهارة. روجعت دلاليًا قوالب/حزم المراحل١/٣/٦ لتصنيف الرقم ودقة السياسة وعدم تقريب الإدخال، وأختامها مشتقة من UI14/19 وBE18 دون تغيير المرجع المعتمد لكل شكل. هذا فحص مصدر ووثائق، وليس build أو typecheck أو tests أو قياس تشغيل.

كشفت مراجعة مستقلة نهائية خروج الدفعة الفارغة بعد حذف آخر صف مرفوع؛ أزيل مسار الخروج المباشر على أساس عدد الصفوف، فأصبح parent dirty يمر بتأكيد التجاهل وuploads.discard حتى عندما يصير الجدول فارغًا. يظل منع التنظيف في النتيجة غير المؤكدة أو السياق القديم قائمًا لحماية ملف قد حُفظ. لا ادعاء تحقق تشغيل لدورة رفع الملف من هذا الإصلاح المصدرّي.

أظهر التدقيق كذلك عيبًا موروثًا في تقريب المعاينة: إضافة EPSILON لا تكفي لضمان half-away لقيمة مثل10.075. بعد تجميد تعديل الخطة، صُحح roundDecimal المشترك إلى معامل/أس عشري وباقي قسمة صحيح عبر BigInt، ثم إعادة الإشارة والمقياس؛ roundMoney يحافظ على API لكنه يرث إصلاح المنتصف، فلا يُقصد بعبارات «بقاء السلوك» السابقة الحفاظ على العيب. لا تقريب إدخال أو إعادة حساب محفوظ، ويظل float قبل التقريب تقريبيًا ونتيجة الخادم هي المرجع. وثق التصحيح في UI19 والمهارة وسجل التغيير، وأعيدت الحزم بالمولد. قبول أمثلة المنتصف والسالب والنمط العلمي عند المالك؛ لم تُشغّل اختبارات رقمية.

تستخدم إعدادات `BilledQuantity` و`EquipmentInvoiceTimeSheetSnapshot.Hours` أيضًا ثابتَي السياسة بدل18/6 المكررين؛ الدقة الناتجة نفسها ولا تعديل قيمة أو schema إضافي لهذين العمودين. دقق عامل مستقل الخوارزمية المصححة مصدرّيًا دون ملاحظة مؤكدة أخرى، وأكد دعم ES2022 لـBigInt؛ لا تشغيل حساب أو اختبار.

ملفات النطاق موزعة على: واجهة EquipmentQuotation (القائمة/النموذج/ساعات التفاصيل)، EquipmentMasterAgreement (القائمة/النماذج/التفاصيل/قالب الماليات)، TimeSheet (القائمة/المحرر/نافذة الدفعة الجديدة/النماذج والخدمة/مساعد المدخلات)، وتصحيح DeliveryNote وقالب فاتورة المعدات السابقين؛ وقواميس اللغتين والدليل والمشتركات الستة الرقمية/التحقق. الخلفية تشمل خدمات العرض والاتفاقية والساعات وموضع تقريب كمية الفاتورة، وخرائط القراءة وListVMs، وكيانات/إعدادات العرض والساعات وسعر الاتفاقية، وDTOs الساعات/دفعتها وenum الوردية وpolicy helper وخدمة/Controller الدفعة وموارد اللغتين. لا ملفات المصدر الأخرى ذات تغييرات المستخدم ضمن هذا التسليم.
