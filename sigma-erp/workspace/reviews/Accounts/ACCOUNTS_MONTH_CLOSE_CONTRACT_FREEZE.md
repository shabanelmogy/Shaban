## Frozen starter conditions

- Month record and owning fiscal year must exist, month/year/state must be valid and calendar month must overlap the fiscal-year dates; fiscal year must be Open.
- Close rejects future calendar months. Current month remains eligible: owner asked to block future months, not to require month-end completion. Uses server DateTime.Today, matching current FiscalYear date ownership; runtime server business timezone remains owner verification.
- Every preceding calendar month from fiscal-year StartDate's month to target month must have a Closed tenant-scoped MonthClose record. Missing preceding records block as well as Open records; no requirement to close unrelated earlier fiscal years. Global per-subscription month unique index retained.
- Every nonvoid journal voucher dated within the calendar month must be Approved and IsPosted. All branches, no client filters. Voided vouchers excluded, tenant/live scoping comes from Repository.
- Same existing FiscalYear integrity definition: details required; account ID required; debit/credit nonnegative; exactly one side positive; exact decimal debit/credit totals equal. Also reject month-dated vouchers whose FiscalYearId does not match the period or date lies outside owning fiscal-year dates. No amount tolerances or client sums.
- Starter settlement readiness means the preceding voucher approval/posting/integrity checks. No new bank/customer/supplier reconciliation completion state, allocation requirement, source-document registry or journal generated by close. Those business definitions are not currently proven and are explicitly excluded under owner's starter-scenario direction.
- Reopen requires valid period and Open fiscal year; it does not require voucher readiness or closing order and does not reopen fiscal year. Reopening an earlier month while later months are closed remains allowed, as requested reopening behavior; subsequent close rechecks prior months.

## API and action state

Preserve GetByFiscalYear materialization/list shape and existing authenticated routes. Add GET VerifyValidMonth/{id}, VerifyVoucherApprovals/{id}, VerifyDataInconsistency/{id}; POST CloseMonth/{id}, ReopenMonth/{id}, null body. All return Result<MonthCloseCheckVM>: IsSuccess=true for a completed business evaluation, Entity {isValid:boolean,message:string,issueCount:number,issues:[{code:string,count:number}]}. Failed readiness is isValid=false, like FiscalYear close. Actual exceptions remain HTTP error. Stable codes: monthNotFound, fiscalYearNotFound, invalidPeriod, fiscalYearClosed, monthAlreadyClosed, futureMonth, previousMonthsOpen, vouchersNotApproved, invalidVouchers, periodImmutable, useCloseAction, invalidStatus, closedRecordDelete. Count nonnegative; issueCount is sum of counts. Message is localized; issue code/count drives EN/AR reasons in UI.

CloseMonth is desired-state/idempotent: already Closed does not reopen; ReopenMonth already Open does not close. Final Close re-evaluates eligibility/approvals/integrity together inside one Serializable check-and-write transaction (existing FiscalYear reference). No arbitrary client mutation timeout. Legacy ToggleStatus remains available but routes through the same guarded transition. Add permits only Open valid records; generic Update cannot relocate period identity and its status transition uses same guarded operation; deleting Closed period records is prohibited so an inherited writer cannot bypass the lock. No schema/concurrency-token/permission system invented. Existing metadata GET/open-record generation retained.

Each failed step shows translated reason list and counts, Retry, no Next/Close mutation until that step succeeds. Final transaction failure retains screen and all current reasons. Header screen title and month/year subtitle; readonly mode, primary Edit hidden, contentPadded, shared styling and scroll. Cancel/close controls blocked during request/confirmation; route destruction tears down reads; read checks may use existing20s timeout, mutations no arbitrary timeout. Final confirmation includes record identity. Parent freezes fiscal selection/actions while dialog shown, refreshes same fiscal year's months after successful close, and emits one success only after required refresh (skip mutation interceptor success). Reopen uses existing confirmation, explicit desired-state request, displays failed reasons in shared read-only dialog. Both declared and transport failures have one explicit owning surface via skip-error header; no duplicate global dialog/toast. Existing list columns Month/Year/Status and DTO identity/date/state retained.
