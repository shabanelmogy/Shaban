## Frozen decisions and API

- UI: shared paged invoice list, routed read-only saved invoice view, and routed financial collection generation workspace (UI1/3/4/6/10/13/14/17/19/22–29). Workshop Job list/editor and actual shared EditableCollectionTable/SummaryCards declarations own appearance. Only selected rows have editable requested gross amount; trip/customer/tax/source balances are readonly. No fake direct manual invoice or Edit/Delete controls on this generation surface. Posted correction belongs to existing voucher lifecycle; J-1 forbids deleting posted history.
- GET `LimousineInvoice`: generic pageNo/pageSize (15 default,cap100), exact total; filters tripNo/customerId/fromDate/toDate applied to pickup calendar date. Columns no/tripNo/invoiceDate/pickupDateTime/customerName/driverName/amount/tax/totalAmount; id for view/print. Lean Detail adds vehicleType/pickupLocation/dropoffLocation/description/branchName and no unused navigation plumbing.
- GET `LimousineInvoice/Candidates` with Filters[fromDate,toDate,customerId,branchId]; complete candidate response (no pretend paging): id/tripNo/pickUpDateTime/vehicleType/pickUpLocation/dropOffLocation/customerId/customer/driverId/driver/description/charges/tax/discount/totalAmount/billedAmount/remainingAmount. Eligibility derives from positive actual remaining, not stale Invoiced. Multiple invoices per trip are permitted. Existing trip status eligibility is preserved; no invented Finished-only rule. Live tenant invoices count toward the cap, including unposted drafts; soft-deleted rows do not. Existing overbilling fails closed rather than silently changing history.
- POST `LimousineInvoice/Generate` request `{ invoiceDate, items: [{tripBookingId,totalAmount}] }`. Invoice date is a required local calendar date. Each row ID positive/unique, gross amount positive/currency-scale-valid. One invoice per selected trip per submission; later submissions may add parts. No client customer/tax/discount/total calculation or tenant/number/audit accepted. Backend rereads selected live same-tenant trips and all existing invoices while holding the shared `ExecuteUniqueWriteAsync<LimousineInvoice>` tenant lock. Entire submission succeeds or fails atomically.
- Request gross defaults to remaining in the new editor. Server net = charges − discount; trip total = net + saved trip tax. Requested gross may not exceed remaining. Explicit stored tax is allocated in proportion from saved trip tax, capped to remaining tax; final gross portion consumes the remaining tax to avoid rounding residue. Invoice net = requested gross − allocated tax, both monetary-scale guarded. Existing domain `SetTaxExplicit` sets authoritative total. Never recalculate saved trip tax from current tax settings. Negative net/tax or inconsistent previous tax balances fail, not guessed.
- Existing `InvoiceService.GenerateInvoices` is the accounting writer: add optional `LimousineTotalAmount` on its GenerateInvoiceRequest only for the supported limousine branch, preserving other invoice types and legacy absence (remaining amount, which previously was full amount when no bills existed). It uses the pricing policy and existing journal posting/account resolution, one transaction across dependent saves. No new journal builder.
- Participating dedicated/generic limousine Add/AddList/AddFromScreen and InvoiceService generation/update/delete share the same tenant/type lock, reread cap, and authoritative pricing. Posted limousine edit/delete is rejected under J-1; unposted edits validate excluding self and refresh both old/new trip flags. Do not silently reprice a saved part as a whole trip. Existing non-limousine behavior remains outside scope.
- Trip Invoiced is derived as billed>=total (positive total), not first invoice. Trip price changes/Finish may not lower total below existing billed amount, use the same boundary; Cancel/Delete reject any existing billed amount, including partial. Client trip Invoiced cannot override this derived state. This is necessary to maintain the user's global cap, not merely the new endpoint.
- No entity/EF change or unique TripNo index: multiple invoices are allowed and TPT cap cannot be represented by such an index. Use canonical shared transaction/app-lock owner; all known limousine writers participate. No schema migration needed. Arbitrary SQL/future writers are outside the cooperating lock guarantee and runtime race acceptance remains pending.
- Existing compatibility `AddFromScreenAsync` and generic payloads remain, but their amount inputs are requests only; producer source owns customer/driver/amount/tax. No unused FullListVM/map retained. AuthGuard/interceptors unchanged; no invented authorization API. New service interface implementation registered by actual DI convention after inspection.
