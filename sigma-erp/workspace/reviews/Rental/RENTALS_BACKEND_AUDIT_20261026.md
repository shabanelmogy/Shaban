## Confirmed actionable findings

### B01 — P1: deleted tariff children are still priced into new booking/agreement calculations

`SiGma.Business/Services/TariffCalculateService.cs:34–47` directly queries `context.Tariffs`, includes RentalRates/Protections/Mileage/Extras without live-child predicates and forces `AsSingleQuery`. It later iterates every returned row. In contrast the editor's aggregate read (`TariffService.cs:268–274`) filters every collection with `IsDeleted != true`. The editor's owned reconciliation (`TariffService.cs:342–343`) calls `Context.Remove` for omitted children; `SiGma.DataAccess/SiGmaDbContext.cs:519–529` converts removal to a retained soft-deleted row. The context has no global soft-delete query filter (`OnModelCreating:41–60`).

Trigger: edit a default daily tariff, remove its old rental-rate row at 100 and add a new row at 120. Save, then start a fresh calculation. The tariff editor shows the live 120 row, but the calculator loads both rows; `RentalBookingChargeCatalog.cs:99–102` sums their Rate/TotalCharge to 220 per day. Booking's validation calls this calculator at `BookingService.cs:1228`; Agreement's validation calls it at `Services/AgreementServices/RentalAgreementService.cs:1605`. The public tariff calculation path delegates to it too (`TariffService.cs:251–260`). Thus deleted configuration can change both preview and authoritative saved charges.

Recommendation: use the same live-child scope in this existing rental calculator, preserving root tenant/type/default-card selection and all current pricing rules. Do not remove historical children or alter saved contracts. Verify removal in each of the four child collections, same-key replacement, multiple legitimate rows, null live flags, and a fresh DbContext. No formula redesign is implied.

### B02 — P2: a voided rental still occupies planner cells

`SiGma.Business/Services/RentalPlannerService.cs:108–121` selects every overlapping live agreement and emits HIR, without checking `IsVoided`. Its actual void writer, `SiGma.Business/Services/AgreementServices/RentalAgreementService.cs:483–487`, sets IsVoided and audit fields while retaining the source; `SiGma.Repos/Repository/Repository.cs:41–45` applies only tenant and soft-delete scope. FE `Rental/RentalPlanner/components/list/list.component.ts:208–219` prefers HIR over overlapping BKG in every covered cell.

Trigger: create an otherwise eligible unpaid open agreement with a vehicle, void it through the existing reason action, then reload the planner for its interval. It still paints as hired and can mask a real booking. Recommendation: exclude voided agreements from occupancy while preserving historical closed intervals and current inclusive-day/clipped interval semantics. Do not automatically exclude all closed agreements from historical planning.

### B03 — P2: deleting a draft master agreement leaves its quotation actions disabled

`SiGma.Business/Services/RentalQuotationService.cs:323–330` computes CanUnapprove and CanCreateMasterAgreement with raw `Context.RentalMasterAgreements.Any(agreement => agreement.QuotationId == x.Id)`. That subquery includes soft-deleted masters. `RentalMasterAgreementService.cs:217–231` allows deletion of an unapproved master without child agreements and soft-deletes it. The actual writers use live repository semantics: master creation checks `ExistsAsync` at `:48–50`; quotation unapproval checks `ExistsAsync` at `RentalQuotationService.cs:433–436`.

Trigger: fully approve a quotation, create its unapproved master, delete that master, and refresh quotation list. Both flags remain false even though both server actions are eligible again. Recommendation: derive both flags from the same tenant/live master query as the writers. Preserve the current approval enums and existing rejection/history policy; no unified approval adoption is required.

## Contract and bounded-risk reconciliation

- Tariff update verifies IDs belong to the loaded aggregate, reconciles all four snapshots and uses the existing tenant/selection unique index. B01 concerns the downstream reader, rather than changing these valid ownership checks.
- DriverTimeSheet preserves full-period replacement, one agreement, exact day coverage, distinct dates/IDs, driver existence, owned row identity/date, derived holiday and server-owned overtime. Read/write guards currently check Invoiced and the configured closed-agreement rule, but not IsVoided. Voided agreement time-sheet eligibility and concurrency with the invoicing writer require a frozen domain decision/lock review before extending behavior; this is recorded as unresolved, not an invented new state transition.
- MasterAgreement's retained Update API can edit an approved master without an approval-state guard. The active UI is Frozen create/view, so no UI trigger was established. Record the precise allowed API mutation policy before changing this legacy writer; do not broaden current frontend scope or declare it a confirmed UI bug.
- Known BE19 generic update/deletion, financial VAT/numbering and unified approval backlog are not silently treated as new rental migrations. No generic repository or approved reference module edits are authorized.
